# 并行调研 / 多角度审查

把一件事拆给几个 agent 同时做，每个是**独立的 CLI 进程**、有自己完整的上下文。
你只读它们最后写下的结论，它们读了多少东西跟你的上下文一分钱关系都没有。

## 先判断该不该组队

| 该组 | 不该组 |
|---|---|
| 三个技术方案要各自摸清楚再对比 | 一件事分三步做完（后一步依赖前一步） |
| 同一份代码要从安全 / 性能 / 可读性分别审 | 改一个函数、修一个 bug |
| 五个陌生模块要同时摸清各自的职责 | 已经知道答案，只是要动手 |
| 每块都要读几十个文件才说得清 | 读两个文件就够了 |

判据一句话：**几块互不依赖，且每块都要读不少东西**。

不满足就别组 —— 起进程有开销，确认清单会打扰用户，而线性的活并行不起来。
**拿不准就不组**：单会话做完这件事的代价，远小于组一个没必要的团队。

## 角色

本场景包**只有只读角色**。要改代码的活不在这里 —— 并发写同一个仓库会静默覆盖
（两个 agent 各读各写，后写的盖掉前面的，没有任何报错），那需要 git worktree 隔离，
是另一个场景包的事。

| role | 干什么 | needs | prefer |
|---|---|---|---|
| `researcher` | 摸清一个方案 / 一个模块 / 一份文档，给出可对比的结论 | `stream`, `usage` | — |
| `reviewer` | 从一个**指定角度**审查已有的东西（安全 / 性能 / 边界 / 可读性） | `stream`, `usage` | — |
| `cross-checker` | 复核别人的结论，专门找漏洞和反例 | `stream`, `usage` | — |

**`needs` 声明能力，不绑 CLI 名字。** 绑了的话那个 CLI 没装就整批起不来。
`prefer` 是软偏好，可以不填。

自定义角色照这张表的字段写：`role` 用 kebab-case（它同时是 `.plans/<role>/` 的目录名）。

## 怎么拆

一个 reviewer 审三个角度 ≠ 三个 reviewer 各审一个角度。**后者才是并行**，
而且每个的上下文只装一个角度的东西，结论更实。

拆的时候给每个 agent 的 `task` 写清三件事：
1. **看什么**（哪个目录 / 哪份文档 / 哪个方案）
2. **回答什么**（一个具体问题，不是"研究一下"）
3. **结论要能独立成立** —— 它看不到别人的产出

```
❌ task: "调研导出功能"
✅ task: "读 src/export/ 全部代码，回答：现在支持哪些格式、各自的入口函数是什么、
         有没有共用的中间层。结论写成一张表。"
```

## 派活

调 `team_spawn`，一次一批（最多 6 个）：

```
team_spawn({
  goal: "选一个 PDF 导出方案",        ← 用户靠这句话决定要不要开工，写清楚
  agents: [
    { role: "researcher",   task: "…" },
    { role: "cross-checker", task: "…" }
  ],
  estimate_tokens: 60000              ← 估不准不要紧，用户看得见真实累计；不确定就别填
})
```

用户会看到一张清单并决定开不开工。**他点算了就别再问第二次**，按单会话把这件事做完。

派完**不要一直轮询、也不要替它们干活**。你可以先做别的，或者告诉用户
「派下去了，进度看团队面板」。

## 收活

每个 agent 把结论写在 `.plans/<role>/findings.md`。收活时逐个读，然后：

- **分歧要显式呈现，不要替用户抹平。** 两个 agent 结论不一致时，那份不一致
  往往比一致的部分信息量更大 —— 写清楚「A 说…，B 说…，差别在…」，让用户判断。
- 某个 agent 没写 findings 就说自己完成了 → 让它补一次；第二次还没有就如实
  告诉用户这一份没拿到，别自己编一段补上。
