Jev 插件：从「七个开关」
改为「可信的判断台」

TypeSafe 的 Jev 是对给定材料回答小而明确的问题的判断 API，不是聊天模型，也不会独立完成「资料核对」「评审验收」等工作流。当前插件的主要问题不是 API 接错，而是产品承诺大于代码实际完成度。

依据：TypeSafe 公开文档 + Eas-Term 本地源码。控制台需要账号登录，未读取私人控制台、账单或真实密钥；本报告不修改插件代码。

建议先收缩能力边界：只做一个可解释、可审核的结构化判断入口；时间线增强作为独立、默认关闭的自动化配方。官方能力边界：Jev with coding agents · Primitives · Intent routing

TypeSafe 官方文档真正支持什么

能力正确用法对插件的约束
Choice / Score / Noul闭集选项、明确刻度、是/否概率；结果是结构化答案，不是长篇分析。一个问题只做一个狭义判断；由 Eas-Term 代码决定后续动作。
共享 state，多问题同一份材料可在一个请求里回答多个相互独立的问题。时间线同一候选的里程碑与项目判断不应默认顺序发两次请求。
置信度与模型版本Choice/Score 提供概率相关置信度，Noul 本身就是概率。阈值必须按场景校准；上线流程宜固定模型版本，不宜直接依赖可变的 jev-latest。
模型弱项官方提示算术、日期、间接措辞、无关长材料与对抗文本的风险，中文准确性低于英文。计数和规则判断由代码做；对中文工作流先用真实样本测误判与弃答。

官方来源：Quick start · Primitives · Speculative fan-out · Confidence · Models · Jev 1.13 jaggedness。

当前设计的缺陷 · 按优先级

P0 · 能力表述失真

「分类、资料核对、评审、路由、自定义」尚不是五条可交付工作流

五个 jev_* 工具暴露相同的任意 state / questions，调用后只是透传到同一 runtime.ask。技能文档给了使用建议，但插件代码没有分别实现引用定位、证据映射、验收规则或工具权限决策。因此面板里的能力名会让用户误以为这些工作流已由插件保证。

证据：resources/plugins/jev/lib/service.mjs 的 tools/list、tools/call；resources/plugins/jev/skills/*.md。官方明确 Jev 只返回结构化判断：Coding agents。
P0 · 授权粒度过粗

面板承诺「只发送授权材料」，但宿主无法验证模型填入的材料来源

用户开启总开关和某个能力后，AI 对话节点可用任意提供的 state 发起调用；宿主当前不对该内容做来源证明、单次出站预览或单次确认。固定服务端点、密钥隔离、停用能力仍有效；问题是数据范围的承诺比代码可强制执行的边界更强。这是静态代码推断，不是已发现泄露事件。

证据：resources/plugins/jev/lib/service.mjs、src/main/pluginHost.ts、resources/plugins/jev/ui/panel.html。
P1 · 判断没有弃答策略

时间线项目推荐把最高分选项直接变成项目 ID

即使置信度很低，选中某项目也会显示推荐；只有明确选到 unknown 才返回空。虽然不会自动移动记录，仍可能造成误导。候选本来还有宿主掌握的来源项目，应先用确定性来源判断，必要时才请求模型；低置信度与「无合适项目」都应保留人工选择。

证据：resources/plugins/jev/lib/timeline.mjs。官方建议按风险设阈值：Confidence；工具候选也需保留「none」与主代理判断：Skill suggestion。
P1 · 自动增强生命周期待验证

时间线事件似乎只在 Jev 进程已存在时才会调用增强

宿主通过现存插件注册表取得 Jev 进程，没有主动拉起；面板关闭或进程回收后，可能静默跳过增强并仅保留原候选。这是代码路径推断，必须做真实生命周期 E2E 才能定性为线上 bug。

证据：src/main/pluginHost.ts 的时间线桥接逻辑。
P1 · 用量可见性不足

「用量与记录」实际只是短时 toast，不是可核查账本

本地保存了最多 200 条请求元数据和成功调用的输入/输出 token，但 UI 只弹最近五次来源与状态；隐藏的详情区未被渲染。日限额与进程生命周期上限同时存在，口径不同；cost 固定为空。可做「依据公开单价的估算」，但不能冒充服务商实际账单。

证据：resources/plugins/jev/lib/usage.mjs、lib/runtime.mjs、ui/panel.html；公开价格与 token 口径：Models、API reference。
P2 · 小但真实的可用性与运维债

连接状态、模型漂移与失败路径需要可解释

进程内连接状态与已保存密钥状态没有分层；验证连接使用一次真实判断请求；业务固定用 jev-latest，可能随模型更新改变阈值表现；429/529 目前没有有界重试。重试必须谨慎处理超时后结果未知的计费风险，不能无脑补发。

证据：resources/plugins/jev/lib/service.mjs、lib/client.mjs、ui/panel.html；官方 Models、API reference、JavaScript SDK。

建议的新产品结构

01 / 判断台

首屏不是开关，而是「选一个任务 → 给材料 → 预览出站内容 → 判断 → 查看理由与不确定性」。首个示例可用低风险的反馈分类。显示原材料片段、具体问题、闭集选项、模型版本、答案及概率；后续动作由人或宿主确定。

02 / 自动化

只放真正的后台配方，与手动判断分开。时间线里程碑增强继续默认关闭；项目建议先以来源项目为准，争议时才调用。每个配方单独显示触发条件、会发送什么、预算、弃答与关闭方式。

03 / 连接与用量

状态分为未配置、密钥已保存但未验证、已验证暂停、运行中、服务异常、预算耗尽。提供按日期/来源的调用记录和输入 token 估算费用；实际账单仍以 TypeSafe 控制台为准。

全局仅保留一个醒目的「暂停所有 Jev 出站」操作。首次启用应明确第三方数据处理边界，不把「五项默认选中」等同于每次材料授权。公开文档对常规账号没有承诺默认零留存；企业 ZDR 是另行条件。TypeSafe legal

可落地的技术重构

  1. 一套判断内核：内部 DecisionService 统一固定端点、预算、取消、日志；每个业务配方把问题模板、输入过滤、候选选项、阈值、版本和回退条件放在可评审配置中。
  2. 缩小对话工具面：不要继续暴露五个同构空壳。通用 jev_decide 仅供用户明确请求；正式的分类、证据核对、工具推荐须有各自输入校验和结果解释，做不全就先不展示开关。
  3. 授权由宿主掌握：宿主记录材料来源与明确授权范围；对话模型构造的原始 state 在出站前预览并确认，后台配方需预设数据白名单。敏感内容默认不送。
  4. 批量与弃答：同一时间线候选的独立问题合并一次请求；项目来源能确定则不用模型；低置信度不展示确定推荐。处理算数/日期靠代码，不让 Jev 猜。官方 fan-out。
  5. 固定可测版本：评估通过的配方固定模型版本，单独审查升级。面板显示模型与问题模板版本；按中文样本重新校准阈值。官方模型说明。
  6. 用量和失败要诚实：展示成功请求的 token 与按当期价格估算的花费；失败、撤销、超时标注费用未知；日上限与进程上限合并成可理解的一套预算。429/529 若加重试，需有次数/退避与未知结果保护。

上线顺序与验收门槛

阶段交付通过标准
P0 / 说真话改能力文案；停用同构空壳的夸大入口；补单次材料预览与授权说明；用量页显示真实记录。用户能说清「何时发送哪段数据」「返回的是判断还是执行结果」；关闭后没有新出站。
P1 / 单一流程先做一个端到端判断台和一条受控时间线配方，模板版本化、置信度弃答、同材料批量问题。非敏感中文测试集上对比现有规则/人工基线，记录误判、弃答、延迟、token 与估算成本。
P2 / 扩展按证据逐个加资料核对、工具推荐等特定配方；连接状态机、模型升级与失败恢复。真实 TypeSafe 账号、小样本在线 CLI、面板生命周期、断网/429/529、macOS/Windows 逐项验证。
当前不能声称已验证：

现有 2026-09-22 验收文件记录 liveProvider=false、realOnlineCLI=false、windows=false。这些是当时的验收状态，不是今天账号能力的证明。必须在不暴露密钥、少量可控付费调用的前提下补做真实测评，才可承诺中文准确率或自动化效果。

已有基础，不应推倒

当前实现已经有一些正确的安全边界：凭证由宿主安全设置管理而非插件网页输入；API 端点固定为 TypeSafe HTTPS，拒绝重定向；请求/响应大小与超时受限；默认关闭、可撤销；时间线建议不会自动移动项目或把模型意见当验收证据。重设计应保留这些边界，优先修正能力叙述、授权粒度、弃答和可观测性。

本地依据：resources/plugins/jev/lib/client.mjs、lib/runtime.mjs、lib/timeline.mjs、src/main/pluginHost.ts。
