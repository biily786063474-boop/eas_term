性能评估：Windows 未响应能不能治

你报 Windows 上出现未响应。我在一个已经跑了 2 天 5 小时的 macOS 实例上采了真实数据， 再对照代码找 Windows 特有的开销。结论先说：CPU 不是瓶颈，内存和主线程阻塞才是； 有四项优化值得做，其中两项几乎无代价。

采样实例存活 2 天 5 小时画布 38 个节点 渲染进程 7 个系统负载 4.34 / 15 核

实测

先纠正一个我自己差点搞错的数
ps 的 %CPU 是累计平均，不是瞬时值
第一次采样看到主进程 62.7%、Renderer 44.4%，差点当成「CPU 烧满」写进报告。 但 macOS 上 ps 的 %CPU 是进程整个生命周期的平均——这进程跑了 2 天 5 小时。 用 sample 抓调用栈印证：热点全是 mach_msg / kevent / uv__io_poll， 此刻是空闲等待。改用 top 取瞬时值才是下面这组真数据。
进程瞬时 CPU内存说明
GPU Helper19.3%915 MB画布在渲染，38 个节点
Renderer（主窗口）15.9%1227 MB最大的一块
主进程5.9%903 MBIPC 转发 + PTY
另有 6 个小 Renderer（webview / Helper），21~136 MB 不等

合计约 3 GB，系统负载 4.34 / 15 核 —— CPU 有余量，内存才是压力所在。 画布上挂着 38 个节点：12 个 AI 对话、10 个网页、7 个代码预览、2 个图片。

已经在起作用的三项优化（别误拆）
· 视口裁剪（PaneLayer，余量 600px）—— 代码里记着实测对照：30 个终端平移 6 秒， 不裁 536→668 MB 一路爬，裁了全程稳定 378 MB
· 网页节点懒挂载 + 120 秒离屏回收（WebView.tsx）—— 离屏的书签节点不建 Chromium 进程
· scrollback 已从 20000 降到 5000（我的记忆里还写着 20000，是过期的）

Windows

四个 Windows 特有的开销

我没有 Windows 机器，下面是代码分析 + 平台已知行为，不是实测。 标注了每条的确信度。

① 每次关终端都起一个 PowerShell 枚举全系统进程 最可疑

确信度 高位置 pty.ts shellsWithChildren

判断「有没有命令在跑」时，Unix 走 ps -axo ppid=（毫秒级）， Windows 走 powershell.exe -Command (Get-CimInstance Win32_Process).ParentProcessId。

PowerShell 冷启动本身就要 300~800ms，Get-CimInstance Win32_Process 还要走 WMI 枚举全部进程——进程多的机器上秒级很常见。这个调用发生在关终端、关项目、退出确认时， 而且是 await 的，那几秒里界面就是「未响应」。

触发时机
关终端 / 关项目 / 退出前确认（pty:busyByIds、anyPtyBusy）
已有超时
4000ms —— 也就是说最坏情况会卡满 4 秒才放弃

② 后台节流三个开关全关了 代价明确

确信度 高位置 index.ts 启动

disable-background-timer-throttling、disable-renderer-backgrounding、 disable-backgrounding-occluded-windows 三个全开着。

理由是充分的，代码里有实测：最小化 10 秒后 setInterval 只剩 26%、rAF 只剩 11%， 而终端输出靠 rAF 写进 xterm——一节流，agent 在后台跑出来的东西全堵在缓冲里。

但代价是：这三个开关是全局的，画布上那 10 个 webview 也一起不被节流， 即使完全离屏、完全看不见，也在全速跑自己的 JS 和动画。Windows 上多窗口调度本就更吃紧。

③ 主进程 IPC 里的同步文件 I/O 中等

确信度 中规模 293 处 readFileSync 类调用

其中约 20 个直接躺在 ipcMain.handle 里——每次调用都阻塞主进程事件循环， 那期间所有窗口的 IPC 全部排队。agentHistory:list 要 readdir + 逐个读文件， 历史多了单次就可能几十毫秒。

Windows 的文件 I/O 比 macOS 慢（尤其有杀毒软件实时扫描时），同一段代码的阻塞时间会显著更长。

④ 每个终端 4 张 canvas，Windows 上 GPU 合成路径不同 较低

确信度 低位置 TerminalView CanvasAddon

终端用 CanvasAddon（曾用 WebglAddon，因半透明背景叠影改回）。视口裁剪已经挡住了大部分开销， 但 Windows 的 GPU 合成与 macOS 差异较大，这条需要在 Windows 上实测才能定性。

优化

四项，按性价比排序

A. 换掉 Windows 的进程枚举方式 几乎无代价

怎么做
用 wmic process get ParentProcessId，或直接 tasklist /fo csv； 更彻底的是用 Node 原生方式（process.kill(pid, 0) 探活 + 维护自己的子进程表），完全不起外部进程
收益
关终端从「可能卡 1~4 秒」变成毫秒级
代价
需要在 Windows 上验证命令输出格式；wmic 在新版 Windows 上已弃用，要做回退
影响功能
无——只换实现，判据不变
风险
低。有超时兜底，失败时退回「当作不忙」，和现在行为一致

B. 给离屏 webview 单独恢复节流 要小心

怎么做
三个全局开关保持关闭（终端需要），但对画布上的 <webview> 单独设 backgroundThrottling: true，或在离屏时主动 setBackgroundThrottling
收益
10 个网页节点离屏时不再全速跑，CPU 和电池都受益
代价
离屏网页里的计时器/动画会变慢——但它们本来就有 120 秒离屏回收， 被回收的更彻底，所以这条影响的只是「离屏 0~120 秒」这个窗口
影响功能
可能有：如果有人用网页节点挂着一个需要持续刷新的页面（如监控看板）， 离屏时会变慢。需要你确认有没有这种用法
风险
中。要实测确认不会影响终端——它们不是 webview，理论上不受影响

C. 把热路径上的同步 I/O 改异步 无代价但工作量大

怎么做
先量：给几个高频 handler 加耗时埋点，跑一天看 p95。只改真正慢的那几个， 不做无差别重写
收益
主进程不再被单次文件读写卡住；Windows 上收益比 macOS 明显（文件 I/O 更慢 + 杀毒扫描）
代价
纯工作量。约 20 个 handler，逐个改 + 逐个验
影响功能
无——但改的过程中容易引入竞态（原来同步保证的顺序没了）， 每个都要想清楚「并发调用会怎样」
风险
中。同步改异步是经典的引 bug 途径，必须一个一个来、每个都有测试

D. 限制画布上同时活跃的重节点数 改行为

怎么做
超过 N 个 AI 对话 / 网页节点时，把最久没看的挂起（保留截图占位，点了再恢复）
收益
内存上限可控。当前 38 个节点 3 GB，这是唯一能压住总量的办法
代价
改变用户可感知的行为：切回去时要等它恢复
影响功能
有。AI 对话挂起后会话状态怎么办？12 个 agent 会话如果被挂起， 正在跑的任务会不会断？这条不搞清楚不能做
风险
高。建议放到最后，且先做 A/B/C 看够不够

结论

是否可接受
建议做：A + B
A（换进程枚举）几乎零代价、零功能影响，而且直指「未响应」这个症状—— 关终端时卡 1~4 秒正是最像「未响应」的表现。
B（离屏 webview 节流）代价明确且有限（只影响离屏 0~120 秒的网页节点）， 收益是 10 个 webview 不再空转。
谨慎：C
收益真实但工作量大，且同步改异步容易引入竞态。建议先加耗时埋点量一天， 只改真正慢的那几个，而不是无差别重写 293 处。
先别做：D
它是唯一能压住内存总量的办法，但会改变你能感知的行为， 而且「AI 对话挂起后正在跑的任务怎么办」这个问题不解决就不能动。
我不知道的部分，得你补
· 未响应发生在什么时候？关终端时？切视图时？还是一直卡？——A 直接对应「关终端时卡」， 如果是别的场景，优先级要重排
· 那台 Windows 的配置（内存多大、有没有杀毒软件实时扫描）——8 GB 的机器跑 3 GB 的 app 会换页， 那是另一类问题
· 画布上开了多少节点——如果也是三四十个，D 的优先级要提前
· 我没有 Windows 机器，上面四条 Windows 特有开销都是代码分析 + 平台已知行为推出来的， 没有一条在 Windows 上实测过

下一步

如果要动手

第一步：先量，别先改

在 Windows 版里加一个轻量耗时埋点（IPC handler 的 p95、PowerShell 调用的实际耗时）， 跑一天把数据带回来。现在这份报告里的 Windows 部分全是推断， 埋点能把它变成事实——省得改完发现根因是别的。

第二步：A 单独发一版

它零功能影响、改动集中在一个函数，适合单独验证。如果未响应就此消失，后面几项都可以缓。

第三步：按埋点数据决定 B / C
