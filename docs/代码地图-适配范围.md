# 代码地图 · 适配范围与局限

> 2026-09-03。判据全部来自**跑用户真实的 29 个项目**，不是推断。
> 改了入口发现或领地推导，回来更新这份文件。

## 一句话

代码地图画的是 **JS/TS 模块之间的 import 关系**。仓库里有 JS/TS，它就画得出来；
没有（Swift / Python / C++ / 纯 HTML / 纯文档），它会**说清楚看到的是什么**，而不是报错。

## 实测覆盖：29 个项目

| | 数量 | 说明 |
|---|---|---|
| 画得出来 | **16** | 从 1 个模块的到 2925 个模块的都有 |
| 画不了 | 13 | 全部核实过：**JS/TS 文件数为 0** |

改造前只有 **1 个**能画（就是开发时用的那个仓库）。三个根因：

### ① 入口只按约定猜 → 只中自己见过的布局

原来靠一张写死的候选表（`src/main/index.ts` 之类）。现在四路取并集：

1. 候选表（扩到 `.js/.jsx`、`electron/main.js` 等 26 个）
2. **`index.html` 里的 `<script src>`** —— Vite 项目的真入口写在这儿，
   package.json 的 `main` 根本不指它（taptv：只看候选表 21 个模块，加上 HTML 是 445 个）
3. `package.json` 的 `main` / `module`
4. **`entriesFromDirs`：扫所有装着源码的目录** —— 保底那层，不靠任何约定

### ② 绝对路径会被 dependency-cruiser 折坏

**入口必须传相对 `baseDir` 的路径。** 它把绝对入口先按 `process.cwd()` 折成相对，
再拿 `baseDir` join 回去：

```
cwd = /…/Projects/vibe coding/terminal      root = /…/Projects/taptv pad
relative → "../../taptv pad/electron/main.js"
join     → "/Users/biily/Biily/taptv pad/electron/main.js"   ← 少了 Projects/ → ENOENT
```

只有「cwd 恰好等于项目根」的那一个能过 —— 也就是开发时用的那个。

### ③ 领地表是本仓库专用的

`TERRITORIES` 编码的是图纸 10 的真实知识（禁区、高耦合）。换个项目一条也命中不了，
**3229 个模块全落进「未登记」**，图是一坨没有结构的灰点。

现在：命中率 < 50%（或模块少于 10 个）就转 `derived` —— 按项目自己的目录结构分组，
**颜色改成表达耦合轻重**，图例文案跟着换。对陌生项目写「安全边界」是编造。

## 还剩的局限

| 局限 | 表现 | 能不能修 |
|---|---|---|
| **只认 JS/TS** | Swift / Python / C++ / Rust 项目画不了 | 换解析器才行，不是配置问题 |
| **框架专有格式** | `.astro` / `.vue` / `.svelte` 里的 import 看不见（Astro 项目实测 0 模块，退回目录扫才有 49 个） | 要自己写这几种的 import 提取 |
| **大项目慢** | 2925 模块约 5.6 秒（同步阻塞主进程那一小段） | 未做：可以放 worker |
| **`dirs` 口径含死代码** | 没认出具名入口时扫全目录，会带上没人 import 的脚本 | 已在状态栏如实标出（「按目录」/「按入口」） |
| **动态 import 的字符串拼接** | `import('./x' + name)` 这类连不上 | 静态分析的固有边界 |

## 两条容易改回去的

- **`isLocal` 必须落到「磁盘上真有这个文件」。** 光看字符串形状拦不住裸说明符 ——
  `fs` / `util` / `@scope/pkg` 都满足「不以 node_modules 开头、不是绝对路径」，
  于是图上多出一堆不存在的节点（本仓库实测 16 个，别人的仓库几十上百个）。
- **循环依赖那块默认折叠。** 本仓库的环才 3 条边，别人的项目一个环 35 条，
  摊开会把主视图整个挤出屏幕。折叠头上仍写着「几个环 · 几条边」—— 收细节可以，藏问题不行。
