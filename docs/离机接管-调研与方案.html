外出断网时，让 Mac mini 接着把任务跑完

调研结论先说：你要的东西不需要"接管"机制。真正省事、也最可靠的做法是 让长任务一开始就跑在 Mac mini 上，MacBook 只当显示器——断网时任务根本不受影响， 因为它从来就不在 MacBook 上跑。

日期 2026-07-31 调研对象 MacBook Pro ↔ Mac mini M4 基础设施 已具备 7 成 状态 待你选方案

Verdict

最省事的方案，和你设想的不是同一个

你描述的是「跑到一半 → 转发给 Mac mini → 它接着跑」。这个「接管」动作是整套方案里 最难、最容易出错的一环，而它其实可以被绕过。

核心判断

「中途接管」难，「一直在那边跑」易，两者效果对你是一样的。

因为你的痛点不是「任务必须在 MacBook 上开始」，而是「我离开时任务不能停」。 只要长任务从一开始就在 Mac mini 的 screen 会话里跑， MacBook 断网 / 合盖 / 关机都与它无关——你回来重新 ssh 进去， 它要么跑完了，要么还在跑。不需要迁移任何状态。

Decomposition

你这一句话里其实是四个独立问题

把它们拆开，每个的难度和解法都不一样——混在一起谈会得出"这事很复杂"的错误结论。

子问题本质是什么解法难度
① 断网为什么停 停的不是"任务"，是 AI 推理。npm build 断网照跑， 但 agent 要调 API 才能想下一步 让需要联网的那一端待在有网的地方（Mac mini 在家，有网） 已明确
② 怎么"转发" 三种完全不同的架构，工作量差一个数量级。
见下一节「三个方案」		 推荐不做转发，改成一开始就在远端跑 需你选型
③ 文件怎么回来 本质是双向同步，而双向同步必然要处理冲突 用 git 分支，不用 rsync。见「文件回流」节 有成熟解
④ 合盖怎么办 你说"外出断网"，但外出多半先合盖—— 合盖后 MacBook 连本地任务都停了，比断网更早发生 同 ①：任务不在 MacBook 上就不受影响 被 ① 覆盖
④ 这条你可能没意识到

MacBook 合盖即睡眠，本地 PTY 里跑的一切当场暂停（不是继续跑，是冻住）。 所以哪怕你外出时手机开热点保持联网，只要合了盖，任务照样停。 这反过来说明："让任务离开 MacBook"是唯一真正管用的方向， 比研究"断网时怎么办"更根本。

Options

三个方案，按工作量从小到大

它们不是互斥的——B 可以作为 C 的补充，但我建议先只做 C。

方案 C 远程常驻：任务一开始就在 Mac mini 上跑 ← 推荐

# 你在 Eas-Term 里开一个「远程终端」，它实际执行的是：
ssh macmini -t 'screen -R eas-<任务名>'

# 之后一切照常：cd 项目、跑 claude、让它干活
# 外出 → 合盖 → 断网 → 完全不影响，因为进程在 Mac mini 上
# 回来 → 同一条命令 → screen 自动重连，输出一个字没丢

好在哪

  • 不需要迁移任何状态——没有"接管"这个动作，也就没有接管失败
  • 断网、合盖、关机、换网络，对任务都无影响
  • screen 断线自动保留，重连即见完整输出
  • Eas-Term 侧改动极小：PtyCreateOptions 加一个 remote? 字段， pty.spawn 那行把 shell 换成 ssh。约 40 行

代价

  • 要提前决定哪些任务放远端跑——临时起意的任务享受不到
  • 文件改在 Mac mini 上，本地看不到（要 git 拉回来）
  • 编辑体验：本地 IDE 改不了远端文件，除非挂 SMB 或用 VS Code Remote
  • Mac mini 上要有一份项目代码，且要保持更新

方案 B 中途交接：把会话搬过去

Claude Code 的会话是完整落盘的（~/.claude/projects/<编码路径>/<sessionId>.jsonl）， 理论上可以：同步项目 + 同步 jsonl → Mac mini 上 claude --resume <id>。

两台机器的用户名都是 biily、路径结构相同，所以那个"路径编码"的目录名天然一致—— 这一点意外地有利，省掉了路径重写。

但我不推荐先做这个

交接时机要人判断（"我马上要走了"），交接过程中两边状态可能打架， 而且正在执行中的那一步会丢（比如 agent 刚发出一个 30 秒的命令）。 它解决的问题，方案 C 用"根本不需要交接"绕开了。 建议等 C 跑顺了、确实遇到"临时起意的任务也想搬走"时再做。

方案 A 完整远程后端：Eas-Term 变成瘦客户端

PTY 全部远程化，画布、文件树、MCP 都指向 Mac mini。这是"把 Eas-Term 改造成远程开发工具"， 工作量以周计，而且会动到已经稳定的 PTY / MCP / 密钥注入三条链路。 收益相对 C 只是"不用提前决定"，不值这个价。列在这里是为了说明它被评估过并被否掉。

Sync-back

改过的文件怎么回到 MacBook

这一节独立于方案选择——无论 B 还是 C，文件回流都是同一套。

用 git，不要用 rsync

你的诉求里有"暂存"和"合并"两个词，那正是 git 的本职。 而 rsync（包括现成的 projects-sync.sh）是覆盖语义—— 它不知道哪边更新，一旦两边都改过，后跑的那次会静默抹掉一边的工作。 

# Mac mini 上，agent 干完活：
git switch -c remote/2026-07-31-重构登录
git add -A && git commit -m "..."

# MacBook 回来后：
git fetch macmini                       # 把 Mac mini 当 git remote
git log --oneline macmini/remote/...   # 先看它干了什么
git merge macmini/remote/...          # 或 cherry-pick 挑着要

不需要 GitHub 中转——git 支持直接把另一台机器当 remote： git remote add macmini biily@10.9.0.2:~/work/<项目>，走的还是那条 WireGuard 隧道。

一个必须定的规矩

Mac mini 上的产出永远提交到独立分支，永不直接动 main。 理由：你回来时可能已经在 MacBook 上改了别的东西， 让两边的工作在分支上相遇、由你决定怎么合，比"自动同步"安全一个数量级。 分支名带日期和任务，方便一眼认出。

Risks

两个真正可能让方案失败的问题

其余都是工程量问题，这两个是"可能根本走不通"的问题。

风险 1 · 账号并发（未确证，需实测）

Claude Code 订阅账号在两台机器上同时跑 agent，是否被允许？我没有确证， 也不打算凭印象给你答案。可能的结果从"完全没事"到"触发风控"都有。

验证成本很低：Mac mini 上装好 claude、登录同一账号， 两边各跑一个小任务，观察是否有限流或掉登录。这一步应该排在所有开发之前。

风险 2 · 密钥怎么到 Mac mini

Mac mini 上的 agent 要用 API key（就是今天刚做完的密钥柜里那些）。 而密钥柜的加密绑定本机钥匙串——secrets.json 拷过去解不开， 这是刻意设计的安全属性，不是缺陷。

所以 Mac mini 需要自己存一份。这不算大问题，但要意识到： 密钥柜目前没有导出/同步功能，两台机器就是两份独立的柜子， 轮换密钥时要改两处。

问题影响 / 对策
