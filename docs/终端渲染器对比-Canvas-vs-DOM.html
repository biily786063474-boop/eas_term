终端渲染器：现在的 CanvasAddon 该不该换成 DOM

同一台机器、同一份画布、同样的操作，把两种渲染器各跑一遍。结论先说：不建议换——收益只在「三十个终端同屏」这一种场景出现，而且刚做的视口裁剪已经把那个场景的问题解决掉了大半。

日期 2026-08-06 版本 0.4.8 + 未发布改动 xterm 5.5 / addon-canvas 0.7 Chromium 138

Verdict

结论

两种渲染器在你日常最常用的场景（分屏、一个终端）上没有可测量的差别；差别只在三十个终端同屏时出现，而那个场景的内存问题已经被视口裁剪解决了。

建 议

保持现状（CanvasAddon），不换。

  • 唯一有收益的场景是「三十个终端全在视口内」，那时省 85MB（10%）。但视口裁剪已经让这个场景不再发生——正常使用时视口里只有几个终端，其余全 display:none。
  • 换渲染器的风险面很大且本轮没有覆盖：Claude Code 那种全屏 TUI、中文宽字符对齐、选区、连字、光标形状——这些都要真用一段时间才暴露。
  • 历史上换过一次渲染器（WebGL → Canvas），起因就是「平时看不出来、快速滚动才花屏」的那类问题。渲染器的坑不会在基准测试里出现。
什么情况下值得重新考虑

如果你之后经常把三十个终端摊开在一屏里长时间盯着（而不是平移浏览），那 85MB 和 39MB JS 堆是实打实的。到那时再换也不迟——这份数据留着就是为了那一天。

Method

怎么测的

两次测量之间只改一行代码（加/去 term.loadAddon(new CanvasAddon())），其余完全相同：同一台机器、同一份画布存档、同一套 CDP 脚本、同样的操作序列。

# 唯一的差异点 —— TerminalView.tsx
CanvasAddon 组   term.loadAddon(new CanvasAddon())
DOM 渲染器组     // 注释掉，xterm 自动回退到内置 DOM renderer

# 两个场景，各跑一遍
场景 A  分屏 · 单个终端 848×481
        → 敲 seq 1 3000，量输出耗时
        → 滚轮 30 次，量耗时
        → 截图比画质

场景 B  画布 · fit 全部 · 30 个终端同屏可见
        → 持续平移 6 秒，每 1.5 秒采一次 renderer rss
        → 量 canvas 张数 / 行 DOM / JS 堆

采样用 ps -axo rss 读进程常驻内存，页面内指标走 CDP Runtime.evaluate。每组只跑一轮，没做多次取均值——所以下面 5% 以内的差异不要当真，只看数量级。

吞吐和滚动完全打平。这有点反直觉——通常认为 canvas 比 DOM 快——原因是这个场景的瓶颈根本不在渲染：3000 行输出的 1 秒里，大部分时间花在 PTY → IPC → term.write() 这条链路上，两种渲染器拿到的都是同样节奏的数据。

DOM 渲染器多出来的 972 个节点，是那个可见终端的 26 行 <div> 加上每行内的字符 span。只有可见终端才产生行 DOM，隐藏的 29 个终端一个都不产生——这一点在场景 B 里很关键。

内存走势（平移的 6 秒里，每 1.5 秒一采）

CanvasAddon   619 MB → 827 → 818 → 835
DOM 渲染器    545 MB → 634 → 750 → 750

两者都在涨 —— 涨的是「可见终端在平移时不断重绘」这件事本身，
不是某一种渲染器的锅。CanvasAddon 涨得更快更高，因为它每帧
要重新分配 4 张后备存储并重传纹理。
但这个场景已经不会发生了

同一天做的视口裁剪（6f99a2e）已经让画布只渲染视口内的终端。同一份画布，同样平移 6 秒：

裁剪前   536 → 578 → 623 → 668 MB   一路爬
裁剪后   378 MB 全程不动

换句话说：换渲染器能省的 85MB，视口裁剪已经省了 290MB，而且是在不动渲染管线的前提下。

Visual

画质对比

同一段输出、同一块区域、放大到 1:1 像素比对。

结 果

肉眼看不出差别。整屏像素差异 0.7%，全部来自行基线的亚像素对齐——不是字形质量问题。半透明毛玻璃背景下两者都干净，没有出现历史上 WebGL 那种叠影。

这一条值得单独说，因为它是当初从 WebGL 换回 Canvas 的唯一理由。docs/终端花屏-渲染优化方案.html 里记着：WebGL 增量重绘配上 allowTransparency: true + 半透明主题背景（rgba(…, 0.45)），快速滚动时用半透明色「擦除」旧像素，误差逐帧累积成叠影。

DOM 渲染器在原理上免疫这个问题——它不做像素合成，半透明交给浏览器合成器处理。所以如果哪天真要换，DOM 是比 WebGL 更安全的方向。

Not Covered

这轮没测到的东西

下面每一条都可能推翻上面的结论，而基准测试照不到它们。

反对换的主要理由，就在这一节

这些全是「平时看不出来、真用起来才炸」的类型——和当年 WebGL 花屏一模一样：慢速输出时每格能被干净重绘一次，误差不累积，所以基准测试永远是绿的。
