Agent 不该是终端，
也不该没有身体

跨进程多 Agent 编排的完整设计。三条主干：会话活在主进程（所以 agent 跑着也不占你画布）、 要不要用多 agent 是项目的属性（Frame 头上一个开关，关着就永远不提）、 运行时不认识任何角色（角色表是可换的场景包，加新场景不改一行代码）。 重点在错误矩阵与挽回机制：14 种失败，逐条给出检测信号与兜底。

Verdict

关键技术事实（已核实）

agentChat:start 起的 CLI 进程活在主进程的 sessions Map 里， 渲染层只是按 sessionId 订阅事件流。

也就是说 agent 会话不需要画布节点就能跑。你要的「不侵占工作空间」不是靠隐藏节点实现的， 而是这些 agent 本来就不必有节点 —— 节点只是你想看它时才挂上去的一块屏幕。

并发写同一个仓库。 CCteam 在同进程里靠「任务划分」避免冲突 —— 那是君子协定， 靠 prompt 约束。跨进程是真并发：backend-dev 和 reviewer 同时改一个文件， 后写的直接盖掉前面的，git 也帮不了你（都在同一个工作区）。

这不是加个锁能解决的工程细节，它决定了架构：写码 agent 必须各自跑在 git worktree 里。 详见错误矩阵 E-07。不做这一层，这套系统跑三天就会毁掉一次你的工作区。

Architecture

进程 / 状态 / 视图，三层分开

这三层现在是纠缠的（关掉节点 = 杀掉会话）。做多 agent 必须先把它们拆开， 否则「不显示节点」等于「杀掉 agent」。 

┌─ 视图层（可有可无，随时开关）────────────────────────┐
│  团队面板（画布组件）        agent 详情（临时 agentChat 节点）
│    谁在干什么 / 进度 / 卡住      ↑ 点某个 agent 才挂上，看完就关
└──────────────────┬───────────────────────────────────┘
                   │ 只订阅，不持有
┌─ 状态层（磁盘，唯一真相）─────────────────────────────┐
│  .plans/<项目>/team.json     ← 团队花名册 + 每个 agent 的状态机
│  .plans/<项目>/<role>/       ← 各 agent 自己的 task_plan/findings/progress
│  主 agent 的上下文压缩了也不影响这一层
└──────────────────┬───────────────────────────────────┘
                   │ 主进程读写
┌─ 进程层（主进程 sessions Map）────────────────────────┐
│  claude ×2   codex ×1   ...   ← 各自独立的 CLI 子进程
│  节点关掉 ≠ 进程杀掉（这是要改的第一件事）
└───────────────────────────────────────────────────────┘
这里有一处必须改的既有行为

现在关掉一个 agent 节点会 killPanePty 掉底层会话（见 store/shared.ts， 当初这么做是为了防止「关了节点但 CLI 还在后台烧 token」）。 多 agent 场景下这条规则要按来源区分：用户手动开的会话照旧（关 = 杀）， 团队派生的会话关节点只是收起视图，杀不杀由团队面板决定。 不区分的话，你想看一眼某个 agent 然后关掉窗口，就把它干掉了。

要新增的 4 个 MCP 工具

工具做什么底层
team_spawn按角色清单批量起会话并投递首条任务agentChat:start（已支持带首条消息）
team_status查花名册 + 每个 agent 的状态 / 最后活动时间 / 累计用量读 team.json + sessions Map
team_send给某个 agent 追加指令（纠偏、补充、叫停）agentChat:send
team_dissolve解散：停会话、收视图、归档 .plans/agentChat:stop + 文件操作

注意没有 team_read_findings 这类工具 —— 主 agent 读子 agent 的产出直接用 Read 就行，那些就是普通文件。能用文件系统解决的不要做成工具， 每多一个工具就多一份常驻 schema 成本。

Container

团队面板：一个画布组件，不是一堆终端

你的判断是对的 —— 往画布上撒 5 个终端节点是设计事故。现有的画布组件注册表 （CANVAS_COMPONENTS，已有 git / design 两个）正好是这个容器的落点， 注释里写着「新增一个画布组件 = 写一个 def 并 push，无需改动其它文件」。

面板长什么样

┌─ 团队 · 重构导出流程 ──────────────── 3 跑 / 1 完 / 1 卡 ─ ⊟ ─┐
│                                                                │
│  ● researcher    调研三种导出格式        4m12s · 12K tok  〉│
│  ● backend-dev   实现 PDF 导出           2m03s · 31K tok  〉│
│  ◐ frontend-dev  等审批：写 src/export/      已等 6m       〉│
│  ○ reviewer      等 backend-dev 交付                          │
│  ✓ custodian     已更新 docs/index.md        48s · 3K tok   〉│
│                                                                │
│  ──────────────────────────────────────────────────────  │
│  本批累计 $0.83 · 46K tok · 起于 14:22        [全部叫停]  │
└────────────────────────────────────────────────────────────────┘

一行一个 agent，行内说清三件事

  • 在干什么 —— 当前任务标题，不是滚动的日志
  • 健康度 —— 跑 / 卡 / 等审批 / 等依赖 / 完 / 崩
  • 烧了多少 —— 时长 + token，这是你唯一需要盯的数字

点 〉 才展开完整会话

临时挂一个 agentChat 节点在面板旁边，你可以看完整对话、插一句话纠偏、 或者接管。关掉这个节点只是收起视图，agent 继续跑。

面板不是入场券

v1 让面板同时承担「你得先放它才能组队」和「显示团队状态」两个职责，这是错的。 入场券归 Frame 上那个开关（见下一节），面板只显示状态， 而且是开工之后自动出现的结果。收起面板不等于解散 —— 那是开关的事。

它放在哪

方案取舍选
放当前项目 Frame 内，作为一个普通节点 跟着项目走、位置由你定；但确实占了一块画布 选这个
专属的团队 Frame（子 Frame） 更隔离，但多一层容器；Frame 本身是「项目分组」语义，团队不是项目 不选
浮层 / 抽屉（像知识库那样贴边） 完全不占画布，但跟画布的空间语义脱节，且抽屉已经有两档了 备选

选第一个的理由：它是一个工件，不是一个模式。团队面板应该能被你拖到顺手的位置、 折叠、跟项目一起存档。做成浮层就变成了「一个模式」，用完得记得关。 而且画布组件天生支持折叠成一行 —— 不看的时候它就是一条状态栏。

Failure Matrix

14 种失败，逐条给检测信号

没有检测信号的失败等于不存在。每一条都要回答：系统怎么知道它发生了。 标 跨进程独有 的三条是这个架构新引入的，同进程方案不会遇到。

启动期

#失败检测信号兜底
E-01CLI 没装 / cwd 不存在agentChat:start 直接返回 error整批不启动，把缺什么一次说清，别起一半
E-02额度已耗尽首条消息回 rate limit 错误整批中止 + 记录已烧掉的；不要重试
E-03批量起 5 个，第 3 个失败逐个 start 的返回值全成或全不成：失败就把已起的停掉。半个团队比没有团队更糟

运行期

#失败检测信号兜底
E-04进程崩溃（OOM / 被杀） 子进程 exit 事件（已有） 面板标红「崩了」+ 保留它已写的 progress.md；不自动重启（可能就是它把自己撑爆的）
E-05卡住：长时间无输出 心跳：距上一个事件超过 N 分钟 面板标黄 + 通知你。不自动杀 —— 它可能在跑一个长命令
E-06等审批没人点 审批 hook 已经能感知（灵动岛在用） 这是最容易静默卡死的一种：面板明确显示「等审批 已等 6m」并 notify
E-07并发写同一个文件 跨进程独有 无信号 —— 这是最危险的地方，它静默发生 git worktree 隔离，见下方专段
E-08死循环：反复做同一件事 3-Strike（CCteam 的机制）：同一错误 3 次 agent 自己上报主 agent；靠 prompt 约束，不可靠但聊胜于无
E-09跑偏：做了没派的活 难以自动检测 靠你点进去看。这正是画布方案值钱的地方 —— 同进程你看不到
E-10烧得比预估多得多 累计 token（面板实时显示） 超过本批预估 2 倍时暂停全批并问你

主控端与收尾

#失败检测信号兜底
E-11主 agent 上下文压缩，忘了自己在带团队 — 状态在磁盘不在上下文（team.json）。压缩后读一次就全回来了 —— 这是三层架构最直接的收益
E-12app 重启 / 崩溃 启动时扫 .plans/*/team.json CLI 子进程随 app 一起死。恢复的是「团队还有哪些活没干完」，不是进程。面板显示「上次这批没跑完」并给重启入口
E-13agent 说完成了但没写 findings 收活时检查文件是否存在/非空 打回重做一次（带上「你没写 findings」）；第二次还没有就标记未完成，交给你
E-14两个 agent 的结论互相矛盾 无法自动检测 主 agent 汇总时显式呈现分歧，不要替你抹平。这条抄 CCteam 的 reviewer 纪律
E-07 专段：为什么必须上 worktree

两个写码 agent 并行改同一个仓库时：A 读了 foo.ts，B 也读了， A 写回，B 写回 —— A 的改动消失，而且没有任何人会发现。 不是 git 冲突（那还好，至少会报错），是静默覆盖。

同进程方案不遇到这个问题，因为子 agent 的 Write 是排队执行的。跨进程是真并发。 

解法  每个写码 agent 起一个 git worktree：
      .worktrees/team-<批次>-<role>/   ← 它的 cwd 指这里

收活  agent 完成 → 主 agent 逐个 review → 合并回主分支
      冲突在合并时暴露（有信号！），而不是静默覆盖

只读角色（researcher / reviewer）不需要 worktree，直接用主工作区
代价    每个 worktree 一份磁盘；node_modules 可以软链

Recovery

五种挽回手段，覆盖上面 14 条

1 接管

点开 agent 会话，自己接着跟它说。这是最强的一招，因为它不需要任何自动化正确 —— 你看到了、你插手了。同进程方案给不了这个。

2 重派

停掉这个 agent，带着「上次为什么失败」重开一个。team.json 记着它的任务定义，重派是一条命令。

3 全批叫停

面板右下角常驻按钮。任何时候都必须一键能停 —— 这是这套系统能不能让人放心用的底线。

4 丢弃 worktree

某个 agent 改坏了，它的 worktree 整个删掉即可，主工作区一个字没动。这是 worktree 隔离的附带红利。

5 从磁盘重建

app 重启、主 agent 压缩、你关了又开 —— 全部靠读 team.json 恢复。唯一真相在磁盘。

0 什么都不做

E-05（卡住）、E-04（崩溃）都不自动重试。自动重试是最容易把小问题变成烧钱事故的机制。报出来，等你决定。

一条贯穿性的纪律

系统不替你做任何「可能花钱」的自动决定。 检测到异常 → 标出来 + 通知； 重启、重派、继续，一律等你点。这跟你在密钥柜、审批 hook 上的既有立场是一致的 —— 那两处都是「AI 不能替用户做不可逆的事」。

Gate

开关在 Frame 上，闸门在批次上

「要不要用多 agent」是项目的属性，不是每次任务的属性。 这是 v2 相对 v1 最大的改动 —— v1 试图靠「面板必须先放」和「description 措辞」来防误触发， 前者是每次都要做的仪式，后者靠语义判断（今天的实测数据表明它不可靠）。

Frame 头上一个开关

┌─ ⚙ 数字艺术软件 ─────────────────── ⊞ ✦ >_ ⊕ ⧉ ─ ┐
   ↑
   多 agent 开关。开着 = 这个项目允许组队；关着 = 主 agent 连提都不会提

技术落点：CanvasFrame 加一个 teamMode?: boolean
          （它已经有 status?: FrameStatus，头部本来就在挂状态指示）
          team_spawn 执行时读这个字段 —— 事实查询，不依赖任何模型判断
为什么这比 v1 的两个方案都好
方案问题
v1-A：面板必须先放每次要做一个仪式性动作；而且让面板同时承担「入场券」和「状态显示」两个职责
v1-B：description 反着写语义触发不可靠 —— 今天实测 24 条查询，原版 description 该触发的只中了一半多
v2：Frame 开关一次设置长期有效，一个布尔字段，看得见

还多了一层 v1 没有的收益：按项目隔离。大项目常开、随手改脚本的小项目常关， 两边互不干扰，不用每次交代。

两道闸门的分工

开关（Frame 级 · 长期 · 你手动拨）     "这个项目能不能用多 agent"
   ↓ 开着才往下走
批次确认（每批一次 · 弹一次）        "这一批 4 个 agent、$1.2，值不值"
   ↓ 你点开工
   团队面板自动出现 + agent 开跑 （面板是结果，不是前提）

关着的时候主 agent 连提议都不会有 —— 这是你要的「不被打扰」。 开着的时候它可以自由提议（那是零成本的文字），但起进程前那张清单必须你点。

批次清单长这样

     ┌──────────────────────────────────────────────┐
     │  本批 4 个 agent，预估 40–70K tok（约 $1.2）  │
     │                                              │
     │  researcher    调研导出格式        haiku      │
     │  backend-dev   实现 PDF 导出       opus       │
     │  frontend-dev  接导出按钮          sonnet     │
     │  reviewer      审这两处改动        sonnet     │
     │                                              │
     │        [ 开工 ]   [ 改一改 ]   [ 算了 ]       │
     └──────────────────────────────────────────────┘

点开工之后这一批跑到底，中途不再打断。只有这几种情况才回来找你：
     · 某个 agent 崩了 / 卡住 / 等审批
     · 累计用量超预估 2 倍
     · 这批干完了，要开下一批
     · 有 agent 要动 worktree 以外的东西

预估怎么来？ 第一版就用「角色 × 历史均值」的粗估，面板上实时显示真实累计 —— 估不准不要紧，看得见就行。这跟上下文百分比那次的教训是同一条： 与其显示一个精心计算但错的数字，不如显示一个粗糙但真实的。

开关的四条细则

问题定法理由
子 Frame 有没有自己的开关没有，继承顶层子 Frame 是文件夹分组，不该各有一套团队设置
默认值关跟密钥柜、审批 hook 一贯立场一致：花钱的能力默认不开
开了要不要立刻出面板不出否则每个开着的项目都挂一块空面板，又变成噪音
有 agent 在跑时能不能关不能，提示先叫停直接关会留下跨进程的孤儿，app 都不一定知道它们还在

Extensibility

运行时不认识任何角色

v1 有个真缺陷：那张角色表（researcher / backend-dev / reviewer / custodian）整个是编程专用的。 照那样做出来，以后想给自媒体场景组团队，就得把编排逻辑重写一遍。

归谁内容
运行时
不变		 Eas-Term 代码 Frame 开关、批次确认、spawn / 状态 / 叫停、状态落盘与恢复、14 条错误检测、团队面板、接管入口
场景包
可换		 一份 skill 有哪些角色、各用什么模型和 CLI、产出落到什么目录结构、要不要隔离、怎么算干完了、需求怎么拆

分开之后，运行时一个字都不知道什么叫 backend-dev。 拿两个场景对比就很清楚：

编程团队                          自媒体团队
─────────────────────────        ─────────────────────────
researcher   调研                 选题手    找选题
backend-dev  写代码 ← worktree    写稿      写正文
reviewer     审查                 配图      交给笔纵画板执行
custodian    维护文档             复盘      发布后回看数据

隔离：git worktree（必须）        隔离：none（各写各的文件）
收活：测试过 + review 过          收活：稿子成型 + 图齐了
产出：.plans/<role>/              产出：那个项目自己的目录结构

共享的是右边这一整套 ↓
批次确认 · 状态面板 · 卡住检测 · 一键叫停 · 崩了怎么办 · 接管

场景包用 skill 承载，不新造机制

~/.claude/skills/team-coding/SKILL.md      ← 编程场景的角色表 + 拆解方法
~/.claude/skills/team-media/SKILL.md       ← 自媒体场景（以后写）
<项目>/.claude/skills/team-xxx/           ← 某个项目专用的团队形态

你已经有整套 skill 基础设施：面板、分类、项目级/全局、分发同步。而 CCteam 本身就是一个 skill。 想要新场景就写一个新 skill，不用改 Eas-Term 一行代码。 「自定义角色」的字段格式直接抄 CCteam 的那张表（名称 / subagent_type / model / 核心职责 / 文档结构）。

现在不该设计的两件事

① agent 的载体不一定是 CLI 会话。 自媒体场景里「配图」那个角色，实际动作是把提示词 交给笔纵画板 —— 可能根本不需要起一个 CLI。但现在猜它长什么样是浪费： 先把 CLI 会话这一种做扎实，接口上留个 kind 字段就够了。

② 隔离策略先只做两种：worktree（编程）和 none（其余）。 以后真遇到需要第三种（比如生图要串行避免额度打架）再加。 CCteam 的假设审计原则在这里适用 —— 尽可能保持简单，只在需要时增加复杂性。

CLI Compatibility

哪些 CLI 能当 agent 载体

多 agent 对 CLI 的要求比单会话更严。 单会话下事件流不完整只是体验差； 多 agent 下这些事件是编排的输入 —— 主 agent 靠它们判断谁在动、谁卡了、烧了多少。

准入判据

能力主 agent 拿它做什么没有会怎样
流式事件知道它还活着 E-05 卡住检测失效 —— agent 死了你也不知道 必需
工具事件知道它在干什么 面板只能显示「跑着」，跑偏了看不出来 必需
usage 上报算账 闸门形同虚设 —— 预估和真实对不上，超支告警发不出来 必需
审批事件知道它卡在等确认 E-06 变成静默卡死，最难查的那种 强烈建议
resume崩溃后续上 只能重头再来（多花一遍钱，不是不能用） 可选
删 DeepSeek Harness 的理由在这里更强

今天移除 dsh 写的判词是：「headless 只打印最终消息，没有流式、没有工具事件，写不出 adapter」。 这样的 CLI 在单会话里是「体验不好」，在团队里是黑盒 —— 主 agent 拿不到任何进度信号，既不知道它活着没，也不知道它烧了多少。 准入判据不是把 chatSupported 抄一遍，是在它之上再加一档。

混编的价值：各自独立的额度池

这一条比「不同模型强项不同」实在得多：5 个 agent 并行烧的是同一个池子，单 CLI 很快撞墙。 Claude 五小时额度打满了，Codex 那边照跑 —— 在多 agent 场景下这不是锦上添花， 而是决定这套系统能不能连续工作。

其次才是成本分层（调研用便宜的、写码用贵的）和模型强项。

场景包怎么表达：声明能力，不绑名字

❌ researcher: { cli: 'codex' }          ← 硬绑。Codex 没装就整批起不来

✅ researcher: {
     needs:  ['stream', 'usage'],          ← 我需要什么能力
     prefer: ['codex', 'claude']           ← 有得选时的偏好，不是硬性
   }

运行时按可用 CLI 匹配，匹配不上就在批次清单里明说： 「researcher 需要 usage 上报，当前可用的 CLI 都不满足」—— 而不是默默降级或直接失败。

这跟 cliList.ts 里已经立过的规矩是一套路子： 「由数据声明，不在 UI 里按 CLI 名字判断，否则加一个 CLI 就要去界面里补一条 if， 而那种补丁必然漏」。现有的 CliCapabilities 已经有 contextUsage / approval 两项可以直接对上， 只差补「流式」「工具事件」两个声明位。

新 CLI（Kimi Code 之类）怎么接

流程不变 —— 走 .claude/skills/agent-onboarding 那份手册， 只是准入判据多了上面那几条。拿到手先跑一遍它的 --help 和一次真实会话， 看事件流里有没有那四样，结论写进 docs/cli-headless-接口实测.md （量 DSH 就是这么量的，那份文档里留着完整的判据和结论）。

一个现成的东西在这里价值翻倍

cliContract 契约自检（指纹漂移检测）。单 CLI 时它防的是 「某天升级后接口悄悄变了」；多 agent 时一个 CLI 的接口漂移会影响整个团队的编排 —— 比如 usage 字段改名，闸门立刻失灵而没有任何报错。 团队模式下这套检查应该在开工前跑一次，而不只是启动时。

Phases

三期，每期都能单独停下来用
第一期 · 骨架
Frame 开关 + 进程与视图解绑 + team.json + 团队面板（只读）
先做四件事：Frame 头上那个开关（它是所有后续能力的总闸，第一个做）、 「关节点不杀进程」、状态落盘、只读面板。 此时还不能派活 —— 但你可以手动开几个 AI 对话，让它们出现在面板里，验证状态机对不对。 这一期做完就有独立价值：多个会话的统一状态视图，你现在开三个 AI 对话就已经需要它了。
第二期 · 派活
team_spawn / team_status / 批次确认 / 全批叫停 / 第一个场景包
能拆解、能派、能停、能看。第一个场景包（team-research）只放只读角色 （researcher / reviewer），不碰写码 —— 避开 E-07，先把编排逻辑跑顺。 场景包从第一天就是 skill，不要先写死在代码里想着以后再抽。 角色用 needs/prefer 声明能力，不绑 CLI 名字（见上一节）。
第三期 · 写码
worktree 隔离 + 收活合并 + 错误矩阵完整实现
最难的一期，E-07 全在这里。不做完这一期就不要让 agent 写代码 —— 第二期只读角色的价值已经足够独立成立（并行调研、多角度审查）。
我建议你先只做到第二期

「并行调研 + 多角度审查」这个能力本身就很值 —— 它不改任何代码，因此几乎没有破坏性风险， 而且正好是 AI 现在最擅长的部分。让 agent 并行写代码是另一个量级的问题， worktree 只解决了文件冲突，还有语义冲突（两个人实现了不兼容的接口）、 合并顺序、review 谁先谁后。做完第二期真用一阵子，再决定要不要上第三期。
