为什么 server 在主进程而不是渲染层

主进程

  • 渲染层关了它还在——手机不该因为你切了个视图就连不上
  • 能拿到网卡地址（要绑局域网 IP，不能绑 0.0.0.0）
  • 读文件要过 fsGuard，那本来就在主进程
  • 跟 mcpBridge 同构，那条路已经验证过

数据却在渲染层

画布状态（frames / nodes / runningPtys）都在 zustand store 里，主进程没有。

所以照抄 mcpBridge.ts 的 invokeRenderer： 主进程收到请求 → IPC 问主窗口 → 渲染层用 collect.ts 算好回给它。 不为此把画布状态搬进主进程——那是两份真相，迟早不一致。

协议

五个端点，一个鉴权头
方法 · 路径要 token 吗干什么
GET /不要 手机页面本体（静态 HTML）。不要 token 才拿得到——不然手机第一次打开是白屏
POST /pair不要 手机报上配对码 + 设备名，换一个「等确认」。不发凭证
GET /pair/wait不要 手机轮询「电脑上点了没」。点了才返回 token，明文只在这一次出现
POST /api要 四个动作全走这一个口，body 里带 action。白名单在这里判
GET /health不要 只回 {ok:true}。给手机判「电脑开着但没配对」用

为什么四个动作挤在一个 POST /api

如果做成 /projects /files /file/:id 这样的 REST， 白名单就散在路由表里——加一条路由就等于加一条能力，而且很容易忘了给它加鉴权。

收成一个口之后，鉴权和白名单各只有一处： 任何请求都得先过 token、再过 isAllowed(action)，然后才可能进业务代码。 漏加一个动作的后果是「这个功能不通」，而不是「这个功能没鉴权」—— 失败方向选对了。

鉴权

Authorization: Bearer <token>
        │
        ▼  sha256(token)
   findDevice(state, hash)     ← 比对哈希，明文系统里没存
        │
        ├── 没有 → 401，不区分「token 错」和「设备被吊销」
        └── 有   → touch(lastSeenAt) → 进白名单闸

401 故意不区分原因：区分了等于告诉探测方「这个 token 曾经有效」。 手机端把 401 一律当「要重新配对」处理，反正用户的动作是同一个。

错误码

码什么时候手机上显示
401token 无效 / 设备被吊销「这台手机的授权已失效，请重新配对」
403动作不在白名单（含只读档里的 send）不该出现——出现了就是手机端有 bug
404项目 / 节点查不到「这个内容已经不在画布上了」
413文件超过 512KB返回截断内容 + 明说截断了
503渲染层没就绪（窗口最小化到托盘等）「电脑正忙，稍后重试」

数据流

一次「看文件内容」要经过几手
手机                主进程 server.ts           渲染层 provider.ts        主进程 fs
 │                        │                          │                     │
 ├─ POST /api ───────────▶│                          │                     │
 │  {action:'file',       │                          │                     │
 │   projectId, nodeId}   │                          │                     │
 │                        ├─ ① token → sha256 → findDevice                 │
 │                        ├─ ② isAllowed('file', readOnly=true)            │
 │                        ├─ ③ IPC 'phone:query' ──▶│                     │
 │                        │                          ├─ resolveFile()      │
 │                        │                          │   第一道：id 必须是
 │                        │                          │   该项目 Frame 里的节点
 │                        │◀── {path, kind} ─────────┤                     │
 │                        ├─ ④ fsGuard 校验 ──────────────────────────────▶│
 │                        │   第二道：路径必须在项目根/知识库根内          │
 │                        │◀───────────── 内容（≤512KB）─────────────────────┤
 │◀── 200 {text} ─────────┤                          │                     │
③ 和 ④ 顺序不能反

必须先问渲染层拿到路径，再交给 fsGuard 判。 反过来（手机直接给路径、主进程只判 fsGuard）的话， 项目根里的任何文件都能被读——包括没摆上画布的 .env。 两道校验防的是两件不同的事，缺一道都不够，这一点在 collect.ts 的 resolveFile 注释里也写了。

安全落点

规格里那八道锁，各自落在哪一行

规格说的是「应该有这些锁」，这里说的是「它们具体在哪个文件里」。 对不上号的锁等于没有。第一步只读，所以第 8 道（留痕）留到第二步——没有写操作就没什么可留的。

#锁落在哪
1默认关，不开就不监听index.ts 启动时读 phone.json， enabled=false 直接不调 server.start()。不是「监听了但拒绝」，是根本没有这个端口
2TLS 端到端第三步（隧道那期）。第一步只在局域网，走明文 HTTP —— 这一点必须在手机端界面上说清楚，不能让人以为已经加密了
3配对要电脑端确认 + 60 秒过期pairing.ts 的 claim/approve（已完成，有测）
4每设备独立凭证，可吊销pairing.ts 的 revoke + PhonePanel.tsx 的设备表
5白名单在电脑端强制server.ts 里 isAllowed()， 在进任何业务分支之前
6路径双重校验① collect.ts 的 resolveFile（已完成，有测） ② server.ts 调 fsGuard
7密钥永不出机器结构上就没有：provider.ts 只调 collect.ts， 那三个函数的返回类型里没有任何密钥字段。secrets.json 这条路上一次都不会被读到
8电脑端留痕第二步——第一步是只读，没有写操作可留
第一步的真实风险等级，说清楚

第一步只在局域网、只读、明文 HTTP。最坏情况： 同一个 Wi-Fi 下的人，如果拿到了 token，能看你画布上 Frame 里的文件内容。

这比「被人远程操控电脑」轻一个数量级，也正是把它排在第一步的原因。 但不能因此说它没风险——所以手机页面上要有一行「当前是局域网明文连接」， 让用户自己判断在什么网络下用。

桌面端 UI

设置里加一页「手机端」

设置菜单已经是标签页形式（0.4.64 改的），加一页是既有模式，不动别的页。

没开的时候

  • 一个开关 + 一句话说清它是什么
  • 说清代价：「打开后这台电脑会在局域网上开一个端口」
  • 不预先生成二维码——开关打开才生成

开了之后

  • 二维码 + 下面一行 http://192.168.x.x:PORT（手机也能手输）
  • 倒计时：「这张码还有 47 秒有效」，过期后一个「换一张」按钮
  • 有人扫了 → 弹「iPhone 请求配对，允许吗」
  • 设备表：名字 / 配对时间 / 最后访问 / 一个「踢掉」

手机页面

单文件、纯内联、零外部依赖

规格里那五张样机就是它的设计稿，直接用 app 的 token 实现。 不引任何框架——四个屏、三个接口，用原生 DOM 写完不到 400 行， 引 React 反而要处理构建产物怎么随包发出去。

四个视图

项目列表 / 会话列表 / 文件列表 / 文件内容。 底部四页签（第一步「会话」只能看状态，点不进对话——那是第二步）

状态

token 存 localStorage。 没 token → 配对引导；401 → 清掉 token 回配对；网络错 → 「连不上你的电脑」

不做

不缓存内容（规格红线）、不做离线、不做下载。 每次进某个视图都重新拉一次

见下一节。你要求的那一步，不省。

验证

回归风险清单

这个功能新增了一个网络监听面，是这个 app 有史以来风险最高的一类改动。 所以回归不能只跑单测，要专门验「没开这个功能的人有没有被影响」。

A · 默认关，等于不存在

  • 全新 userData 启动 → lsof -i -P | grep Eas 只应看到 MCP 那个 127.0.0.1 的口
  • phone.json 不存在时不报错、不自动创建
  • 关掉开关 → 端口立刻消失（不是等退出）

B · 现有功能不受影响

  • 957 个单测全过
  • MCP 桥照常工作（画板 52 个工具还能调）
  • 启动耗时没有明显变化（ipc-slow.log 里不出现 phone 相关的慢调用）
  • 终端、AI 对话、画布、甘特图、看板逐个开一遍

C · 安全断言（要真的去打，不是看代码）

  • 不带 token 打 /api → 401
  • 带错 token → 401，且响应体里不能透露原因差异
  • action 传 send → 403（只读档）
  • action 传 __proto__ / constructor → 403，且不污染任何对象
  • 伪造 nodeId 读文件 → 404
  • 真 nodeId 但路径在项目外 → 被 fsGuard 拒
  • 吊销设备后旧 token 立刻失效
  • 配对码过期后再 approve → 拒

D · 打包后还能用

  • resources/phone/index.html 真的进了包（extraResources 加了那一条）
  • 打包实例里 GET / 拿得到页面，不是 404
