## 一、十四条裁定

**Ruling 1 · T3–T7 五个组件任务不写单测。** 判定逻辑已全部抽进 T1/T2 的纯函数并被 20 条测试覆盖；
本仓库没有 React 测试基础设施，搭 mock 渲染框架的收益低于维护成本。
**但不是简单照搬 A 的同类裁定** —— A 那次的代价是「四条 Important 落在被豁免的文件里」，
所以这次改成：要求 T8 的 e2e 覆盖每个组件的**关键失败路径**，而不只是 happy path。

**Ruling 2 · T8 的断言必须覆盖失败路径。** 计划给了八条，追加三条硬要求：
折叠状态下失败项仍可见 / 审批卡片出现时 `elementFromPoint` 命中卡片本身 / `{k:'error',fatal:false}`
的 notice 在界面上真的看得见。**追加的第二条后来被评审指出在当时场景下恒真**（见 §二）。

**Ruling 3 · `costUsd` 省略时沿用上次值。** 依据不是 UI 体验，是字段来源：
Claude 的 `total_cost_usd` **名字就是 total、语义是累计**。累计值缺失时清空 = 显示假信息。
若将来某个 CLI 的该字段是「本轮花费」，应在 adapter 层归一成累计语义，不改这里。

**Ruling 4 · T4+T5、T6+T7 各合并成一次 dispatch。** 前者共用同一份视图模型，后者同处工具栏区
且读同一份 capabilities，审查范围仍然清晰。

**Ruling 5 · 首条消息不单独 send（我的简报写错了，实现者读代码纠正得对）。**
`AgentChatStartParams.message` 是必填，`restartAndDeliver` 在 start handler 内部就同步投递了它。
照简报写会对 Claude **重复投递首条消息**。计划文本已更新。

**Ruling 6 · agent 节点无 UI 创建入口，e2e 通过 store 直接注入。**
不为此提前做 C 的创建入口：e2e 要验的是对话界面本身，不是创建流程；提前做会模糊 B/C 边界。
**代价就是这份文档开头那句话。**

**Ruling 7 · 节点关闭时停 CLI，走 `killPanePty` 而不是组件卸载钩子。**
依据是仓库自己的注释：`store/shared.ts` 的 `killPanePty` 写着「这条『用户主动关』的路径会在同一个
同步调用里把 leaf 从布局树摘掉，TerminalView 随之卸载、清理时把 `pty:exit` 的监听也摘了 ——
真正的退出事件到达时已经没人接」。**这个仓库已经为 terminal 踩过一次这个坑。**

**Ruling 8 · 解除「不许动 `src/main/`」，补 `StartOpts.skipApprovalHook`。**
实现者核实「用户拒绝装 hook → 不装，会话照常起」做不到（`restartAndDeliver` 无条件调
`installApprovalHook`），它在「无视拒绝照装」与「干脆不起会话」之间选了后者 ——
方向对，但结果是**「不同意就用不了」= 阻断**，与 A 的 Ruling 14「**告知而非阻断**」矛盾。
Ruling 14 当初选「告知」的理由是：用户在未注册目录/别人的仓库里临时用是合理需求。
**产品承诺不能因为任务的文件边界就放弃。**

**Ruling 9 · Task 8 评审的十条问题全修，P0-3 只取一半。**
P0/P1 五条是**实测出来的**假绿与确定性污染，不是理论顾虑。P2 五条加起来不到 30 行，一并修。
P0-3 只试 `electron-vite build --mode development`（后经实测不成立，保留补丁方案 + 安全网），
**不做 worktree 方案** —— 结构性重做超出一个验证脚本该占的份额。

**Ruling 10 · 最终评审的 C1 + 六条 Important + M1 现在就修，不留给 C。**
评审建议判成「可以合并 + 一份 C 上线前的硬门槛清单」。**采纳它的分级，不采纳它的时序。**
理由：① 修法评审都写明了，现在修是「照着做」，留到 C 时修是「先重新理解一遍再做」；
② 门槛清单要跨会话存活才有用，而当时唯一记着它的是那份会被删掉的账本；
③ C1 与 I1 是同一族的安全语义问题（用户的明确选择被静默丢弃/推翻），A 那轮的 Critical 也是这族
—— **这个模块在这件事上已经栽过一次**。
**I2+I3 做正解而非打补丁**：让 `CliInfo` 带上 `approvalHook`，UI 才判得了
「这个 CLI 的审批走不走这条 hook」。打 `caps.approval.length>0` 的补丁能解 I2 但解不了 I3。

**Ruling 11 · 「卸载 hook 后没有重新开启入口」不补。**
卸载是用户的明确动作，「卸载完立刻想再开」是低频路径，新建节点重走询问卡片是可用退路；
补按钮要新增 `hookInstall` IPC，是扩面不是收尾。
**关键是实现者已经把 notice 里那句用户照做不了的「随时可以在工具栏重新开启」改成了如实说法**
—— 界面不再说谎是底线，死角本身可以等。

**Ruling 12 · I1 的 IPC 胶水只有代码走查，接受。**
真机复现要真 spawn CLI + 等 15 分钟空闲回收或改模型，成本与收益不成比例。
**但这是 C 让节点可达后最该补真机回归的一条。**

**Ruling 13 · `MAX_NOTICES=8` 丢最旧时会挤掉硬验收那条，记档不修。**
去重后要 8 条互不相同才触发，两个高频重复源都会被折叠，实际到不了；版面已由 CSS 保住。

**Ruling 14 · 收尾轮修三项后不再开完整复审。**
三项都是窄改动、判据明确，控制方自行核验。继续叠复审轮的边际收益已低于成本。

## 二、三次「已验证的事实」被后续实测推翻

这一节比上面十四条更值得读。**每一条都是当时有人真心相信、且写进了文档的结论。**

**① 切画布视图丢终端状态的根因。**
立档写的是「resize 撞 shell 标题钩子」。加埋点实测：切视图期间 `onTitleChange`/`setPtyRunning`
**一次都没调用**。真因是切回分屏时 `isActive` false→true 触发程序性 `focus()` → `focusin`
→ `clearAttention` 把标记吃掉。而且丢在「切回来」那一下，不是「切过去」。

**② 「同步 `wc.send()` 30/30 零丢失」。**
A 那轮的复审搭过隔离 Electron 测试 app，结论是 microtask 语义保护了这个模式，30/30 全捕获。
B 的最终评审重搭探针、带对照组，实测 **`syncCaptured=1/30, asyncCaptured=30/30`**。
修复后的复审又**自己重写一套探针**独立复现，数字一致。
→ 这就是 C1，`{k:'error',fatal:false}` 那条硬验收项在生产链路上 29/30 会丢。
**幸运的是那条错误结论只写在会被删掉的账本里，没进这份存档的前身。**

**③ Ruling 2 追加的「审批卡片 `elementFromPoint` 命中自身」这条断言。**
是控制方要求加的，评审直接指出它**在当时场景下恒真、没测到任何一行代码** ——
`.ac-approval` 没有 `z-index` 也没有 `position`，是文档流里的普通块，没有可被破坏的层级规则；
而脚本又把节点最大化了，恰好排除了唯一能盖住它的东西。
修法是跑完退出沉浸态，**在画布上未最大化的普通节点形态下再测一遍** —— 那才是用户会遇到的形态。

**共同点：三条都是「看起来验过了」。** 第 ① 条有立档，第 ② 条有测试 app 和数字，
第 ③ 条是控制方亲手加的硬要求。真正戳破它们的都是**带对照组的反向变异**：
先证明探针/断言抓得住已知的坏情况，再看它对被测对象说什么。

## 三、交给子项目 C 的清单

### 必须先解决的（否则用户建出节点就会踩到）

- **M5**：agent 节点**不跨重启存活，而且会变成终端**。`serializeCanvas` 的白名单只有
  `code | image | web`，agent 节点落盘时 `pane` 被剥掉；重启后 `materializeCanvas` 把
  「没有 leafId/pane/component 的节点」一律当终端占位重开一个 shell。
  **这是 C 一定会踩的第一个坑。**
- **创建入口本身**：`KIND_OPTIONS` 加 `'agent'`，以及规格里说的「空画布双击提示 → 建出第一个
  项目 → 默认落 agent 节点」。

### 最该补真机回归的（按优先级）

1. **I1**：卸载 hook → restart 不再把它装回用户项目（Ruling 12，目前只有代码走查）
2. **C1 在真实会话里的表现**：探针证明了机制，但没在 Eas-Term 真实进程里跑过一轮完整会话
3. **I2/I3 的第三个 CLI 分支**：现在只有 Claude/Codex 两种 `approvalHook` 取值

### 记档不修的 Minor（判断过，不是遗漏）

| 编号 | 内容 | 为什么不修 |
|---|---|---|
| M2 | `__t8Visible` 测不出「被祖先 `overflow:hidden` 裁掉」「滚出滚动容器」 | 判据继承自被认可的断言 8。**结论是：别再把断言 8 当「判据最扎实的模板」照抄**。真要覆盖那两种情况，用 `IntersectionObserver` 或复用脚本里已有的 `elementFromPoint` 命中测试 |
| M3 | 审批卡片可能在「点过之后」重新出现 | 触发窗口是点击到 `approval.resolved` 回来的几十毫秒内恰好来一个新 assistant 轮次。最坏是多发一次 `resolveApproval`，对已敲定的 id 是安全空操作 |
| M4 | 隐藏期间收到消息，切回来停在对话顶部 | `hidden` 是 `display:none`，此时 `scrollHeight` 为 0。下一个事件会修正 |
| M6 | 几处 IPC 调用没有 catch | I4 的失败路径已接住（不接等于 I4 只修一半），其余四处未动 |
| M7 | `MessageTurn` 用数组下标当 key | 复审独立核过这条不变量目前成立（合并后的列表严格只追加）。**但它依赖多个没有编译期保障的前提叠加** —— C 打破其中一条不会有信号，只会表现成「执行区的展开状态跳到别的轮次上」 |
| M8 | 画布模式下点下拉会顺带切换节点选中态 | `onMouseDownCapture` 的白名单是 `closest('button, input')`，`<select>`/`<textarea>` 不在内。与终端行为一致，不是新问题 |
| Ruling 13 | `MAX_NOTICES=8` 丢最旧时挤掉的正好是硬验收那条 | 去重后要 8 条互不相同才触发，实际到不了 |
| 收尾②| `stoppedAgentChatSessionIds` 随进程生命周期增长 | 拿「永久但极小的 string-per-session」换掉「无界的 per-session `ChatEvent[]`」（后者可能装着未截断的工具输出）。若 agent 节点将来会被高频开关则值得重新量 |

### 两处已知的接口天花板（新增 CLI 时会撞上）

- **`sandbox` 只能在 start 时定一次**：`setParams` 的 patch 类型只收 `{model?, effort?}`。
  一个「沙箱可中途切换」的 CLI 进来要动 IPC 签名。
- **Codex app-server 不做**：详见 `docs/codex-app-server-协议探针.md`。93 个类型、
  10 种服务端主动请求、5 种审批的决定集互不相同、还有问答型 `ToolRequestUserInput`
  —— 中间事件模型装不下。方案 B（capabilities 协商能压到多小）是继续这个方向前唯一该做的探测。

agent 节点根本不落盘（连回滚都不会出问题）。

最要紧的是别让 C1 那一族（用户的明确选择被静默丢弃）再长出来 —— 这个模块已经栽过两次。
