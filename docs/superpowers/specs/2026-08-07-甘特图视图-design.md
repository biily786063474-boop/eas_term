# 甘特图视图 · 设计

日期：2026-08-07 · 状态：待实施

## 要解决什么

现在回答不了「上周三下午我在哪个项目上花了两小时」。终端跑过的活没有留下时间轴 ——
`runningPtys` 只反映此刻谁在跑，`ptyTiming` 只留最后一轮的时长，重启就清零。

甘特图给出这条时间轴：**横轴是时间，一行一个项目，每根条是一次「你发了什么 → agent 干完」**。

## 采集

### 两个点，都在渲染层

| 位置 | 拿到什么 |
|---|---|
| `TerminalInput.send()` | 输入框提交的整段文本（局部变量 `text` 已是原文） |
| `TerminalView` 的 `term.onData` | 直接敲进终端的键，累积成行，遇 `\r` 产出一条候选 |

两处都是**用户发出去的**文本。agent 的输出一律不记。

放渲染层而不是主进程的 `pty:write`，是因为「agent 是否在跑」（`setPtyRunning`）判定在
`TerminalView` 里、靠 spinner 得出。主进程拿不到这个信号，跨进程同步只会多一层竞态，
而两条输入路径在渲染层同样齐全（`term.onData` 就是键盘输入写进 PTY 的唯一出口）。

### 行缓冲器

`term.onData` 收到的是按键字节流，要还原成「一条输入」：

- 可见字符累积进缓冲
- `\x7f` / `\b` 退格弹出末字符
- `\x1b[...` 控制序列（方向键、Home/End 等）整段跳过，不进缓冲
- `\x1b[200~ ... \x1b[201~` bracketed paste 取中间内容整段入缓冲
- `\r` → 产出一条候选，清空缓冲

**准确性边界（必须承认）**：TUI 有自己的行编辑与历史。按 ↑ 调出上一条命令时，画面上的内容
不来自我们的缓冲，此时产出的候选会与实际发出的不符。自动补全（Tab）同理。
不去追平这些 —— 追平意味着重新实现一遍各家 TUI 的编辑器，且随它们改版失效。

### 什么时候才算一条任务

候选文本产出后**不立刻落盘**，挂起等待：

- 3 秒内（硬编码常量 `PENDING_TTL_MS`，不做成设置项）该 pty 的 `setPtyRunning(true)`
  到达 → 落一条记录，`startAt` 取 running 那一刻
- 超时未等到 → 丢弃（`cd` / `ls` / 打错的命令不会让 agent 跑起来）
- 同一 pty 新候选到来 → 覆盖旧的挂起项

`setPtyRunning(false)` → 补上 `endAt`。

**agent 正在跑时又发一条**（补充指令、排队）：此时不会有新的 `false → true` 转换，
按上面的规则会超时丢弃。这类补充是常态，不能丢 —— 处理办法是**附加到该 pty 当前
未完成的那条记录上**，存进 `follow: string[]`，详情弹层里按顺序列出。
不为它单开一根条：它没有自己的起止，硬拆只会让图上多出一堆零长度的条。

## 数据

```ts
type GanttTask = {
  id: string
  projectId: string
  ptyId: string
  leafId: string        // 点条能跳回那个终端
  prompt: string        // 原文，超过 2000 字截断（详情弹层够看，磁盘不失控）
  follow?: string[]     // 这一轮里补发的指令，同样各自截断 2000 字
  startAt: number
  endAt: number | null  // null = 还在跑
  aborted?: true        // 应用被强杀导致没能写 endAt，读取时补的标记
}
```

落 `userData/gantt.json`，主进程管，照 `src/main/board.ts` 的范式：逐条校验，
字段缺失整条丢弃 —— 半条记录跑进 UI 是最难查的那种问题。

**保留一周**：每次写入时顺手剔除 `startAt` 早于 7 天的条目。不设定时器 ——
定时器要考虑休眠、时钟跳变、多窗口重复触发，而写入时清理天然只在有新数据时发生。

**没写完的记录**：`endAt` 仍为 null、而这个 `ptyId` 已经不在本次运行的活终端里，
说明上次是被强杀的（正常退出走 `setPtyRunning(false)`）。读取时给它打 `aborted: true`，
`endAt` 留 null，图上画成**右端渐隐的开放条**，宽度封顶到该行可视区右缘。
不去编一个结束时间 —— 编出来的数字会被当成真的。

## 视图

新增 `viewMode: 'gantt'`，排在 `board` 之后。

- **一行一个项目**，同项目并行的任务在行内上下堆叠，行高随并行数增长；空闲项目占一行
- **时间轴刻度到分**
- **条上最多 10 字符**，超出省略；hover 出浮层显示全文 + 起止时刻 + 时长
- **点击条**跳回对应终端：切到看板模式并全屏那个 leaf（`setViewMode('board')` +
  `setBoardFullscreen(leafId)`）。选看板而不是画布，是因为画布要先找到节点再平移过去，
  而看板全屏是现成的一步到位；那个 leaf 已经不在了就只提示，不跳

### 时间尺度：导航带 + 取景框（2026-08-07 定）

主区不锁死一个跨度，底部加一条导航带：

- **导航带**画**完整保留期（7 天）**的全景，每个项目一条压缩的活动密度带，
  上面盖一个可拖动的**取景框**
- **主区**显示取景框内那一段，跨度可在 **24 小时 / 3 天**之间切换
- 拖取景框 → 主区跟着走；切跨度 → 取景框宽度跟着变

**为什么不是「上面 8 小时、下面 3 天」两个平级的甘特图**（最初的想法）：
8 小时那段数据会在下面**再出现一次**，只是被压扁 —— 同一条任务两个宽度，
读者要在两套比例尺之间换算。而且 20 个项目的垂直空间直接翻倍。
导航带的形态是「一份数据 + 一个取景框」，不产生重复，垂直只多占 40px 左右，
而且「我现在看的是整周里的哪一段」变成显式的。这是时间线工具的通行做法
（Chrome DevTools Performance、Grafana 都是它）。

## 模式切换

现有三段控件 `.view-seg`（终端 / 画布 / 看板）换成**单个按钮**，文案「模式切换」，
点击展开下拉，四项：终端 / 画布 / 看板 / 甘特图。

## 已知限制

1. **升级前的历史没有。** 数据从装上新版才开始记，头几天图是空的。
2. **改动上线前已经在跑的任务记不到起点** —— 采集必须先看到「你发了什么」，
   那几条只能等下一轮。
3. **TUI 行编辑场景可能记错文本**（见「准确性边界」）。时间轴仍然准确，
   因为起止取自 `setPtyRunning`，与文本采集无关。

## 不做

- 不做跨设备同步、不做导出
- 不做手工编辑/补录任务
- 不解析 agent 输出去猜「它在干什么」——那是另一个量级的问题
