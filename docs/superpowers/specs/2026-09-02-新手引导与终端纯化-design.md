## 用户原话（2026-09-02）

> 用户开始使用的时候，引导用户一步一步进行操作。让用户在画板上去双击，双击之后建立了一个项目的
> frame，初次建立 frame 是空的 frame。空的 frame 上面有三个按钮，分别是 claude code、codex
> 和系统默认的 harness。用户点击后自动在 frame 中创建 AI 对话模块，并切换到相应的流程。
> 如果没有安装，则出现引导安装弹窗。所有的安装都要在 UI 里面完成，不要让用户看到不该看到的
> 开发者相关的东西。用户点击安装之后就直接安装完成，然后引导用户去登录，选择订阅登录还是
> 怎么样的，去做匹配的 UI。
>
> 然后终端里面的 top bar 上面的内容选项等取消，终端就是纯粹的终端。所有的 AI 对话由 AI 对话
> 模块来单方面承接。当然，CLI 里面的那些逻辑不要改变 —— 当用户在终端里面去进行 claude code 和
> codex 的时候，依旧要使用他们的状态机，以及其他的已经在终端落地的那些东西，包括之前做的
> 统计之类的、甘特图，都要保留。终端只取消它的 UI 入口。

## 一、一句话概括

**把「选哪个 AI」这个决定从终端的控制条搬到空 Frame 上，并让它一路把人送到能对话为止。**

终端因此退回纯终端；AI 对话模块成为唯一的对话入口。终端里手敲 `claude` 仍然照常工作，
它背后那一整套（状态机 / 甘特 / 统计 / 审批解析）**一个字都不动**。

## 四、子项目 A：空 Frame 的三个按钮

### 4.1 形态与判据

空 Frame（`f.nodes.length === 0`）里，把那行「空 Frame」换成一组引导：

```
              选一个 AI 开始
   ┌──────────┬──────────┬──────────┐
   │ Claude   │  Codex   │ 默认      │      ⌨ 先开个终端
   │ Code     │          │ harness  │      （弱一档，逃生口）
   └──────────┴──────────┴──────────┘
```

**顺序按常用度固定**（用户 2026-09-02 拍板），**不跟着 `pickCli` 的
「随包排最后」走** —— 那条管的是挑默认值，两件事共用一套顺序会互相弄坏。
理由与「先开个终端」那颗的设计见 §8.1 / §8.2。

**三个按钮恒常显示，不按 `available` 过滤。** 依据是 `CliInfo.available` 的文件头注释：

> `false` 不等于「不显示」—— 用户第一次打开软件时本来就一个都没装，
> 那时候更需要看见「有哪些可选」。

按钮下方的小字按状态分三种（**这三句是给用户看的，不许出现命令、路径、变量名**）：

| 状态 | 判据 | 小字 | 点击后 |
|---|---|---|---|
| 可用 | `available && chatSupported` | （无） | 直接建节点 |
| 没装 | `!available` | 「点一下装好」 | 建节点 → 面板开在 `from:'install'` |
| 装了没登录 | `available && !loggedIn` | 「点一下登录」 | 建节点 → 面板开在 `from:'login'` |

> ⚠️ **「默认 harness」那颗的判据不一样。** 它随包分发，`available` 恒真（探测必过），
> 所以「没装」这一档对它不存在；它的三档是 `ompSetup.ts` 的
> `nextStepOf`：`provider` → `login` → `model` → `ready`。
> 用 `available` 去判它会得出「一直可用」，而用户点进去撞到的是选服务商那一屏。

### 4.2 缺口一：`openAgentPane` 收不了 CLI

`addAgentNode(frameId, opts)` 把 opts 原样转给 `openAgentPane`，而后者的参数表里
（`tabsSlice.ts:39-58`）有 `projectId / cwd / owner / role / initialMessage / sessionId /
background / resumeId`，**唯独没有 `cli`**。

而 `AgentChatView` 挑 CLI 的逻辑是现成的：

```ts
// AgentChatView.tsx:200-204
const pinnedCli = useStore((s) => { … return leaf?.pane.kind === 'agent' ? leaf.pane.cli : undefined })
// :544
setSelected((cur) => cur ?? pickDefaultCli(usable, pinned, readLastCli()))
```

`pickDefaultCli` 的第一条就是「pinned 压过一切」。**所以机制齐全，只差把值送进去。**

**改法**：`openAgentPane` 的 opts 加 `cli?: string`，建 pane 时写进 `pane.cli`。
一处新增字段、一处透传，不新增判定。

> **不要走「先写 localStorage 的 `lastCli` 再建节点」这条捷径。** 那个 key 是
> 「用户上次手动切换到哪个 CLI」的记忆（`pickCli.ts:42`），拿它当传参会有两个后果：
> ① 点一次引导按钮，等于把**全局默认**也改了；
> ② 两个 Frame 想开不同 CLI 时，后建的那个会把先建的记忆冲掉。
> 传参和记忆是两件事，别复用同一个格子。

### 4.3 缺口二：`pane.cli` 不落盘

`layout.ts:85-93` 的注释写得很清楚：

> **它今天不落盘**：`persist.ts` 的 `serializeCanvas` 对 agent pane 只写
> `{kind, cwd, resumeId}`。所以别把它当成「记住用户选的 CLI」—— 它只是内存里的
> 一次性传参（插件页开会话 / 派活），重启后就没了。

**这次要改变这个性质。** 用户从引导按钮选了 Codex，重启之后那个节点应该还是 Codex，
而不是悄悄退回 `pickDefaultCli` 的推测值。

**改法**：`serializeCanvas` 对 agent pane 多写一个 `cli`；反序列化时读回来。
**同时把 `layout.ts` 那段注释改掉** —— 留着一句「它今天不落盘」比没有注释更糟。

> 🔴 `store/` 是红区，改 persist 要照 [03-3B](../../architecture/03-agent角色边界.md#3b--开发期-agent你的边界) 的规矩：
> 加字段是安全的（老 canvas.json 读回来 `cli` 是 `undefined`，正好退回原行为），
> **但不许改已有字段的含义或顺序**。

### 4.4 点了之后走哪条流程

三个按钮共用一条路，分支只在最后一跳：

```
点按钮
  └→ addAgentNode(frameId, { cli })      建节点、面板挂载
       └→ AgentChatView 挂载，pinnedCli = 这个 cli
            ├─ 可用且已登录 → 直接进对话（什么弹窗都没有）
            ├─ 没装         → setSetupFor({ cli, from: 'install' }) → CliSetupPanel
            ├─ 装了没登录   → setSetupFor({ cli, from: 'login' })   → CliLoginPanel
            └─ 默认 harness 没配好 → OmpSetupPanel（它自己按 nextStepOf 决定停在哪一屏）
```

**这四个分支今天全都存在**（`AgentChatView.tsx:238-243` 那个入口的注释明写
「它不用自己判断该开哪张面板 —— 分支放在渲染那一侧」）。所以子项目 A 不需要新写任何一张面板，
只要保证按钮把 `cli` 送到，剩下的自己会发生。

### 4.5 「点击安装之后就直接安装完成」

用户这句话要按字面做：**点了安装就开始装，不再让用户在几种安装方式之间挑。**

今天 `agentInstall.ts` 的 `optionsFor()` 会给出 2–3 个候选（官方脚本 / Homebrew / npm），
面板让用户选。新链路取**第一条**（`optionsFor` 返回的顺序就是推荐顺序，官方脚本排第一）。

> **其余候选不要删。** 装失败时那几条是唯一的退路（公司网络挡了 curl，brew 可能通）。
> 做法是：默认直接用第一条，**失败之后**才把其余选项摊开。
> 成功路径上用户一次选择都不用做，失败路径上他仍有牌可打。

## 五、子项目 B：终端 top bar 下线

### 5.1 要拆的是什么

`CanvasAgentBar.tsx`（文件头自述）：

> 形态：左侧星星按钮（显示当前 CLI 的品牌标识，点开换）→ 角色/模型/思考三枚胶囊 → 右侧 ▶ 启动。

这一整条就是用户说的「top bar 上面的内容选项」。它渲染在 `PaneView.tsx:490` 的
`.agentbar-wrap` 里，**只在画布终端节点上出现**（分屏不渲染这层）。

### 5.2 ⚠️ 这会推翻一条 2026-08-27 的用户决定

`PaneView.tsx:480-488` 那段注释：

> **一个 CLI 都没装时也照常显示**（2026-08-27 用户要求）。原来是整条藏掉……
> 但藏掉的代价更大：新用户第一次打开软件时**什么都看不到**，也就不知道这里本来能选 CLI、
> 更不知道该装什么。现在改成照常显示，启动按钮在没装时变成「安装」，点它直接装 ——
> 把「困惑」换成了「一条能往下走的路」。

**当时那个问题真实存在，现在由空 Frame 的三个按钮接管。** 所以这次下线是有条件的：

> 🔴 **子项目 B 必须排在子项目 A 之后。** 反过来做，中间会有一段时间
> 「新用户什么都看不到」—— 那正是 8-27 修掉的问题，别把它再造一遍。

### 5.3 拆到什么程度：**摘引用，不删文件**

```diff
  // PaneView.tsx
- {canvasTerm && pane.kind === 'terminal' && (
-   <div className="agentbar-wrap"><CanvasAgentBar … /></div>
- )}
```

`CanvasAgentBar.tsx` 与 `canvas.css` 里的 `.agentbar*` 样式**保留在仓库里**，理由：

1. 它带着大量实测结论（Claude 的 effort 档位来自 `claude --help` 真实探测、
   Codex 的模型表是主进程给的已知默认……），删了这些知识就没了；
2. 万一这条引导路走不通要回退，`git revert` 比重写便宜。

**但要在文件头加一段「已下线」的说明**，写清楚哪天、为什么、被谁取代 ——
否则下一个 agent 会看到一个没人引用的组件，然后花时间去搞清楚它是不是死代码。

### 5.4 ⚠️ 会被顺带孤立的两个东西

**① 角色（roles）**

`CanvasRoleEditor` / `CanvasRoleManager` **只能从 AgentBar 打开**（全仓搜索：
除了 `CanvasAgentBar.tsx` 自己，没有第二个引用点）。摘掉 AgentBar，
用户就再也进不去角色管理了。

而 `main/roles.ts` 是 🔴 文件，[图纸 01 红线 5](../../architecture/01-系统上下文.md) 明写：

> 代码那半只有一个角色有硬拦：`roles.ts` 的 `illustrator` 用 `tools.deny` 通配符挡图像类 MCP。

**这条 deny 仍然在主进程生效**（它不依赖那个 UI），所以下线不会造成安全回退。
但**用户失去了编辑角色的入口**，`~/.eas/roles.json` 变成只能手改的文件。

> **这是个需要用户拍板的取舍，不要替他决定。** 三条路：
> (a) 接受，角色暂时没有 UI 入口；
> (b) 把角色管理搬到设置面板里（工作量小，一个 tab）；
> (c) 搬到 AI 对话模块的工具栏上（更贴近它的实际用途）。
> **实现前先问。**

**② `AgentCmdBar`**

它有**两个**渲染点：`CanvasAgentBar.tsx:442`（画布，作为第二行）和
`PaneView.tsx:479`（分屏，独立渲染）。摘掉 AgentBar 只会带走画布那一份。

用户说的是「top bar 上面的**内容选项**」（胶囊），命令按钮条是另一回事。
**默认保留 `AgentCmdBar` 在两处都可用** —— 它是纯终端也用得上的东西（往终端里塞常用命令），
不属于「AI 对话入口」。

> 若用户的本意是连它一起清掉，那就把 `PaneView.tsx:479` 那行也摘掉。**实现前确认一句。**

## 六之二、子项目 C：空画布那行字 + 「造梦空间」这个词

> 用户 2026-09-02 追加：「空画布的时候要在屏幕中间显示一行字，**双击创建你第一个造梦空间**，
> 并且给你补充语意，**frame 就是造梦空间，也是项目区**，这些语意也要同步到 eas-term 的 skill
> 以及随软件植入的提示词。」

### 6-2.1 那行字（一处改动）

`CanvasStage.tsx:1259` 已经有这条引导，只是文案不同：

```diff
- <div className="canvas-empty-hint">双击开始你第一个项目吧</div>
+ <div className="canvas-empty-hint">双击创建你第一个造梦空间</div>
```

位置和行为**都不用动**，现成的就对：挂在 viewport 而不是 `canvas-world`
（不跟着缩放平移飘走）、`pointer-events:none`（不挡住它正下方的双击热区）、
判据是 `!frames.length && !freeNodes.length`。那几条各自的理由写在原注释里，别顺手改。

### 6-2.2 「造梦空间」是**加语义，不是重命名**

用户说的是「**补充**语意」。所以：

| 层 | 怎么处理 |
|---|---|
| **用户看得见的文案** | 说「造梦空间」 |
| **代码标识符**（`frame_id` / `frames` / `.cframe` / `addProjectFrame`…） | **一个都不改** |
| **给 AI 读的文字**（skill / MCP 工具描述） | Frame 后面挂一句「用户叫它造梦空间 / 项目区」 |

> 🔴 **绝对不要把 `frame_id` 改成 `dreamspace_id`。** 那是 MCP 的对外契约，
> 用户自己配过 MCP 的客户端、已经发出去的 skill 副本、`canvas.json` 里的存量数据全对着它。
> 改标识符换不来任何用户可见的好处 —— 用户根本看不到参数名。

**要解决的真问题只有一个**：用户说「把它摆到我那个造梦空间里」时，AI 得知道那指的是 Frame。
这是**词表问题**，一句话就够，不需要动结构。

### 6-2.3 同步到哪几处（一份源，两个落点）

`skills/eas-term/` 是**源**，`agentRules.ts` 的 `syncRules()` 把它分发到两处：

```
skills/eas-term/*.md          ← 源，改这里
   │  syncRules()（只由「扩展能力」面板的 IPC 触发，不在启动流程里）
   ├─→ ~/.claude/skills/eas-term/     Claude 侧
   └─→ ~/.eas/agent/                  Codex 侧（常驻区只放指针，正文在这儿）
```

> ⚠️ **改完源要去点一次同步才生效。** 直接改 `~/.claude/skills/eas-term/` 是改分发产物，
> 下次同步原样覆盖 —— 看起来像「有个自动化把我的修改还原了」。

**要改的四个文件**（`Frame` 出现次数）：

| 文件 | 次数 | 改法 |
|---|---|---|
| `skills/eas-term/SKILL.md` | 6 | **只在最靠前那处**加一句词表，其余原样 |
| `skills/eas-term/canvas.md` | 3 | 同上，靠前处加一句 |
| `skills/eas-term/plugins.md` | 3 | 不用改（它已经在讲「在 Frame 里双击」这类操作，词表在 SKILL.md 里管得到） |
| `mcp/eas-mcp.mjs` | 13 | **只改 `canvas_list_frames` 那一条**，见下 |

**词表那句话，建议写成**：

> Frame（画布上的框）**就是用户口中的「造梦空间」，也叫「项目区」**——
> 一个 Frame 绑一个项目，里面装着这个项目的终端、AI 对话、文件预览。
> 用户说「造梦空间」「项目区」「我那个框」，指的都是它。

**MCP 那侧为什么只改一条**：13 处里 12 处是参数说明（`frame_id: '不传则…'`），
那些是给 AI 看「怎么填参数」的，塞词表进去等于在每个工具里重复一遍同一句话，
白占上下文。`canvas_list_frames` 的 `description` 是**唯一一处在解释「Frame 是什么」**的地方，
词表挂在那儿一次就够 —— 而且它恰好是 AI 想「用户说的那个空间是哪个」时会去调的工具。

### 6-2.4 ⚠️ 一处容易漏的：`agentRules.ts` 的常驻区**不提 Frame**

`codexRegion()`（`agentRules.ts:125`）注入的只有触发条件和路径指针，
正文全在 `~/.eas/agent/` 下按需读。所以：

- **不需要**在常驻区加词表（那是全局常驻的，每个会话都占字数）；
- 词表放在 `SKILL.md` 里就够 —— 常驻区已经有一条「这条不是触发条件，是随时都作数的规矩」
  指向它，可达性有保证。

> 这一条是有教训的：改动前 `syncRules` 把整份 SKILL.md 灌进 canvas.md，
> 拆成渐进式披露之后「边界/分寸」两节在 Codex 侧变得不可达，才补的那条指针。
> **加新内容进 SKILL.md 时，先确认它在两侧都读得到。**

3. 点一次「扩展能力」面板的同步 → `~/.claude/skills/eas-term/SKILL.md` 和

4. 在终端里问 AI「把这个报告摆到我的造梦空间里」，它调的是画板 MCP 工具而不是反问。

### 8.1 三颗按钮固定顺序 —— 注意它和 `pickCli` 不是一回事

**固定的理由是肌肉记忆** —— 第三颗永远是同一个，不因为今天装没装 Claude 而换位置。

> ⚠️ **别去改 `pickCli` 来实现这个顺序。** 那个函数管的是「没人明说时用哪个」，
> 两件事共用一套顺序，改一处必然弄坏另一处。按钮顺序**写死在渲染那一侧**。

### 8.2 「先开个终端」那颗

## 八之二、子项目 D：角色注入 AI 对话会话

> 用户 2026-09-02：「那就转移到 AI 对话中的合适位置进行角色的注入这个 session」
> 以及界面上的具体要求：「角色入口变成一个小 icon，放到和新对话、压缩同级，
> **点开后向上展开角色卡**」。

### 8-2.1 ⚠️ 这不是「挪个入口」，是新建一条链路

**摸出来的事实**：这 8 个角色（全流程 / 勘探员 / 工匠 / 验官 / 原型师 / 笔杆子 /
画师 / 杂役）**今天只对终端里 ▶ 启动的 agent 生效** ——
`CanvasAgentBar` 把 `role.contract` 和 `role.tools` 拼进 `buildClaudeCmd()` / `buildCodexCmd()`
写进终端。**AI 对话会话完全不吃角色**：`agentChat/session.ts` 里那个 `role`
是团队角色名（`live.rec.role` → `teamRole`），跟这 8 个预设毫无关系。

所以拆掉 AgentBar 不只是「角色没有编辑入口」，是**角色这个功能整个失效**。
把 icon 搬进对话工具栏而不接注入，得到的是一颗点了什么都不会发生的按钮 ——
**比没有更糟**。

### 8-2.2 一个角色要注入三样东西

| 带什么 | 注入到哪 | 风险 |
|---|---|---|
| `contract`（职责契约文本） | Claude：接在 `--append-system-prompt` 后面（`adapters/claude.ts:99` 已经在那儿拼 `OUTPUT_STYLE_PROMPT` ＋ 可选的 `ASK_FIRST_PROMPT`，再接一段即可）<br>Codex / omp：各自的系统提示口 | 🟢 小 |
| `tools.deny` / `denyServers`（工具边界） | Claude：`--disallowedTools`（`denyServers` 展开成 `mcp__<名>__*`）<br>Codex：`-c mcp_servers.<名>.enabled=false`（它没有工具级开关，只能整个 server 关）<br>**omp：另一套** —— 它是 `--tools` 白名单，不是黑名单，语义反过来 | 🔴 **安全相关**，见下 |
| `model` / `effort` 预设 | 工具栏上这两个控件已经有了，角色只提供默认值 | 🟢 小 |

> 🔴 **工具边界那行是[图纸 01 红线 5](../../architecture/01-系统上下文.md) 点名的东西**：
> 「代码那半只有一个角色有硬拦：`roles.ts` 的 `illustrator` 用 `tools.deny` 通配符
> 挡图像类 MCP」。把它接进对话会话 = 把一条现有的安全边界搬到一条新链路上。
> **这一半单独做一轮、单独验**，别和契约文本混在同一个 commit 里 ——
> 混在一起的话，出问题时分不清是哪半引起的。
>
> ⚠️ **omp 那条要特别小心**：它的 `--tools` 是**白名单**，
> 而角色给的是**黑名单**。直接把 deny 名单塞进去是语义反转。
> 正确做法是「白名单减去 deny」，而白名单本身在 `omp/paths.ts` 的 `OMP_TOOLS`，
> 那份有打包前的真 ACP 握手闸门盯着 —— 算错了会让 `session/new` 整个失败。

### 8-2.3 界面：小 icon + 向上展开的角色卡

用户的原话是「和新对话、压缩同级」「点开后向上展开角色卡」。

```
┌─ 角色卡（向上展开）────────────┐
│  ○ 无角色                      │
│  ● 工匠   唯一能写代码的        │
│  ○ 验官   审查，禁改代码        │
│  ○ 画师   视觉产出，生图受限     │
│  …                            │
│  ⚙ 管理角色…                   │
└───────────────────────────────┘
        ▲
[✦][模型 ⌄][强度][👤][💬][⚡]  ← 👤 是角色，与新对话/压缩同级
```

**向上展开是硬要求**：这条控件行贴在输入框底部，向下展开会掉出可视区
（画布节点尤其明显，节点下边缘就是画布背景）。

复用现成的：`CanvasRoleEditor` / `CanvasRoleManager` 两个组件今天只被
`CanvasAgentBar` 引用，把它们接到新入口上即可，**不用重写**。

### 8-2.4 一条必须先答的问题：**换角色要不要重开会话？**

角色的契约是 `--append-system-prompt`，而那个 flag **只在 spawn 时传一次**。
也就是说：

- **会话没起来之前**换角色 → 下次 spawn 生效，无缝；
- **会话已经在跑**时换角色 → 系统提示词改不了，除非重开会话。

**裁定：(b) —— 换角色时弹确认「会结束当前会话」，照「新对话」那条的规矩走。**
（用户 2026-09-03）

理由：角色不是「参数」是「换了个人」。半路换掉而上下文还是旧的，比重开更让人困惑。

落地细节：

- 会话**没起来**时换角色 → 不弹confirm，直接换（下次 spawn 自然带上）。
  **别无脑弹** —— 空态换角色本来就没有会话可结束，弹一次确认是纯打扰。
- 会话**在跑**时换角色 → 走 `requestConfirm`，文案照「新对话」那条的形状：
  说清「会结束当前会话、旧记录不删、能从空态找回来」。
- 确认之后的动作 = 换角色 **＋** 走一次「新对话」那条既有路径。
  **不要另写一条结束会话的代码** —— 那条路上有乐观插入撤回、麦克风收音、
  resumeId 记账，各自都有事故史，重写必漏。

> 被否掉的 (c)（只当下次默认）为什么不行：模型控件那句「下条消息起生效」成立，
> 是因为 `/model` 命令**真的能中途改**；角色的契约走 `--append-system-prompt`，
> 中途改不了。照抄那句话会变成一句假承诺。

### 8-2.5 执行顺序（角色这块内部）
