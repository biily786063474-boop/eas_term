## 用户原话（2026-09-02）

> 用户开始使用的时候，引导用户一步一步进行操作。让用户在画板上去双击，双击之后建立了一个项目的
> frame，初次建立 frame 是空的 frame。空的 frame 上面有三个按钮，分别是 claude code、codex
> 和系统默认的 harness。用户点击后自动在 frame 中创建 AI 对话模块，并切换到相应的流程。
> 如果没有安装，则出现引导安装弹窗。所有的安装都要在 UI 里面完成，不要让用户看到不该看到的
> 开发者相关的东西。用户点击安装之后就直接安装完成，然后引导用户去登录，选择订阅登录还是
> 怎么样的，去做匹配的 UI。
>
> 然后终端里面的 top bar 上面的内容选项等取消，终端就是纯粹的终端。所有的 AI 对话由 AI 对话
> 模块来单方面承接。当然，CLI 里面的那些逻辑不要改变 —— 当用户在终端里面去进行 claude code 和
> codex 的时候，依旧要使用他们的状态机，以及其他的已经在终端落地的那些东西，包括之前做的
> 统计之类的、甘特图，都要保留。终端只取消它的 UI 入口。

## 一、一句话概括

**把「选哪个 AI」这个决定从终端的控制条搬到空 Frame 上，并让它一路把人送到能对话为止。**

终端因此退回纯终端；AI 对话模块成为唯一的对话入口。终端里手敲 `claude` 仍然照常工作，
它背后那一整套（状态机 / 甘特 / 统计 / 审批解析）**一个字都不动**。

## 四、子项目 A：空 Frame 的三个按钮

### 4.1 形态与判据

空 Frame（`f.nodes.length === 0`）里，把那行「空 Frame」换成一组引导：

```
        选一个 AI 开始
   ┌──────────┬──────────┬──────────┐
   │ Claude   │  Codex   │ 默认      │
   │ Code     │          │ harness  │
   └──────────┴──────────┴──────────┘
```

**三个按钮恒常显示，不按 `available` 过滤。** 依据是 `CliInfo.available` 的文件头注释：

> `false` 不等于「不显示」—— 用户第一次打开软件时本来就一个都没装，
> 那时候更需要看见「有哪些可选」。

按钮下方的小字按状态分三种（**这三句是给用户看的，不许出现命令、路径、变量名**）：

| 状态 | 判据 | 小字 | 点击后 |
|---|---|---|---|
| 可用 | `available && chatSupported` | （无） | 直接建节点 |
| 没装 | `!available` | 「点一下装好」 | 建节点 → 面板开在 `from:'install'` |
| 装了没登录 | `available && !loggedIn` | 「点一下登录」 | 建节点 → 面板开在 `from:'login'` |

> ⚠️ **「默认 harness」那颗的判据不一样。** 它随包分发，`available` 恒真（探测必过），
> 所以「没装」这一档对它不存在；它的三档是 `ompSetup.ts` 的
> `nextStepOf`：`provider` → `login` → `model` → `ready`。
> 用 `available` 去判它会得出「一直可用」，而用户点进去撞到的是选服务商那一屏。

### 4.2 缺口一：`openAgentPane` 收不了 CLI

`addAgentNode(frameId, opts)` 把 opts 原样转给 `openAgentPane`，而后者的参数表里
（`tabsSlice.ts:39-58`）有 `projectId / cwd / owner / role / initialMessage / sessionId /
background / resumeId`，**唯独没有 `cli`**。

而 `AgentChatView` 挑 CLI 的逻辑是现成的：

```ts
// AgentChatView.tsx:200-204
const pinnedCli = useStore((s) => { … return leaf?.pane.kind === 'agent' ? leaf.pane.cli : undefined })
// :544
setSelected((cur) => cur ?? pickDefaultCli(usable, pinned, readLastCli()))
```

`pickDefaultCli` 的第一条就是「pinned 压过一切」。**所以机制齐全，只差把值送进去。**

**改法**：`openAgentPane` 的 opts 加 `cli?: string`，建 pane 时写进 `pane.cli`。
一处新增字段、一处透传，不新增判定。

> **不要走「先写 localStorage 的 `lastCli` 再建节点」这条捷径。** 那个 key 是
> 「用户上次手动切换到哪个 CLI」的记忆（`pickCli.ts:42`），拿它当传参会有两个后果：
> ① 点一次引导按钮，等于把**全局默认**也改了；
> ② 两个 Frame 想开不同 CLI 时，后建的那个会把先建的记忆冲掉。
> 传参和记忆是两件事，别复用同一个格子。

### 4.3 缺口二：`pane.cli` 不落盘

`layout.ts:85-93` 的注释写得很清楚：

> **它今天不落盘**：`persist.ts` 的 `serializeCanvas` 对 agent pane 只写
> `{kind, cwd, resumeId}`。所以别把它当成「记住用户选的 CLI」—— 它只是内存里的
> 一次性传参（插件页开会话 / 派活），重启后就没了。

**这次要改变这个性质。** 用户从引导按钮选了 Codex，重启之后那个节点应该还是 Codex，
而不是悄悄退回 `pickDefaultCli` 的推测值。

**改法**：`serializeCanvas` 对 agent pane 多写一个 `cli`；反序列化时读回来。
**同时把 `layout.ts` 那段注释改掉** —— 留着一句「它今天不落盘」比没有注释更糟。

> 🔴 `store/` 是红区，改 persist 要照 [03-3B](../../architecture/03-agent角色边界.md#3b--开发期-agent你的边界) 的规矩：
> 加字段是安全的（老 canvas.json 读回来 `cli` 是 `undefined`，正好退回原行为），
> **但不许改已有字段的含义或顺序**。

### 4.4 点了之后走哪条流程

三个按钮共用一条路，分支只在最后一跳：

```
点按钮
  └→ addAgentNode(frameId, { cli })      建节点、面板挂载
       └→ AgentChatView 挂载，pinnedCli = 这个 cli
            ├─ 可用且已登录 → 直接进对话（什么弹窗都没有）
            ├─ 没装         → setSetupFor({ cli, from: 'install' }) → CliSetupPanel
            ├─ 装了没登录   → setSetupFor({ cli, from: 'login' })   → CliLoginPanel
            └─ 默认 harness 没配好 → OmpSetupPanel（它自己按 nextStepOf 决定停在哪一屏）
```

**这四个分支今天全都存在**（`AgentChatView.tsx:238-243` 那个入口的注释明写
「它不用自己判断该开哪张面板 —— 分支放在渲染那一侧」）。所以子项目 A 不需要新写任何一张面板，
只要保证按钮把 `cli` 送到，剩下的自己会发生。

### 4.5 「点击安装之后就直接安装完成」

用户这句话要按字面做：**点了安装就开始装，不再让用户在几种安装方式之间挑。**

今天 `agentInstall.ts` 的 `optionsFor()` 会给出 2–3 个候选（官方脚本 / Homebrew / npm），
面板让用户选。新链路取**第一条**（`optionsFor` 返回的顺序就是推荐顺序，官方脚本排第一）。

> **其余候选不要删。** 装失败时那几条是唯一的退路（公司网络挡了 curl，brew 可能通）。
> 做法是：默认直接用第一条，**失败之后**才把其余选项摊开。
> 成功路径上用户一次选择都不用做，失败路径上他仍有牌可打。

## 五、子项目 B：终端 top bar 下线

### 5.1 要拆的是什么

`CanvasAgentBar.tsx`（文件头自述）：

> 形态：左侧星星按钮（显示当前 CLI 的品牌标识，点开换）→ 角色/模型/思考三枚胶囊 → 右侧 ▶ 启动。

这一整条就是用户说的「top bar 上面的内容选项」。它渲染在 `PaneView.tsx:490` 的
`.agentbar-wrap` 里，**只在画布终端节点上出现**（分屏不渲染这层）。

### 5.2 ⚠️ 这会推翻一条 2026-08-27 的用户决定

`PaneView.tsx:480-488` 那段注释：

> **一个 CLI 都没装时也照常显示**（2026-08-27 用户要求）。原来是整条藏掉……
> 但藏掉的代价更大：新用户第一次打开软件时**什么都看不到**，也就不知道这里本来能选 CLI、
> 更不知道该装什么。现在改成照常显示，启动按钮在没装时变成「安装」，点它直接装 ——
> 把「困惑」换成了「一条能往下走的路」。

**当时那个问题真实存在，现在由空 Frame 的三个按钮接管。** 所以这次下线是有条件的：

> 🔴 **子项目 B 必须排在子项目 A 之后。** 反过来做，中间会有一段时间
> 「新用户什么都看不到」—— 那正是 8-27 修掉的问题，别把它再造一遍。

### 5.3 拆到什么程度：**摘引用，不删文件**

```diff
  // PaneView.tsx
- {canvasTerm && pane.kind === 'terminal' && (
-   <div className="agentbar-wrap"><CanvasAgentBar … /></div>
- )}
```

`CanvasAgentBar.tsx` 与 `canvas.css` 里的 `.agentbar*` 样式**保留在仓库里**，理由：

1. 它带着大量实测结论（Claude 的 effort 档位来自 `claude --help` 真实探测、
   Codex 的模型表是主进程给的已知默认……），删了这些知识就没了；
2. 万一这条引导路走不通要回退，`git revert` 比重写便宜。

**但要在文件头加一段「已下线」的说明**，写清楚哪天、为什么、被谁取代 ——
否则下一个 agent 会看到一个没人引用的组件，然后花时间去搞清楚它是不是死代码。

### 5.4 ⚠️ 会被顺带孤立的两个东西

**① 角色（roles）**

`CanvasRoleEditor` / `CanvasRoleManager` **只能从 AgentBar 打开**（全仓搜索：
除了 `CanvasAgentBar.tsx` 自己，没有第二个引用点）。摘掉 AgentBar，
用户就再也进不去角色管理了。

而 `main/roles.ts` 是 🔴 文件，[图纸 01 红线 5](../../architecture/01-系统上下文.md) 明写：

> 代码那半只有一个角色有硬拦：`roles.ts` 的 `illustrator` 用 `tools.deny` 通配符挡图像类 MCP。

**这条 deny 仍然在主进程生效**（它不依赖那个 UI），所以下线不会造成安全回退。
但**用户失去了编辑角色的入口**，`~/.eas/roles.json` 变成只能手改的文件。

> **这是个需要用户拍板的取舍，不要替他决定。** 三条路：
> (a) 接受，角色暂时没有 UI 入口；
> (b) 把角色管理搬到设置面板里（工作量小，一个 tab）；
> (c) 搬到 AI 对话模块的工具栏上（更贴近它的实际用途）。
> **实现前先问。**

**② `AgentCmdBar`**

它有**两个**渲染点：`CanvasAgentBar.tsx:442`（画布，作为第二行）和
`PaneView.tsx:479`（分屏，独立渲染）。摘掉 AgentBar 只会带走画布那一份。

用户说的是「top bar 上面的**内容选项**」（胶囊），命令按钮条是另一回事。
**默认保留 `AgentCmdBar` 在两处都可用** —— 它是纯终端也用得上的东西（往终端里塞常用命令），
不属于「AI 对话入口」。

> 若用户的本意是连它一起清掉，那就把 `PaneView.tsx:479` 那行也摘掉。**实现前确认一句。**

## 六、绝对不动的东西（红线）

用户原话：「CLI 里面的那些逻辑不要改变……依旧要使用他们的状态机，以及其他的已经在终端落地的
那些东西，包括之前做的统计之类的、甘特图，都要保留。终端只取消它的 UI 入口。」

已核对过耦合关系，下面这些**与 `CanvasAgentBar` 零引用关系**，摘掉 UI 不会伤到它们：

| 保留项 | 位置 | 由什么驱动 |
|---|---|---|
| 终端状态机 | `features/status/` | 终端输出解析，不经 AgentBar |
| 甘特图采集 | `features/gantt/` 的 collector | `TerminalInput.tsx` / `TerminalView.tsx` / `main/pty.ts` |
| 审批解析 | `features/terminal/approvalParse.ts` | 终端输出 |
| 终端待办 | `useTerminalTodos.ts` | 终端输出 |
| 密钥徽章 | `SecretBadge.tsx` | PTY env |
| 路径链接 | `pathLinks.ts` | 终端输出 |
| MCP 桥 | `main/mcpBridge.ts` 经 `pty.ts` 注入 | PTY 生命周期 |

**验证判据（实现时必须跑）**：摘掉 AgentBar 之后，在终端里手敲 `claude`，
① 状态机点亮、② 甘特图记上这一轮、③ 审批卡照常弹、④ MCP 工具在会话里可用。
**四条全过才算这一步做完。** 只做单测不算 —— 这四条都是跨进程的。

## 七、执行顺序

顺序是**有依赖的**，不是排列偏好：

| # | 做什么 | 为什么排这里 | 验收 |
|---|---|---|---|
| 1 | `openAgentPane` 加 `cli` 参数并透传到 `pane.cli` | 后面全部依赖它 | 单测：传了 cli，新 pane 带上；不传，行为不变 |
| 2 | `pane.cli` 落盘 + 改 `layout.ts` 注释 | 早做，否则 3 做完会有「重启就丢」的中间态 | 单测：序列化/反序列化往返；老 canvas.json 读回来不炸 |
| 3 | 空 Frame 三按钮 + 接四条分支 | 依赖 1、2 | **真机**：三颗各点一次，分别到达对话/装/登录/omp 配置 |
| 4 | 「点安装就装」（取第一条命令，失败才摊开其余） | 依赖 3 的面板已接通 | **真机**：断网点安装，要看到失败原因与其余选项 |
| 5 | 摘 `CanvasAgentBar` 引用 + 文件头写「已下线」 | **必须最后**，见 §5.2 | **真机**：§6 那四条 |

> ⚠️ **第 3 步和第 5 步之间要停一次给用户看。** 引导链路是纯体验的东西，
> 一次做完再给他看，改起来就是全推翻；中间看一眼，方向错了只丢一步。
