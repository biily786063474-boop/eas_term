## 三、目标与非目标

**目标**

- 写码角色的会话默认落在自己的 worktree 与分支上，主工作区不被动。
- 每个角色在每个项目里有一份**章程**（静态：边界、落点、判据）与一份**台账**（动态：这条分支改了什么、为什么、到哪了）。
- 一个内置的**合并官**角色，配两个工具：看依赖波及、做合并预检；合并前后各跑一次回归，失败就退回。
- 一张 app 自动维护的**协同板**，每条会话启动时读到，随时可查，两条分支碰同一文件时能看见。
- 全部约束分两档写清楚：硬（CLI/OS/git 强制）与软（章程里说的）。

**非目标**

- 不做自动 rebase / 自动解冲突。冲突是人或合并官的活。
- 不做按路径的写权限强制（三家 CLI 都没原生支持）。章程写明「不该碰」，协同板做提醒，合并官做把关。
- 不改 `team_spawn` 的批次 worktree 逻辑，只共用底层操作。
- 不做跨项目协同板。

## 四、三条路线与推荐

**A · 全靠契约文本**：把「先开分支」「先看别人在改什么」「合并前跑测试」都写进 contract，
让模型自己执行。零代码。缺点：全是软约束；协同板得靠模型自报，而模型会说「已完成」而文件不存在
（`cli-headless-接口实测.md` 坑 1）。用户的原话是「在任何时候都知道」，靠自觉做不到。

**B · app 强制隔离 + 事实驱动的协同板 + 合并官角色（推荐）**：分支由 app 在起会话时建好、
cwd 直接指过去（模型没有「不开分支」的选项）；协同板由 app 从会话表和 `git diff` 算出来
（不是模型写的）；合并官是一张角色卡，但它拿到的依赖图与预检结果来自工具（事实），
回归命令来自项目设置（用户定的）。

**C · 全自动流水线**：合并官不是角色而是 app 里的一个按钮，自动 merge + 测试 + 回滚，
冲突时才起会话。优点：省 token。缺点：用户明确说要「合并角色」，且冲突之外的判断
（「这两条分支同时改了 store，语义冲突但文本不冲突」）恰恰需要模型看依赖图。
**B 里合并官的第一步就是机械预检，C 的省 token 好处 B 已拿到大半。**

**推荐 B。**

## 五、章程与台账（「每个角色自己的文档」）

用户这句话有两种读法，都做，但分开放，别混：

### 5.1 章程 `docs/roles/<roleId>.md`（项目级，进 git，用户可改）

回答「在**这个项目**里，这个角色能碰什么、产出放哪、什么算做完」。固定四段：

```markdown
# 工匠 · 本项目章程
## 边界
- 可以改：src/renderer/src/features/**、src/shared/**
- 不要碰：src/main/mcpBridge.ts、resources/agent-hooks/**（理由：图纸 03-3B 静默失效区）
## 产出与落点
## 完成判据
## 交接格式（写进台账的字段）
```

- **首次在某项目用某角色时由 app 生成初稿**：边界段留空让用户填，其余三段从角色卡的
  `contract` 与绑定报告（硬约束那几行）生成。已存在就不动。
- **注入方式：指针，不是全文。** 起会话时在系统提示末尾附一行
  「本项目对你这个角色的章程：`docs/roles/<id>.md`，动手前先读」。全文注入违反托管区纪律
  （`syncRules` 文件头那条 99% 字符的教训）。
- 章程里「不要碰」是**软约束**。硬约束只有绑定层那份；章程模板顶部固定一行说明这点，
  免得用户以为写了就拦得住。

### 5.2 台账 `.eas/board/<branch>.md`（项目级，**不进 git**，app 与角色共同写）

回答「这条分支到目前为止改了什么、为什么、卡在哪」。是协同板的一条记录，见第八节。
app 维护头部（角色 / 分支 / worktree / 起止时间 / 触及文件），角色通过 `board_note` 工具
追加自己的说明（决定、未完成项、给合并官的提醒）。契约里要求「每完成一个可交付的小步就记一条」。

## 六、写码会话自动进 worktree

### 6.1 规则

角色卡加一个显式字段，**不推断**（沿用 `team_spawn` 的 `isolation` 纪律：「系统不会替你判断这个角色写不写代码」）：

```ts
interface AgentRole {
  …
  /** 起会话时是否隔离到自己的 worktree。缺省 'none'。 */
  isolation?: 'worktree' | 'none'
}
```

内置默认：`e2e` / `builder` / `prototyper` → `worktree`；`scout` / `inspector` / `writer` /
`illustrator` / `runner` → `none`；新增的 `merger` → `none`（它就该在主工作区）。用户可改。

### 6.2 流程（起会话时，在 `agentChat:start` 里）

1. 角色 `isolation === 'worktree'` 且 cwd 是 git 仓库 → 建 `.worktrees/<roleId>-<6 位短 id>`，
   分支 `eas/<roleId>/<短 id>`，从当前 HEAD 分出。三道前置检查沿用 `teamWorktreeOps`。
2. 会话 cwd 改为 worktree；审批 hook（项目级 `<cwd>/.claude/settings.json`）跟着装到 worktree 里
   —— 这一点已经在 `team_spawn` 的 worktree 上成立，不是新行为。
3. 不是 git 仓库 → **不静默降级**：起会话前提示「这个目录不是 git 仓库，工匠会直接改主工作区」，
   用户点「继续」才起。
4. 会话结束**不删 worktree**。删除是用户在分支徽标上点的，且未提交改动一律拒删
   （`team_dissolve` 的纪律原样适用）。

### 6.3 界面

对话节点的角色名旁显示分支徽标 `eas/builder/ab12ef`，hover 显示 worktree 路径与触及文件数；
徽标菜单：「合并到主干」（起合并官，见第七节）、「打开终端到这个 worktree」、「删除」。

## 七、合并官

### 7.1 角色卡（内置，`group: 'main'`）

```
id: merger  name: 合并官  desc: 把角色分支合进主干；懂依赖波及，合并前后跑回归
caps: {}（要 git、要跑测试、要改冲突文件，硬约束不收紧）
isolation: 'none'
contract:
  你这一轮的职责是把一条角色分支合进主干，不是继续开发。
  流程固定：1 读协同板；2 调 merge_preflight 看冲突与「同时在改」的分支；3 调 repo_impact 看改动波及；
  4 在分支 worktree 跑回归；5 合并（--no-ff）；6 在主干再跑回归；7 失败就撤销合并提交并报告。
  只改冲突文件，不顺手重构。每一步的结果写进台账。
  完成判据：主干回归绿、台账有合并记录、协同板上这条分支标为「已合并」。
```

「只改冲突文件」是软约束，合并官的报告里必须列出它改过的文件，让用户能核对。

### 7.2 两个新 MCP 工具（eas-term server）

| 工具 | 输入 | 输出 | 来源 |
|---|---|---|---|
| `merge_preflight` | `{ branch }` | 合并基点、改动文件清单、`git merge-tree --write-tree` 的冲突文件、协同板上其他活跃分支与本分支的**文件交集** | `git.ts` 新增两个只读命令 + 协同板 |
| `repo_impact` | `{ files[] }` | 这些文件的反向依赖（谁 import 了它们）、涉及的环、建议的回归范围（按测试文件同目录匹配） | `analyzeProject(root)` 现有结果反查 |

两者都只读，不进 `fsGuard` 写侧。`merge_preflight` 不改工作区：冲突探测用 `merge-tree`，
不做试合并（git ≥ 2.38，低版本回落为「无法预检，直接合并看结果」并在报告里说明）。

### 7.3 回归命令

`Project` 加 `testCmd?: string`。项目设置里一个输入框；为空时从 `package.json` 的 `scripts.test`
推断并显示「推断值」。合并官通过契约里的「跑回归」= 执行这条命令；没有命令时合并官必须在报告里
写「未跑回归」，不许说「测试通过」。

### 7.4 触发

分支徽标菜单「合并到主干」→ 起一条合并官会话（当前项目主工作区为 cwd），首条消息预填
「把 `eas/builder/ab12ef` 合进 `main`」。也可以手动选合并官角色再说要合哪条。

## 八、协同板（「任何时候都知道代码该怎么改」）

分两层，静态那层项目里早就有，动态那层是新的。

### 8.1 静态：项目规范

`CLAUDE.md` / `AGENTS.md` / `docs/architecture/` / 角色章程。app 只在起会话时**注入指针**，不复制内容。

### 8.2 动态：`.eas/board.md`（项目根，gitignored，app 维护）

```markdown
# 协同板 · 2026-09-05 14:02 自动生成，勿手改
| 分支 | 角色 | 状态 | 起于 | 触及 |
|---|---|---|---|---|
| eas/builder/ab12ef | 工匠 | 活跃 | 13:10 | src/renderer/src/features/agentChat/**（4 文件）|
| eas/e2e/9c0d11 | 全流程 | 闲置 40 分钟 | 11:02 | src/main/roles.ts, src/shared/types.ts |
| ⚠ 两条分支都改了 src/shared/types.ts |
```

- **数据全部来自事实**：会话表（哪条活着、多久没动）+ 每条 worktree 的 `git diff --name-only <基点>`。
  模型写不了这张表，只能通过 `board_note` 往自己那条台账追加说明。
- **刷新时机**：会话起 / 每轮 `result` 事件 / 会话结束 / 分支删除。写文件用临时文件 + rename，
  多会话同时刷新不会写出半截。
- **注入**：起会话时把当前板**全文**放进系统提示（它就几行，不违反 token 纪律；超过 20 行截断并附路径）。
  会话中途变化不推送 —— 三家 CLI 都没有中途注入系统提示的通道；契约要求「改文件前先 `board_read`」，
  加一个只读工具 `board_read` 让它随时查。
- **交集告警**：两条活跃分支触及同一文件 → 板上标 ⚠，两个对话节点的分支徽标变色。
  这是提醒，不是拦截。

### 8.3 为什么这样就够

用户要的是「知道该怎么改」，拆开是三个问题：规范是什么（静态层，指针）、别人在改什么
（板）、我这条改到哪了（台账）。三样都是文件、都在项目里、都能被任何 CLI 读到 ——
这正是三个 harness 通用的前提。

## 十、分阶段与依赖

```
绑定层·阶段一 ──┐
               ├─→ P1 分支隔离 + 协同板（第六、八节）──→ P2 合并官 + 两个工具 + testCmd（第七节）
章程模板 ──────┘                                        └→ P3 章程自动生成 + 台账 board_note（第五节）
```

- **P1 先做**：它是其余一切的地基（没有分支就没有合并，没有板就没有「互相看见」）。
- P2 依赖 P1 的板与分支命名。
- P3 可与 P2 并行。
- 绑定层的阶段二、三（编辑器矩阵、Codex 待验项）独立推进。

每个阶段的真机验证都要在**隔离配置目录**里做（[[eas-term-测登录别毁凭证]]），且要真的起两条会话看板上出现两行。

## 十一、待决项（按下面的假设写的）

1. **「角色文档」指章程还是台账？** 假设：两个都要，分开放（第五节）。
2. **worktree 目录与分支前缀**：沿用 `.worktrees/`，分支前缀 `eas/<roleId>/`（与团队的 `eas-team/` 区分）。
3. **回归命令来源**：`Project.testCmd` 优先，`package.json` 推断兜底；没有就如实报「未跑」。
4. **合并官能不能改代码**：能，但契约限定为冲突文件，报告列出改过的文件供核对。
5. **合并后 worktree 删不删**：不自动删，徽标上点删；未提交改动拒删。
6. **不是 git 仓库时**：提示后可继续，不静默降级。
7. **协同板注入全文还是指针**：几行以内全文，超 20 行截断附路径。

## 十二、评审团

| 视角 | 结论 |
|---|---|
| 完成性 | 六条需求各有落点；合并官的「懂依赖图」落在 `repo_impact`，「跑回归」落在 `testCmd` |
| 体验 | 用户不用记「先开分支」：选了工匠就在分支上；合并是徽标上一个菜单项 |
| 安全 | 主工作区只有只读角色与合并官会碰；协同板是事实不是自报；预检不改工作区 |
| token 成本 | 章程走指针；板几行；合并官多两次工具调用，换来少一次「合错了再修」 |
| 维护 | 全部复用已有零件（worktree 操作、依赖分析、git 模块、托管区纪律），新增的是两个只读工具与一个字段 |
| 风险 | Claude 的 `--resume` 按 cwd 找 transcript，worktree 删除后旧会话不可恢复（现在团队 worktree 已是如此，需在删除确认里说明） |
