# 自定义知识库：让用户按自己的分类建一个库

> 2026-08-11 · 设计定稿

## 要解决什么

内置知识库的分类是写死的八个目录（`00-inbox` / `me` / `people` / `methods` /
`domains` / `projects` / `sources` / `_templates`）。这套分法对很多人不合适 ——
做研究的想按「课题 / 文献 / 实验」分，做内容的想按「选题 / 素材 / 成稿」分。
现在他们只能忍着，或者干脆不用。

目标：**用户想换分类时，照着内置库的建法引导他建一个自己的库，
而这个库享有和内置库完全一样的读写能力**（查询、图谱、体检、收件箱、归档、双链）。

**老库原样不动** —— 不搬、不改、不删。建完新库直接切过去，老库还在盘上，随时能指回去。

## 一个让成本大幅下降的发现

现有读写机制**几乎不认目录名**：

```
walkNotes(root)   全库递归；只跳过 点开头 / 原始素材目录 / 根部 CLAUDE.md·AGENTS.md
      ↓
scanNotes         抽 front-matter 的 summary、tags，和正文里的 [[双链]]
      ↓
图谱 · 体检 · 查询 · 反链    全建在这一份数据上
```

`wiki:setPath` 也只校验「是不是一个存在的文件夹」，不校验长得像不像知识库。

**所以一个自定义分类的库，今天就能被现有工具正常读写。** 真正绑死在那八个目录上的只有四处：

| 位置 | 干什么 | 自定义库的处理 |
|---|---|---|
| `WIKI_DIRS`（paths.ts） | init 时建骨架 | 按配置建，不走它 |
| `looksLikeWiki`（paths.ts） | 只用来算 status 的 `looksEmpty` | 纯提示，无影响 |
| `inboxOf` / `00-inbox` | 收件箱 + `.eas-sources.json` 来源映射 | 收件箱功能依赖它，配置里必须指定一个 |
| `schema.ts` | 生成库内 `CLAUDE.md`/`AGENTS.md`（给 agent 的说明书） | **必须按新分类重写**，否则 agent 拿到的是一份描述不存在目录的说明 |

## 设计

### 一、库内一份 `.eas-wiki.json`

放在库根目录，声明这个库长什么样：

```json
{
  "version": 1,
  "dirs": [
    { "name": "00-收件箱", "purpose": "丢进来还没整理的原始素材", "role": "inbox" },
    { "name": "课题",     "purpose": "一个课题一篇，记它的进展与结论" },
    { "name": "文献",     "purpose": "读过的论文与书，一篇一条，含出处" },
    { "name": "_模板",    "purpose": "新建笔记的模板", "role": "templates" }
  ],
  "frontMatter": { "required": ["summary", "tags"], "optional": ["status", "source"] }
}
```

三个约定：

- `role: "inbox"` **必须恰好有一个** —— 收件箱是有专属机制的（徽章计数、
  `.eas-sources.json` 记录「这份文件原来在哪」），没有它整理流程就断了。
- `role: "templates"` 可选；有的话新建笔记会从这里取模板。
- `purpose` 不是注释，是**要写进 agent 说明书的正文**。这一句写不清楚，
  agent 就不知道东西该往哪放 —— 它是这份配置里最该斟酌的字段。

点号开头是有意的：`walkNotes` 跳过点开头的条目，所以它不会被当成笔记扫进图谱。

### 二、app 侧的配置闸门

四个耦合点改成「有配置就按配置，没有就走今天写死的那套」：

| 函数 | 有 `.eas-wiki.json` 时 | 没有时 |
|---|---|---|
| `dirNames(root)` | 按配置里的 `dirs` 返回 | 今天的八目录（含老库中文名回落） |
| `inboxOf(root)` | 返回 `role:"inbox"` 那个 | `00-inbox` / 老库中文名 |
| `looksLikeWiki(root)` | 配置文件在就算是 | 今天的判据 |
| schema 生成 | 按 `dirs` 逐条列出 `name` 与 `purpose` | 今天的模板 |

**老库一个字节都不会变** —— 它们没有这个文件，全部走 else 分支。这是整个设计里
最要紧的一条：内置库的用户不该为这个功能付出任何代价。

### 三、skill：`wiki-architect`

**装在哪**：`~/.claude/skills/wiki-architect/`（全局）。它引导的是「怎么组织你的知识」，
和当前在哪个代码项目里无关 —— 放进某个项目的 `.claude/skills/` 会让它只在那个项目里可用，
而用户想整理知识库的时刻往往不在那个项目里。

**依赖**：这个 skill 必须等第二块（app 侧配置闸门）上线之后才有意义 ——
在那之前它建出来的库虽然能被读写，但收件箱会认不出、库内说明书仍描述内置分类。
所以实现顺序是 **配置闸门 → skill**，不能反过来。

唤起词：「重新设计知识库」「知识库分类不合适」「按我的方式建知识库」「自定义知识库」。

流程五步：

1. **读现状** —— 当前库有没有、多少篇、怎么分布。已有库的话把分布摊给用户看
   （哪个目录堆着、哪个空着），让他的新分类有依据，而不是凭空想。
2. **问清怎么分** —— 一次一个问题。核心是那句 `purpose`：不是问「你要几个文件夹」，
   而是问「你平时往里放的东西，大致分几类，每类一句话怎么描述」。
3. **给出方案让用户改** —— 目录清单 + 每个的一句话 + front-matter 字段，等他点头。
4. **建库** —— 创建目录骨架、写 `.eas-wiki.json`、生成库内说明书、放模板、
   `wiki:setPath` 指过去。
5. **确认** —— 把新库的状态读回来给用户看（几个目录、说明书写了什么）。

### 四、给 agent 的说明书怎么覆盖

这条是用户明确要求的。落点只有一处，比想象的简单：

知识库的能力**不写进任何全局文件**（`agentRules.ts` 里写着为什么：换个终端不该读到
Eas-Term 专属的东西，整条能力搬进了 MCP 工具，靠 PTY 注入的端口/令牌做门禁）。
agent 侧关于「这个库怎么分类」的唯一来源，就是**库内那份 `CLAUDE.md` / `AGENTS.md`**。

所以只要 schema 生成按新配置走，覆盖就完成了 —— 沿用现有的 v4 围栏机制：
围栏内是我们生成的、可安全重写，围栏外用户自己补的规矩原样保留。

MCP 工具描述（`mcp/eas-mcp.mjs`）里讲的是**流程**（先 lint 再读、归档要等确认），
和分类无关，不用动。

## 明确不做

- **不搬老库的内容**。跟「老库原样不动」直接冲突，而且搬迁要处理双链会不会断、
  归错了怎么回滚 —— 那是另一个独立设计，不进首发。
- **不做多库并存**。Eas-Term 同时只指向一个库，这是现有设计，本次不改。
- **不做分类的自动推荐**。skill 问清楚、给方案、用户拍板；不去猜「你应该这么分」。

## 风险与取舍

| 风险 | 处理 |
|---|---|
| 用户配了一个没有 inbox 的库 | 写配置前校验，缺了就明确拒绝并说清收件箱为什么必需 |
| 目录名带 `/`、以点开头、或与 `.eas-wiki.json` 撞名 | 建库前校验名字，非法就当场指出 |
| 用户建完发现分类不合适 | 目录和配置都是普通文件，改名/改配置即可；skill 支持二次唤起调整 |
| 配置文件被手工改坏 | 解析失败时**回落到内置八目录**并在界面提示，不能让库变成打不开 |

## 验收

- 建一个三目录的自定义库 → 现有全部工具照常工作：`wiki_query` 查得到、
  图谱画得出、`wiki_lint` 不误报、收件箱徽章正常、归档流程走得通
- 库内 `CLAUDE.md` 描述的是新分类，且围栏外手写的内容在重新生成后仍在
- 指回老库 → 一切和今天完全一致（这条是回归，必须验）
