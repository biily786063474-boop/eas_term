# 统一状态机与四个显示面

**日期**：2026-08-14
**范围**：把散在五个地方的「终端在干什么」收拢成一个状态机，四个显示面改为它的视图。

---

## 为什么做这件事

「一个终端此刻是什么状态」这件事，今天有**五处各自为政**：

| 位置 | 干什么 |
|---|---|
| `store/uiSlice.ts:68-103` | 六个字段存原始信号，不变式写在注释里靠人工在各调用点维护 |
| `features/island/useIslandFeed.ts`（297 行）| 把六个字段聚合成灵动岛要的一帧，顺带解析「这个 pty 落在哪」 |
| `features/canvas/CanvasDrawer.tsx:437` | 右上角待处理气泡（数字）|
| `features/canvas/CanvasDrawer.tsx:489` | 抽屉项目行右侧的文字徽章 |
| `features/canvas/CanvasStage.tsx:529` | 双击弹出的项目列表右侧提示 |

外加 `features/canvas/CanvasRunMonitor.tsx` 单独显示「正在跑」。

后果已经出现了两次：

1. **右上角的通知消失了。** `2746825 左右抽屉对调` 把待处理气泡挪到了 `left: 48px; top: 14px`，而左上角原本住着运行监视 `.crm`（`left: 14px; top: 14px`、宽 186px、z-index 42），气泡是 z-index 31 —— **被整个盖住**。而运行监视那条规则上方就写着当初的约定：「放左上：右侧是「完成 / 待处理」那一侧……两类状态分列左右才不混」。搬动的人没看到那条注释，因为它在另一个文件的另一个位置。
2. 六个字段的不变式（「`ptyTiming` 和 `runningPtys` 同源」「`ptyApproval` 和 `attentionPtys` 同生共死」）只存在于注释里，任何新增的读取方都得重新读一遍注释才知道该怎么用。

统一之后，「状态」这件事在整个应用里只有一个说法，四个面是它的视图。

## 一、状态机

### 1.1 状态定义

状态长在**终端（ptyId）** 上，三态互斥：

| 状态 | 含义 | 判据（**只看当前信号，不看历史**）|
|---|---|---|
| `running` | 正在跑 | `ptyId ∈ runningPtys` |
| `approval` | 停下等你批准 | 不在 `runningPtys`，且 `∈ attentionPtys`，且 `ptyApproval[ptyId]` 有解析出的问句 |
| `done` | 跑完了、还没人管 | 不在 `runningPtys`，且 `∈ attentionPtys`，且没有解析出的问句 |
| （无）| 纯 shell，或已经被看过 | 以上都不是 |

判据写成「当前信号的纯函数」而不是「刚从 running 落下」，是有意的：后者要求状态机记住历史，
于是它得自己维护一份状态、还得和 store 对齐，那正是这次要消灭的东西。
`runningPtys` 的维护时机（spinner 起落）已经在 `TerminalView` 里做好了，状态机只读不写。

**不一致时谁说了算**：`attentionPtys` 是权威 —— 它回答「有没有待处理」；
`ptyApproval` 只回答「待处理的内容是什么」。所以 `ptyApproval` 有残留值但
`attentionPtys` 里没有该 ptyId 时，状态是「无」，不是 `approval`。
（这种残留是可能的：两者「同生共死」是靠调用点手动维护的约定，不是结构保证。）

`approval` 是唯一「不管就永远卡着」的状态，所以在任何排序里都排最前。

### 1.2 迁移

只有四条：

| 从 | 到 | 触发 |
|---|---|---|
| 无 | `running` | spinner 起 |
| `running` | `approval` | spinner 落，且解析到问句 |
| `running` | `done` | spinner 落，且没有问句 |
| `approval` / `done` | 无 | **那个终端被聚焦到眼前** |

最后一条与现有语义一致，不改旧行为：在灵动岛点「知道了」只是让灵动岛别再冒
（`silencedNotices`），**不等于处理完** —— 侧栏红点、抽屉呼吸、标题栏铃铛照旧留着，
真正消掉要等你去那个终端。

**「被聚焦到眼前」的判据：发生了一次指向该终端的聚焦动作。** 具体是：
用户点进该终端本体（它拿到输入焦点），或从任何一个状态面点击跳过去
（已完成列表、项目行、双击列表、灵动岛）。

**「它在画布上可见」不算。** 这一条必须写死：画布模式下 `PaneLayer` 把所有 tab 的
所有 leaf 都渲染着（见 `PaneLayer.tsx` 顶部注释「永不换父」），一个终端只要 Frame 在视野里
就一直「可见」。拿可见性当判据的话，`done` 会在产生的同一帧被清掉，整个功能等于没有。

### 1.3 数据来源

**不新增存储。** 仍然是 `store/uiSlice.ts` 现有的六个字段：

```
runningPtys      正在跑的 ptyId
attentionPtys    待处理的 ptyId
silencedNotices  灵动岛上点过「知道了」的 notice id（按 notice id 记，id 里带耗时，
                 所以同一终端下一轮完成时会重新提醒）
ptyTiming        每个终端的耗时账本（与 runningPtys 同源）
ptyApproval      停下等审批的问句与选项（与 attentionPtys 同生共死）
approvalSentAt   写回选项后等 spinner 复活的时刻（1.5s 没转起来 = 写回没生效）
```

状态机只是把这些注释里的不变式**变成代码**。

### 1.4 不持久化

`done` / `approval` 不落盘，重启后清空。理由：`ptyId` 重启后本就全变
（见 `useTerminalTodos.ts` 顶部对同一问题的记录：重启后画布上「看起来还是那个终端」
的节点，背后是全新进程、全新 leafId，唯一扛得住重启的是画布节点自己的 id）。
要跨重启保留就得另建一套锚点，是另一个量级的工作，本次不做。

## 二、模块结构

新建 `src/renderer/src/features/status/`，`features/island/` 并入：

```
features/status/
  machine.ts        纯函数。**不引 React、不引 electron** → node --test 直接跑
  machine.test.ts   见第五节
  useStatus.ts      唯一的 store 读取口，四个视图都从这里拿
  StatusIcon.tsx    三个动态 icon 的唯一实现
  DoneList.tsx      右上角气泡点开的已完成列表
  RunMonitor.tsx    ← 从 canvas/CanvasRunMonitor.tsx 搬来
  useIslandFeed.ts  ← 从 island/useIslandFeed.ts 搬来，改成消费 machine.ts
  status.css        以上全部的样式
```

**为什么纯函数模块**：这个仓库现有的 72 个测试全部长在 electron-free 的纯逻辑模块上
（`taxonomy.ts` / `projectPaths.ts` / `sessionPaths.ts` / `snapshotPaths.ts`），
`node --test` 直接跑 `.ts`、零依赖。状态机的全部价值在于迁移规则和聚合规则能被测 ——
「已完成什么时候清」「一个项目 3 个终端显示哪个」写错了肉眼极难发现。
塞进 zustand slice 就测不了（得 mock store）。

### 2.1 `machine.ts` 的四个导出

```ts
/** 一个终端此刻是什么状态 */
export function statusOf(ptyId: string, raw: RawSignals): TermStatus | null

/** 这个 pty 落在应用的哪个位置。从 useIslandFeed 的 Located 提出来 —— 
 *  灵动岛、已完成列表、项目行都要解同一件事 */
export function locate(ptyId: string, tabs: Tab[], frames: Frame[], projects: Project[]): Located | null

/** 按项目聚合：最紧急的那个 + 计数 + 全部明细 */
export function byProject(ptys: string[], raw: RawSignals, ctx: LocateCtx): ProjectStatus[]

/** 排序：approval > done > running > 其余；同档内按最近变化时间倒序 */
export function sortProjects(list: ProjectStatus[]): ProjectStatus[]
```

`RawSignals` 是那六个字段的只读快照，由 `useStatus.ts` 从 store 取好传进来 ——
`machine.ts` 不认识 store。

## 三、四个显示面

### 3.1 抽屉项目行（`CanvasDrawer.tsx:489`）

现在：

```tsx
{projectHasAttention(p.id) ? <span className="cd-proj-badge attn">待处理</span>
 : onCanvas ? <span className="cd-proj-badge">画布中</span> : null}
```

改成：**动态 icon + 计数**，不显示文字。

**`画布中` 删掉** —— 它是「这个项目在不在画布上」这个**位置信息**，不是任务状态，
混在同一个位置显示会让人以为它是状态的第三种取值。

### 3.2 双击弹出的项目列表（`CanvasStage.tsx:529`）

现在每项 `hint: exist ? '已在画布' : undefined`。

改成：**动态 icon**（同一套 `StatusIcon`），`已在画布` 删掉（同上，位置不是状态），
并按 §1 的规则**动态排序**。

点击行为按**两档**分（不是叠加，先判上面这档）：

1. 该项目有 `approval` 或 `done` 的终端 → **聚焦到最紧急的那个终端**
   （这本身就会把视图挪过去，不需要再 `centerOnFrame`），并按 §1.2 清掉它的状态
2. 否则 → 维持原行为：已在画布就 `centerOnFrame`，不在就建 Frame

### 3.3 右上角气泡 + 已完成列表

**位置改回右上角。** 这既是你的要求，也顺带修好 §「为什么做这件事」里那个
「通知不见了」的 bug —— 左上角是运行监视的地盘，两类状态分列左右是原本就定下的约定。

点击气泡 → 弹出 `DoneList`：**只列 `done` 状态的项目**，点某项 → 聚焦到对应终端 → 该项消失（§1.2 第四条）。

### 3.4 灵动岛（`useIslandFeed.ts`）

**外观与交互完全不动。** 只把它内部那套推导换成调用 `machine.ts`，
`Located` 那段搬进 `machine.locate`。推送节流（250ms）、审批过期判定（1.5s）
这些灵动岛特有的东西留在 hook 里，不进状态机。

### 3.5 运行监视（搬家）

`CanvasRunMonitor.tsx` → `features/status/RunMonitor.tsx`，**位置仍在左上角**，
数据源换成 `useStatus`。它只显示 `running`。

## 四、动效规格

三个 icon 同尺寸、同基线，放在一起要能一眼分开。

| 状态 | 形态 | 动效 |
|---|---|---|
| `running` | 三个点 | 轮番上跳，`cubic-bezier(.34, 1.56, .64, 1)`（回弹，与仓库既有抽屉弹簧同一条曲线），相邻点相位差 ~120ms |
| `approval` | 圈 + 感叹号 | 整体缓慢呼吸（opacity + 轻微缩放）—— 三者中唯一「持续动但不前进」的，对应「卡住」这个语义 |
| `done` | 圈 + 对勾 | **对勾右端超出圆的边缘**；入场时对勾描边一次，之后静止 |

## 五、测试

新建 `machine.test.ts`（在现有 72 个之外），锁死：

- 三态判定与互斥（不会同时是两种）
- 四条迁移各一条用例
- **清除规则**：聚焦那个终端 → 清；聚焦同项目的**别的**终端 → 不清
- 聚合：3 个终端 2 done 1 running → 项目行显示 done 的 icon、计数 2、点击落到最早那个 done
- 排序：approval 排在 done 前，done 排在 running 前
- 边界：项目没有任何终端、终端查不到所属项目、`ptyApproval` 有残留值但 `attentionPtys`
  里没有该 ptyId（按 §1.1 应判为「无」而不是 `approval`）

这些正是肉眼极难发现写错的部分 —— 状态显示错了不会崩、不会报错，只会让人在某个时刻
少看到一条该看到的提醒，而那时候已经想不起来是哪里的问题了。
