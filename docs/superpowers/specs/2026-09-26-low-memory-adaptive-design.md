# 16GB 设备自适应运行设计（待用户审阅）

## 目标
让 16GB 及更低内存设备在全新安装、首次发送 AI 消息、多 Frame 和媒体浏览时保持可用；资源保护不得误拦用户主动操作，也不得通过杀掉正在执行的 CLI、插件任务或未保存视图来“省内存”。兼容 32GB+、macOS/Windows；不把物理内存容量直接当作系统压力。

## 已知事实
- `runtime/controller.ts` 将 macOS 内存 `warning` 与 `critical` 都送为 `critical:true`；交互型 Claude 启动仅在 `critical-pressure` 等待，调度器默认 60 秒超时。
- 默认 `eco` 的 50% 阈值用于**整机占用加预留**的后台准入，不是本软件内存上限；16GB 机器上容易让后台任务长期排队。交互型绕过百分比阈值，但不绕过上述误判。
- `PaneView` 已懒加载词典、代码图谱和 Wiki；`idleWatchdog` 已以 30 秒间隔查看进程 CPU，不能重复造相同机制。尚无可对照的 16GB 本机进程内存基线。
- 首次发消息时 `agentChat:start` 创建会话即回 `ok:true`，资源排队在后台完成；异步失败后输入框已清空。

## 用户体验契约
1. 用户主动发送的消息优先于预取、索引与后台任务；macOS `warning` 不阻止消息启动。真正 `critical` 可短暂等待，但界面需给出明确原因和取消/手动重发，不得静默延迟执行。
2. 在未确认投递到 CLI 前，原文可恢复；任何自动重试都不得把同一消息重复交给 CLI。
3. 节能策略仅降级可恢复或可延迟的工作：隐藏页动画、预览、索引、插件预热与缓存；不全局杀进程、不卸载正在编辑/运行的模块。
4. 跨平台读数不可信时只监测、不闭闸；资源事件只记录脱敏的数值/原因/阶段，不记录提示词、密钥、命令或路径。

## 架构
- **准入层**：区分 `warning`、`critical`、未校准；用户交互型与后台型采用不同策略，拒绝原因用结构化码跨越 `scheduler → sessionStartup → agentChat → UI`，不靠错误字符串包含 `timeout`。
- **测量层**：复用 `app.getAppMetrics()` 与现有 runtime monitor，增加限频、按需的进程内存快照和阶段标记（冷启动、空闲、首次消息、多 Frame、媒体）；保留聚合数据而非内容。
- **适配层**：仅依据测得热点做延迟初始化/隐藏暂停/有上限缓存。任何策略改动都需对 8/16/32GB 与未校准平台跑矩阵；不凭经验直接调低现有阈值。

## 验收标准
- 受校准的 macOS 上 `warning` 条件下首次 Claude 消息不发生资源等待超时；真正 `critical` 的提示准确、原文可手动重发且最多投递一次。
- 8/16/32GB 模拟压力与 macOS/Windows 未校准路径均有自动回归；`npm run check`、`npm run build` 通过，打包应用以隔离 userData 启动并核对 UI/日志。
- 实体 16GB 设备上记录同一套场景的发布前/后进程 RSS、系统压力、首条消息启动时延和峰值；热点优化至少让选定场景中本软件进程组合峰值比基线下降 20%，同时不能恶化首次消息时延或使活动任务中断。未测到基线前，不宣称已适配 16GB。
