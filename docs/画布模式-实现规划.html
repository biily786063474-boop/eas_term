00本次定稿锁定的两个决策

这两条是全局画布相对旧「tab 级 canvas」方案的根本变化,决定了数据模型与 P0 骨架,已确认。

决策 ① · 终端「共享」——同一批终端,两种摆法

画布不是独立工作区。切到画布 = 把当前项目已有的终端/面板按项目铺成 Frame;在画布里新建的终端,切回分屏也能看到。同一个 leaf(含 pane / ptyId)被 split 树和 canvas 节点共同引用,共用同一个 PaneView 实例——这既是"两视图同源"的产品语义,也是"终端不断连"的技术前提。反面(独立工作区)被否决:同一终端不能两边看到、要维护两套状态。

决策 ② · 双层渲染——装饰层可缩放,活内容层永不换父

原型用 world { transform: scale() } 整体缩放、节点嵌在 frame DOM 内——那是假终端才成立。真实的活终端 PaneView 一旦从「分屏容器」移进「画布 frame」,父 DOM 变了就会被 React 卸载重建 → xterm 重挂载 → 会话与滚动缓冲全丢。解法:活内容层(所有 PaneView)常驻一个全局容器永不换父,frame 边框/标题/点阵/图形是另一层装饰,可随意 transform scale。见 §5-A。

02现有架构的同构点(已核验)

项目现有架构里藏着与无限画布同构的基建,复用它们能省掉一半工作、并绕开最大的坑。以下均已对读源码确认。

① 布局已是「绝对定位 + 坐标计算」,不是 DOM 嵌套

layout.ts 顶注:"所有终端叶子以绝对定位渲染在同一容器里,分屏/调整比例只改坐标,不改变 React 元素层级,从而保证 xterm 实例永不重挂载"。computeLayout 产出 0~1 比例矩形,PaneView 据此算 left/top/width/height 百分比(PaneView.tsx:138-143)。画布节点只是把 rect 来源换成"世界坐标×视口"。

② PaneView 已是「可切换内容的卡片」,leaf 已是「内容单元」

PaneView 接 {tabId, leaf, rect, isActive},按 pane.kind 渲染 Terminal/Code/Diff/Image/History/Chat/Dict(PaneView.tsx:188-212)。leaf({id, pane},pane 含 ptyId)是内容单元,现挂在 tab.root 树里(shared.ts:6-15)。画布节点不重写内容渲染——只是换一个引用同一 leaf 的外壳。

③ 所有 tab 的所有面板本就常驻挂载

App.tsx:100-102 tabs.map(tab => <TabContent visible={tab.id===activeTabId}/>)——非激活 tab 用 display:none 隐藏而非卸载,所以跨 tab 切换终端也不断连。这正是"统一渲染层"要推广的机制:把"每 tab 一个容器"升级为"一个全局内容层容纳所有 leaf"。

④ 入口 action 齐全,画布零平行逻辑

openTerminal({projectId,cwd}) / openFile / openInPane(复用同类面板或分屏)/ setPaneKind / closeLeaf 均已存在(tabsSlice.ts)。画布的"新建终端 / 拖文件预览 / 切类型 / 删节点"全部复用它们,不建平行 CRUD。

结论:不引入 react-flow / tldraw,自研轻画布引擎。最难的"活终端塞进画布还不断连"这件事,只要坚持所有 PaneView 始终挂同一父容器、同一 key={leaf.id},切模式只改 style 即可解决——这是自研契合现有架构、第三方库无法替代的优势。

03形态总览

对齐配套原型(画布模式-原型.html)的既定形态。注意与现有分屏视图的两处布局差异。

  • 顶栏:中间项目药丸,右侧分段控件 [终端 · 画布] + 主题点。差异画布模式不显示 TabBar。
  • 主体:左为画布舞台 .stage,右为资源抽屉 .sidebar。差异抽屉在右侧(现分屏 Sidebar 在左侧);画布模式下左侧 Sidebar 让位给舞台。
  • 舞台:.viewport(裁剪 + 点阵背景,背景随缩放)→ .world(装饰层,transform: translate + scale)。活内容层 .pane-layer 覆盖其上(见 §5-A)。
  • Frame:head(圆点 + 名称 + 路径 + "N 面板"计数 + 新建终端 + 折叠 + 删除✕)· body(容纳节点,空时提示)· 右下 resize 手柄。可拖 / 折叠(只剩 head)/ resize / 重命名。
  • Node:head(类型胶囊 kind-pill + 标题 + 删除×)· body(按 kind 渲染)· 右下 resize。可拖 / resize / 切类型 / 重命名 / 复制 / 删除。
  • Shape:矩形 / 箭头 / 便签,直接在世界坐标;便签双击编辑文本。
  • 浮动控件:左侧竖排工具栏(选择/新建Frame/矩形/箭头/便签);右下缩放胶囊(− 100% + ⤢);顶部提示条;收起抽屉后右上浮动展开按钮。

04数据模型

核心思想:leaf 是共享内容单元,split 树与 canvas 场景各存一份布局、共引同一批 leaf。画布是全局单例,不属于任何 tab。

// 新增 canvasSlice —— 全局画布场景(单例),挂进 store
interface CanvasSlice {
  viewMode: 'split' | 'canvas'        // 全局视图,titlebar 分段控件切换
  canvas: CanvasScene
  /* actions 见下 */
}

interface CanvasScene {
  viewport: { x: number; y: number; scale: number }  // 平移 + 缩放(世界→屏幕)
  frames: CanvasFrame[]
  shapes: CanvasShape[]
}

interface CanvasFrame {
  id: string
  projectId: string | null   // 绑定项目(null=画布内新建的临时 Frame)
  name: string                // 默认取项目名,可重命名
  x: number; y: number        // 世界坐标(Frame 左上角)
  w: number; h: number
  collapsed: boolean
  nodes: CanvasNode[]         // 成员节点
}

interface CanvasNode {
  id: string
  leafId: string            // ← 引用共享 leaf(与 split 树同一份)→ 终端不重挂载
  x: number; y: number    // 相对 Frame 局部坐标(Frame 拖动时无需改)
  w: number; h: number
}

interface CanvasShape {
  id: string
  type: 'rect' | 'arrow' | 'sticky'
  x: number; y: number; w: number; h: number   // 世界坐标
  text?: string; color?: string
}
为什么 node 坐标是"相对 Frame"而非世界坐标:Frame 拖动/折叠时,成员节点应整体跟随。存局部坐标后,Frame 移动只改 frame.x/y,节点世界坐标 = frame + node 实时算出,天然联动、绝不脱节(对齐原型 body.appendChild(nodeEl) 的相对定位语义)。

leaf 池:如何"共享"

现有 leaf 存在各 tab.root 树里。canvas node 通过 leafId 引用它们。新增一个纯查找工具,跨所有 tab 收集 leaf:

// 跨全部 tab 找 leaf —— canvas 与 split 共用的解引用
const allLeaves = tabs.flatMap(t => collectLeaves(t.root))
const leafById = (id) => allLeaves.find(l => l.id === id)

seedCanvas()                               // 把每个项目的全部 leaf 按项目铺成 Frame + 网格节点

05最硬的三个技术点

其余都是标准 2D 变换。真正需要设计权衡的只有这三点。

难点 A · 跨模式 / 平移缩放,xterm 绝不能重挂载 —— 双层渲染

React 里只要 PaneView 的父 DOM 变(分屏容器 → 画布 frame),就会卸载重建。原型把节点嵌进 frame 里,真实实现不能照抄。

对策:装饰层 + 活内容层,双层叠加,共用同一视口变换。

.workspace // 全局工作区,始终挂载 ├─ .canvas-stage (装饰层, 仅 viewMode==='canvas') │ └─ .world { transform: translate+scale } │ ├─ Frame 卡片 // 边框/标题栏/计数/折叠/resize 手柄 — 死内容 │ ├─ 空 Frame 提示、Shape(矩形/箭头/便签)、点阵背景 │ └─ 位图缩放无所谓(无活终端) │ └─ .pane-layer (活内容层, 始终存在, 永不换父) └─ allLeaves.map(leaf => <PaneView key={leaf.id} rect={rectFor(leaf)} />) // ← key 不变 → 不断连 rectFor(leaf) 按全局 viewMode 决定像素矩形 + 可见性: split : 属激活 tab → computeLayout(百分比→像素);其余 leaf → display:none canvas: 被某 node 引用 → worldToScreen(frame+node);未引用 → display:none

PaneView 恒在 .pane-layer、父不变、key=leaf.id 不变 → React 走 update 而非 remount。Frame 拖动/折叠/resize 只是重算成员节点的 rect(纯坐标,不触碰 DOM 挂载)。两层用同一 viewport 保证像素对齐:装饰层靠 world 的 transform,活内容层靠每个 PaneView 的 left/top/w/h + scale。

代价Frame 与其成员节点的坐标联动、装饰层与活内容层的对齐,都需在一处封装(见 §6),别让坐标散落。

难点 B · 缩放时终端文字的清晰度

整体缩放若用 CSS scale(),xterm 的 canvas 会被位图拉伸,放大时文字发虚。只影响终端节点——code/image/md/web 是 DOM 文本,CSS scale 下始终清晰。

  • MVP:活内容层每个 PaneView 用 transform: scale(vp.scale)。缩小看全局时位图缩放完全可接受;≈100% 时本就清晰。先能用。
  • 进阶(聚焦真渲):双击节点进入"聚焦"→ 该节点 scale=1 真实像素渲染 + 对 xterm fit() 真 resize,文字锐利。失焦回位图缩放。
  • 阈值优化:scale∈[0.9,1.1] 时对可见终端做一次真实 fit,常用区间始终清晰。
难点 C · HTML 网页预览器 —— 必须 iframe,不能 BrowserView

新 PaneKind:'web'。严禁用 Electron BrowserView / WebContentsView:它们是原生叠加层,不受 CSS transform 控制,无法跟随画布缩放/平移/裁剪,会"浮"在画布之上错位。

  • MVP:<iframe sandbox="allow-scripts" referrerpolicy="no-referrer">。用途:预览 docs 里的 HTML 报告(srcdoc 或 file://)+ 嵌 dev server(localhost:5173)实时预览。
  • 进阶(可选):需要跨域/持久会话时改 <webview>(仍是 DOM,受 transform 控制),但要开 webviewTag 且承担其不稳定性,非 MVP。

06坐标数学(封装在一处)

// viewport = {x, y, scale}
const worldToScreen = (wx, wy, vp) => ({ x: wx*vp.scale + vp.x, y: wy*vp.scale + vp.y })

// 节点世界坐标 = Frame + 节点局部坐标;再转屏幕 + 乘 scale 得像素 rect
function rectForNode(frame, node, vp) {
  const wx = frame.x + node.x, wy = frame.y + node.y
  const p = worldToScreen(wx, wy, vp)
  return { left: p.x, top: p.y, w: node.w*vp.scale, h: node.h*vp.scale, scale: vp.scale }
}

// 屏幕 → 世界(拖拽落点、右键新建定位)
const screenToWorld = (sx, sy, vp) => ({ x: (sx-vp.x)/vp.scale, y: (sy-vp.y)/vp.scale })

// 滚轮缩放以光标为锚点,保持指针下世界点不动
const zoomAt = (px, py, factor, vp) => {
  const s2 = clamp(vp.scale*factor, 0.2, 2.2)
  return { x: px-(px-vp.x)*(s2/vp.scale), y: py-(py-vp.y)*(s2/vp.scale), scale: s2 }
}

09技术选型评审团

按完成性 / 体验 / Token-包体 / 风险四维评审。结论——自研。

方案完成性体验(不断连&设计一致)Token/包体风险
自研画布 选它 高 复用 PaneView/leaf/action 最佳 双层渲染 100% 复用不断连基建 + 直套 base.css 零依赖 引擎+抽屉+图形 ≈1200 行 中 双层对齐 + 缩放清晰度需自理
react-flow 中 差 它托管节点 DOM,活 xterm 塞进去要跟其渲染周期对抗 +~50KB 高 与"同容器不重挂载"哲学冲突

为什么第三方库反而更难:它们都自己托管节点的挂载/卸载,而本项目命脉是"xterm 永不重挂载"。让外部库配合这条约束,比自研一个契合现有架构的轻画布更费劲、更脆,且视觉难对齐毛玻璃令牌。

11风险与对策

R1 · 统一渲染层重构回归分屏

P0 第一优先级是"split 行为零改变"。做法:先抽出 pane-layer 让 split 走它、canvas 为空,确认分屏无回归后再填 canvas。分两步提交,便于二分回退。

R2 · 终端缩放发虚

难点B 分层解:MVP 位图 + 聚焦真渲 + 常用区间自动 fit。非阻塞。

R3 · 多终端 × 画布重绘性能

非聚焦终端降帧/暂停 rAF(呼应已做的写入合并);视口外节点 content-visibility:auto 或只留占位卡。

R4 · 状态复杂度 / 坐标散落

canvas 独立成 canvasSlice,action 收敛;世界↔屏幕变换只在 §6 一处封装。

R5 · iframe 安全

sandbox 最小授权(allow-scripts,按需加 allow-same-origin);不放开 allow-top-navigation;遵守项目沙箱红线,不绕过安全规则。
