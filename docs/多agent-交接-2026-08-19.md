### 🔴 P0 · `finishBatch` 从不在成功路径调用 —— 派一批就锁死一个 Frame

**这是当前最要命的一条,已经在真实使用中触发了。**

`mcpHandler.ts` 里 `finishBatch(where.frameId)` **只在「起到一半失败」的 catch 里**调；
成功 return 那条路不调。`batchRequest.ts` 的 `running` Set 于是永久记着这个 frameId。

后果：**这个 Frame 再也派不了活**，`askForBatch` 会在弹窗之前就抛
「这个项目已经有一批 agent 在跑了」，而它提示的补救动作（去面板里停掉）
跟这个闸门**根本没接线** —— `TeamPanel` 的停按钮走 `agentChat.stop`，
不碰 `batchRequest`。唯一出路是重启 app。

**修法**：两处都要接
1. `TeamPanel` 停掉某个会话时，如果这个 Frame 上已经没有 owner:'team' 的活会话了 → 调 `finishBatch(frameId)`
2. 或者更彻底：`running` 不再自己维护一份状态，改成**现算**——「这个 Frame 上还有没有 owner:'team' 且 alive 的会话」。那样它不可能和现实脱节

我倾向第 2 个。自己维护一份「谁在跑」的状态，就一定会有忘记清的路径。

### 🔴 P0 · 渲染层那条 9 分钟超时是死代码

`batchRequest.ts` 的超时守卫写成了：

```ts
if (pending?.resolve !== resolve) return   // ← 恒为 true，永远从这儿返回
```

`pending.resolve` 存的是**包装闭包**，`resolve` 是 Promise 的原始 resolve，
两者永远不是同一个引用。cross-checker 用 `mock.timers` 把时钟推过 9 分钟实测确认：
定时器回调跑了、`pending` 还在、比较是 false，**直接 return，什么都没做**。

**修法**：守卫比一个稳定的身份，不要比 resolve

```ts
let timer: ReturnType<typeof setTimeout>
const mine = { req, resolve: (d) => { clearTimeout(timer); resolve(d) } }
timer = setTimeout(() => { if (pending !== mine) return; /* … */ }, WAIT_MS)
pending = mine
```

**并且把那条实测收进 `batchRequest.test.ts`** —— 现有 7 条全在状态机层，
没有一条碰超时，所以这个 bug 才能带着「711 全过」的提交信息进来。

### 🟡 P1 · 真正最短的一道闸在第三层，只有 5 分钟

`mcpBridge.ts` 的注释把链路当成两层，实际是**三层**，而最外面那层最短：

| 层 | 位置 | 上限 | 实际 |
|---|---|---|---|
| ① MCP shim | `mcp/eas-mcp.mjs` 的裸 `fetch` | **300 秒** | undici 默认 headersTimeout，**最先炸** |
| ② 渲染层 | `batchRequest.ts` `WAIT_MS` | 9 分钟（名义） | 永不触发（上一条） |
| ③ 主进程 | `mcpBridge.ts` `WAITS_FOR_HUMAN` | 10 分钟 | 会触发但太晚 |

所以「清单能等 10 分钟」是假的，实际 5 分钟。
**修法**：给 shim 那个 fetch 显式设更长的 timeout（或 `AbortSignal.timeout`），
并在 `mcpBridge.ts` 那段注释里把三层都写上 —— 那段注释现在是错的。

真机验证抓到四件事，其中三件是我写错的：

3. **「删工作树不丢改动」是错的** —— 分支只指向建树时的 HEAD，agent 干完多半没 commit，

   而 `teamFindings` 查主工作区，E-13 对隔离角色整个失效。
   改成**产出落主工作区（绝对路径）、改动留工作树**

**仍然挡不住语义冲突**（两个 agent 各自实现出不兼容的接口）—— worktree 只解决文件层面。

## 六、第二轮（2026-08-19 下午）：真机验证抓到的连带 P0

第一轮修完之后装 0.4.34 做验证，四项全过。顺手把「关节点不杀进程」也验了 ——
纪律成立（进程确实还在跑），**但它暴露出身份存错了层**。

### 已修 · 身份存在视图层，关掉节点面板就不认识它了

`role` / `owner` 一直只存在渲染层的 `pane` 上。而「关节点不杀进程」把节点和进程的
生命周期拆开了，于是关掉节点那一刻：角色名退回 CLI 名、`teamRows` 不再认它导致
「全部叫停」计数从 2 掉到 1（**静默地把它漏在后台烧 token**）、`team_status` 完全看不见。

修法是把身份挪进主进程 `SessionRecord`，随 `SessionBrief` 下发。
`isTeamOwnedCaller` 有同一个 bug（notify 拦截和派活硬约束都靠它），一起改了。

**这条的教训比修法值钱**：面板还在 ≠ 面板管得着。纪律第 4 条说的
「关节点不杀进程必须与面板能停同时成立」，被一个谁都没想到的路径绕过去了。

### 已修 · 时长那一列的语义（用户截图指出）

那列显示 `now - lastActiveAt`，即「多久没动静」。而 `lastActiveAt` 每收到一块 stdout
就续期，**对活跃会话恒趋近 0** —— 给在跑的行显示它没有任何信息量，还会被读成
「跑了 0 秒」。加了 `startedAt`，在跑的行改显示已运行时长。

### 已修 · 分不清「卡死」和「干完了」

`invariant-auditor` 写完 findings 后静默 13 分钟，面板报「可能卡住」，实际早交活了 ——
headless 流式模式跑完一轮**不退出**，它和真卡住的进程在静默上完全一样。

主进程其实知道（`turn.start`/`turn.done`），只是从没往上送。记进 `SessionRecord.busy`。
面板据此把团队 agent 的 idle 显示成「已交活」（你自己开的对话仍是「空闲」）。

### 已修 · 主 agent 收不到完成信号

用户指出的：agent 干完了我这边没反应。查下来那条链上**没有任何完成信号会回到主
agent 手里** —— 工具描述明写「别轮询」，又没有推送，等于让它靠猜。
实测这次 agent 07:38 写完，主 agent 到 07:51 被用户提醒才去查，中间 13 分钟空转。

`team_status` 加了 `wait:true`：挂到有人交活才返回，8 分钟，一次调用一次返回。
排在三层超时链路最里层，`WAITS_FOR_HUMAN` 因此改名 `LONG_WAITS`（等的不一定是人）。

### 已加 · 团队成员不能再派活（硬约束）

用户要的。**不靠 prompt** —— 失败模式是指数级的（每人再派 3 个，两层 9 个独立进程），
而限流闸按 Frame 现算，一批快跑完时最后一个成员派新的一批正好穿过去。
`mcpHandler` 里硬拦，简报里也提前告知一遍（只拦不说的话 agent 会白试一次再想办法绕）。

### 已加 · 派活简报补上工作纪律

原来只有四行（你是谁 / 目标 / 任务 / 产出写哪）。参考 CCteam 的 onboarding 模板补上
2-Action Rule、结论三要素（判据/证据/**边界**）、3-Strike、BLOCKED 出口、定期自检。
**只搬得动的那部分** —— 它那套「先确认再开工」「完成汇报发 SendMessage」全靠双向
消息通道，我们没有，对应改成落盘。内容在 `features/team/brief.ts`，有单测。

  交活后显示「已交活」、关节点后角色名和叫停计数不掉、`wait:true` 真的挂得住、
  团队 agent 调 `team_spawn` 被拒、新简报生效

### 教训（比修法值钱的那几条）

1. **面板还在 ≠ 面板管得着** —— 纪律说「关节点不杀进程必须与面板能停同时成立」，

3. **单测测不到连起来的那一段**：分发链三环、id 三层，各段单独看都对。
   花名册那块补了 `.e2e.test.mjs`（真建目录、真写文件、真读回来）
4. **管道会吃掉退出码**：`npm run dist | tail -5` 的退出码是 tail 的，永远 0。
   打包失败被报成 completed，只有末尾几行堆栈露馅
