灵动岛状态栏

Eas-Term 不在前台时，屏幕顶部常驻一条状态胶囊：折叠时只说「有几个在跑」， agent 要你审批或答完了就展开成卡片，能当场处理，也能一键跳回那个 session。

日期 2026-08-02 基线 v0.3.3 已定决策 3 条 待你确认 4 条

VERDICT

结论：独立常驻窗口，分三期，第一期两天可用

地基比预想的厚——「谁在跑」「谁需要处理」「跳回 session」这三件事画布里已经有了， 搬到窗外即可。真正要新造的只有三样：常驻窗口、耗时统计、审批解析。

推荐方案

主进程新开一个 无边框 always-on-top BrowserWindow（src/main/island.ts）， 独立 HTML 入口，不复用主窗口渲染树。主进程持一份状态聚合器，渲染层把 runningPtys / attentionPtys / 会话元信息推给它，它再广播给灵动岛。 点击操作反向走 IPC 回主窗口执行（聚焦 / 写 pty）。

口径提醒

「单次会话总耗时」我按两个值做：卡片主显本轮耗时（这次提问到答完， 对「它想了多久」最有信息量），副显会话累计（这个终端起会话至今）。如果你只要一个，说一声去掉哪个。

Codex 会话拿不到 transcript——session.ts 只解析 Claude Code 的 jsonl。 Codex 终端的卡片会降级成「项目名 + 状态 + 耗时」，没有提问梗概和回答正文。要补的话是独立一期的活。

ARCHITECTURE

架构选型：三个方案

核心矛盾是「状态在渲染进程的 zustand 里，而窗口要在主进程开」。三个方案的差别就在这条线怎么划。

方案做法优势代价结论
A. 独立窗口 新建无边框 always-on-top 窗口，独立 HTML 入口，主进程做状态中转 形态就是你要的灵动岛；主窗口最小化也活着；不受主窗口渲染树影响 要写窗口生命周期 + 一套双向 IPC；多一个渲染进程（约 30–50MB） 推荐
B. 菜单栏 Tray 系统托盘图标 + 下拉面板 最省事，系统原生，零窗口管理 不是灵动岛——没有屏幕顶部居中的胶囊形态，弹窗样式受系统菜单限制，审批按钮做不出你要的视觉 否决
C. 主窗口迷你模式 把主窗口缩成一条贴顶部，切换尺寸 复用现有渲染树，零新窗口，状态天然同步 主窗口一旦最小化就没了——而这功能存在的前提正是「你切走了」。自相矛盾 否决

视觉硬约束

  • 整块用毛玻璃底 + 1px 边框，圆角 16px（折叠态 999px 全圆）——形态上和系统灵动岛同源
  • 折叠↔展开只做高度和透明度过渡（220ms），不做位移弹跳——顶部是常驻区，跳动很烦
  • 一张卡片只出现一个语义色；同时来多条通知时按队列一次显示一条，右上角标 1/3
  • 整个窗口不可拖动、不进 Dock、不抢焦点（focusable:false + 点击时才临时接管）

APPROVAL

审批直通：怎么认，怎么兜底

这是全案唯一的高风险点。核心思路：宁可认不出退回通知，也绝不认错了替你按。

识别流程

标题 spinner 停下 ──► 读 xterm buffer 末 20 行
                          │
                          ├─ 命中「? 问句 + 连续编号选项」──► 审批类：列出选项，常驻
                          ├─ 命中裸问句无选项          ──► 输入类：只通知，点击跳转
                          └─ 都不命中                  ──► 完成类：读 transcript 取回答，8 秒收

写回：点「允许」= pty.write("1\r")。按选项的序号写，不按文案猜语义。
失效自检：写回后 1.5 秒内 spinner 没重新转起来 → 判定写回没生效，
        卡片自动切回「点击跳转到终端」，并在日志里留一条解析失败样本。
保留的分歧

我对「在灵动岛点允许」这件事本身有保留意见，但按你的决定实现。 理由：审批框弹出来是因为 agent 要做有副作用的事（删文件、改配置、发网络请求）， 而灵动岛卡片受宽度所限，只能显示命令的前一行。「rm -rf node_modules」和 「rm -rf ~/Documents」在截断后可能长得一样。

→ 缓解措施（已计入 P2）：命令正文不截断显示，超长时卡片自动加高到 3 行； 识别到 rm -rf / sudo / curl … | sh 这类模式时，禁用直通按钮， 强制「跳回终端处理」。要不要这条你在决策码里说。

REVIEW PANEL

评审团：四个视角

按你习惯的维度各打一遍，分歧原样保留。

完成性 8/10

你描述的能力全部可实现。扣分在 Codex 会话的元信息缺失—— 那不是设计问题，是 Codex 本身没留 transcript，得等它出结构化输出或者自己录屏解析。

体验 9/10

「不在前台就出现」这条选得对——它让这个模块从「偶尔用上」变成「每天都在」。 扣分在多通知队列：三个项目同时答完时，一次只显示一条会有等待感。

实现成本 中

约 850 行新代码 + 5 个新文件。P1（窗口 + 折叠态 + 完成通知 + 跳转） 是大头也是最稳的部分；审批解析虽只 90 行，但调试要反复触发真实审批框，耗时不成比例。

长期风险 需盯

审批解析依赖 claude/codex 的 TUI 样式，属于「今天能跑、明年可能悄悄坏」的代码。 必须配失效自检（写回没反应就自动降级），否则就是你最烦的那种「测试好使、过段时间又坏」。

RISKS

风险与对策

按「会不会咬人」排序，前三条是真会出事的。

风险后果对策
审批框解析失效
高		CLI 升级换了框样式，按钮点了没反应写回后 1.5s 自检 spinner；没转起来就降级成「跳回终端」并记日志
transcript 串会话
高		同项目开两个终端，卡片显示的是另一个终端的回答按节点绑的 sessionId 定位 jsonl，不再用「cwd 下最近修改」
常驻窗口耗电
中		多一个渲染进程长期挂着没有任务在跑时销毁窗口而非隐藏；有任务才创建。空闲态零成本
刘海机型遮挡
已实测		在有刘海的 Mac 上，居中贴顶会被刘海吃掉中间一截最终做法与此处原写的不同。原方案「下移到刘海下沿」实测是错的——那样就成了一条悬在菜单栏下面的普通通知条，失掉贴边的形态感。改为：窗口贴屏幕物理上沿（enableLargerThanScreen + roundedCorners:false，否则 macOS 会把它顶回菜单栏下方、并给四角抹圆露出壁纸），画一整块不透明纯黑覆盖刘海区，文字分居两侧不放中间。中间不留透明缝——试过，缝里露的是壁纸，整条断成两截；且截屏分析证实屏幕顶部一行纯黑像素都没有，刘海位置根本无从对齐。
抢焦点
中		弹卡片时打断你在别的 app 里打字focusable:false + setVisibleOnAllWorkspaces；只在点击瞬间临时取得焦点
全屏应用之上
低		你在全屏的编辑器里，灵动岛看不见screen-saver 层级 + visibleOnFullScreen；实测确认，做不到就如实说
