Verdict

结论：插件与 harness 之间只有一种通用语言，界面走 MCP Apps，Eas-Term 做宿主

四个数字先把盘子说清楚，再给裁决。

3
已接入的 harness（Claude Code / Codex / omp），三家配置格式各不相同
1
三家的交集：MCP。skills / hooks / 清单格式都不通用
0
现有生态里带可渲染 UI 的插件数（2026-08-24 实测，两家都是 0）
34
Eas-Term 自己已通过 MCP 暴露的工具数——它本身就是一个「插件」的样板
核心裁决

① 插件 ↔ harness 的通信协议就是 MCP，不要另起一套。三个 harness 唯一都认的东西就是 MCP server（stdio / http）。你写的插件只要是一个标准 MCP server，Claude Code、Codex、omp、以及任何未来的 harness 都能连——Eas-Term 已经在替你把它写进三家各自的配置格式里。

② 界面协议采用 MCP Apps（MCP 的官方 UI 扩展）：工具声明一个 ui:// 资源，宿主取出 HTML 放进沙箱 iframe，双方用 postMessage 上的 JSON-RPC 对话。这样你的插件前端不只在 Eas-Term 里能显示，在任何实现了 MCP Apps 的宿主里都能显示；反过来，Eas-Term 实现了宿主侧，别人按这个标准写的插件面板也能渲染进我们的画布。

③ Eas-Term 的角色：宿主 + 枢纽。画布上的「插件模块」= 一个新的画布组件 plugin-panel，内容是插件的 UI 资源；面板通过宿主拿到 Frame 上下文（cwd / 项目 / 节点）并可调用插件自己的工具与画布工具；harness 侧的工具调用结果通过宿主推给面板。面板永远不直接碰 harness——harness 只说 MCP，这条边界不破。

保留的分歧 · 先说清楚

第三方现成插件（Linear / GitHub 这类）不会因此长出界面。它们没有 UI 资源，Codex 连接器型插件甚至本地一个字节都没有，指向的是 ChatGPT 托管的界面。这套协议解决的是「你自己写的插件带界面并跨 harness」，以及「别人按 MCP Apps 写的插件进我们画布」。对存量第三方插件维持 L1+L2（会话预设 + 工具面）。

OpenAI Apps SDK（window.openai）是另一套，与 MCP Apps 不兼容。ChatGPT 里的插件界面走它。要不要再做一个兼容层是第二期的事，本报告不建议一期就做。

Current State

现状：插件现在是怎么和 harness 通信的

两条链路。一条是 Eas-Term 自己作为「插件」被 harness 调用，一条是第三方插件的工具被合并进会话。都是 MCP。

链路 A · harness → Eas-Term（画布 34 个工具是这么暴露的）

// 每个会话一个轻量 shim 进程，共享同一个 HTTP 网关（每 App 实例一个）

现状的天花板

插件在画布上没有自己的模块——「插进画布」实际是开了一个带着它工具的对话节点。原因不是我们没做，是插件里一行 UI 代码都没有。带 Web 界面的（如 ChatCut）走的是 canvas_open_url 开成网页节点，那是一个完整的外部网页，不是插件面板，和 Eas-Term 之间没有任何通信。

Why MCP

为什么「任意 harness 互通」只能建立在 MCP 上

把三家的扩展点摆在一起，交集一眼可见。

扩展点Claude CodeCodexomp（ACP）通用？
工具MCP（~/.claude.json / --mcp-config）MCP（config.toml [mcp_servers.*]）MCP（session/new 传名单，仅 stdio）是
提示词 / skillskills/ commands/ agents/skills/、AGENTS.md无对应否
行为钩子hooks/（Pre/PostToolUse）hooks.json（形状不同）无否
插件清单.claude-plugin/plugin.json（只有 name/description/author）.codex-plugin/plugin.json（有 interface 块：图标/品牌色/默认提示词）无插件概念否
界面无.app.json 远程 app id（ChatGPT 托管）无否
会话上下文（cwd / 项目）PTY 环境变量（我们注入）同左同左（omp 由我们起进程）我们能保证

所以协议分两层：工具层用 MCP（三家都认，零适配）；界面层不能指望 harness——harness 根本不渲染任何东西，界面只能由宿主（Eas-Term、Claude.ai、VS Code 这类有屏幕的程序）来画。而宿主之间要通用，就需要一个宿主侧的标准——这正是 MCP Apps 的定位。

MCP Apps 一句话

MCP 的官方扩展（SEP-1865，spec 2025-11 起，SDK 包 @modelcontextprotocol/ext-apps）：MCP server 的工具在 _meta.ui.resourceUri 里指向一个 ui:// 资源；宿主通过 resources/read 取到 HTML，放进沙箱 iframe；iframe 与宿主之间用 postMessage 承载 JSON-RPC——面板可以反过来 tools/call 自己 server 的工具，宿主把工具结果通过 ui/notifications/tool-result 推给面板。Claude.ai、VS Code Copilot、Goose 等已按它做宿主。

Protocol

协议设计：三层，两层是标准，一层是我们的可选扩展

原则：标准能覆盖的一律用标准，Eas-Term 特有的能力放在 _meta.eas.* 命名空间里，别的宿主看不懂就忽略，不影响插件在那里运行。

层 1 · 工具层（MCP，标准）

插件 = 一个 MCP server。stdio 优先（三家都吃；omp 只吃 stdio）。这一层今天已经通：写好 server，放进 Eas-Term 的插件目录，agentMcpConfigPath 就会把它合并进三家的会话。

层 2 · 界面层（MCP Apps，标准）

// tools/list 里的一个工具
{
  "name": "board_show",
  "description": "打开看板面板",
  "inputSchema": { "type": "object", "properties": { "projectId": { "type": "string" } } },
  "_meta": { "ui": { "resourceUri": "ui://my-plugin/board.html" } }   ← 面板入口
}

// resources/read ui://my-plugin/board.html → 一份 standalone HTML（内联 JS/CSS）
// 宿主把它放进 sandbox iframe，之后双方用 postMessage 上的 JSON-RPC：
面板 → 宿主   ui/initialize                 握手，宿主回能力集与主题
面板 → 宿主   tools/call { name, arguments } 面板调自己 server 的工具（宿主代转，可拒）
宿主 → 面板   ui/notifications/tool-result  模型那边调了工具，结果推给面板刷新
宿主 → 面板   ui/notifications/theme        明暗 / 尺寸变化

这一层让面板不需要知道自己在哪个宿主里。同一份 board.html 在 Eas-Term 画布里、在 Claude.ai 里、在 VS Code 里都能显示。

层 3 · 宿主扩展（Eas-Term 特有，可选）

标准没有「画布」的概念。Eas-Term 在握手时多给一份上下文，并多开几条方法——全部挂在 eas/* 前缀，插件按需用：

方法 / 字段方向给什么为什么要有
ui/initialize 返回值里的 _meta.eas.context宿主 → 面板{ frameId, nodeId, projectId, cwd }和现在 CanvasComponentCtx 一模一样的形状。画布是多项目并置的，面板必须知道自己挂在哪个 Frame——不许自己去猜「当前项目」（组件协议已定的纪律）
eas/canvas.call面板 → 宿主透传画布工具：canvas_open_file / open_url / add_note …面板里点一条结果 → 在旁边开文件。走现有 mcpHandler，同一套路径白名单，不新开口子
eas/session.events（订阅）宿主 → 面板绑定会话的 turn 开始/结束、工具调用面板可以跟着对话进度刷新，而不是靠轮询
eas/panel.resize面板 → 宿主请求节点尺寸画布节点有默认尺寸，面板知道自己需要多大

插件包的形状（Eas-Term 插件目录）

~/.eas/plugins/<name>/
  plugin.json          ← 我们的清单（超集：兼容 Codex interface 块的字段名，好复用现有 UI）
  .mcp.json            ← 和 Claude / Codex 插件同形，写法不用学新的
  server/              ← MCP server 本体（node / python / 任意，能 stdio 就行）
  ui/board.html        ← ui:// 资源；也可由 server 动态生成

// plugin.json
{
  "name": "my-board",
  "displayName": "看板", "brandColor": "#5E6AD2", "composerIcon": "./ui/icon.svg",   ← 借 Codex 的字段名
  "defaultPrompt": "看看这个项目的待办",
  "panels": [ { "id": "board", "tool": "board_show", "defaultSize": { "w": 420, "h": 320 } } ],   ← 哪个工具开哪个面板
  "permissions": { "canvas": ["open_file","add_note"], "fs": "project" }   ← 层 3 的权限声明，宿主按此放行
}

跨 harness 怎么发布：同一个包，Eas-Term 一键「导出为 Claude 插件 / Codex 插件」——各生成对应的 .claude-plugin/plugin.json 或 .codex-plugin/plugin.json，.mcp.json 原样带走，ui/ 一并打包（那两家不渲染它，但也不碍事；到了 Claude.ai 这类 MCP Apps 宿主就能显示）。不写「一份清单三家通吃」——三家格式不同，导出是最不撒谎的做法。

Host Side

Eas-Term 做宿主：面板怎样被读到、渲染进画布上的插件模块

复用三样现成的东西：画布组件协议（外壳）、mcpBridge 网关（通信）、webview/iframe（渲染）。新增的只有一个组件和一条转发路径。

用户在 Frame 双击菜单点「看板」插件
  │
  ▼
addComponentNode(frameId, { type: 'plugin-panel', props: { pluginId, panelId } })   ← 复用组件节点，不新造节点类型
  │
  ▼
PluginPanel（新画布组件，render(ctx) 里）
  1. 主进程 plugin:openPanel → 起/复用该插件的 MCP server（stdio，同 shim 的方式）
  2. resources/read ui://… 取 HTML                       主进程做，渲染层不直接碰插件进程
  3. 放进 sandbox iframe（srcdoc，sandbox="allow-scripts"，不给 allow-same-origin）
  4. postMessage 桥：iframe ⇄ PluginPanel ⇄ IPC ⇄ 主进程 ⇄ 插件 server
     · ui/initialize 回 { capabilities, theme, _meta.eas.context: ctx }       ctx 就是 CanvasComponentCtx
     · tools/call 经主进程转给插件 server；eas/canvas.call 转给 mcpHandler（同一套白名单）
  5. 绑定会话里模型调了该插件的工具 → 主进程收到结果 → 推 ui/notifications/tool-result 给面板

为什么用 iframe 而不是 <webview>

网页节点用的是 Electron <webview>（独立进程、完整导航），它的代价是「永远浮在普通 DOM 之上、压不住」（CanvasFileNode.tsx 有记录）。插件面板是一份我们自己取来的 HTML，不需要导航，sandbox iframe 够用且能被画布正常叠放。第三方 HTML 进渲染层的安全靠 sandbox 属性 + CSP，不靠进程隔离。

为什么 resources/read 在主进程做

插件 server 是子进程，渲染层本来就不该直接持有子进程句柄（现有 shim 也是主进程管）。而且 HTML 落到渲染层前可以在主进程过一遍 CSP 注入和尺寸上限，跟 dict.ts 的 SVG sanitize 是同一个思路：能在进渲染层之前做的检查，就在之前做。

复用组件协议时的一处必要改动

CANVAS_COMPONENTS 是编译期数组，插件是运行时发现的。不要把插件 push 进那个数组——只注册一个 plugin-panel 组件，插件身份放在 props 里。这样组件协议一个字不改，旧画布里的节点也不受影响（component.type 一旦发布不能改名的纪律仍然成立）。

与现有纪律的对齐

  • 只读用户的插件目录、绝不代装——延续 plugins.ts 的规矩；~/.eas/plugins/ 是我们自己的目录，写入只发生在「导出」那一步且目标由用户选
  • 一次会话只带一个点选的插件——面板打开不改变这条；面板和会话是两回事，面板可以独立存在
  • 图纸同 commit 更新：11（MCP 网络图加 pluginHost 一支）、13（所有权矩阵加 pluginHost / PluginPanel）、10（模块领地图）
  • eas-term 自己的 34 个工具也可以带 _meta.ui——比如 team_status 开一块团队面板。这意味着 Eas-Term 的能力也能以面板形式出现在别的宿主里，但那是顺带的好处，不是一期目标

Risks

风险与未决问题

前两条影响方案形状，动手前定；后面的是实现期处理。

安全 · 第三方 HTML 进渲染层

这是本方案唯一新增的攻击面。硬规矩：iframe sandbox="allow-scripts" 且不给 allow-same-origin（否则它能读父页面）；主进程注入 CSP（default-src 'none'; script-src 'unsafe-inline'; img-src data:，不许外连）；postMessage 桥只接受白名单方法，eas/canvas.call 只透传已在 mcpHandler 白名单里的工具与路径；HTML 尺寸上限（同 SVG 的 8000 字符思路，面板可放宽到 512KB）。这些不是可选项，是一期验收项。

标准仍在演进

MCP Apps 的方法名与 _meta 键在 2025-11 后仍可能调整。做法：桥的方法名集中在一个纯函数模块（appsProtocol.ts，有单测）里映射，spec 变了改一处；不要把方法名散在组件和主进程两边——这是 LONG_WAITS 两处必须一致那类坑的翻版，提前避开。

进程与内存

每个插件 server 是一个进程；面板打开与会话绑定分别会起它——要按插件复用同一个进程（主进程持有句柄，引用计数），否则一个插件在画布上放三块面板再加一个会话就是四个进程。bizone-canvas 每会话 93MB 的教训在前。

要你定的
  • 一期只做「我们目录里的插件」还是直接做三期的泛化（任何 MCP Apps server）？建议一期收窄，先把沙箱和桥打磨对。
  • 面板与会话的关系：面板能否不绑会话独立存在？建议能——看板本来就不该依赖一次对话。
  • 示例插件做什么：看板 / 项目待办 / 甘特图里程碑详情？选一个你天天会用的，样板才有人维护。
