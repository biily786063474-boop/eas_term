# 插件独立发布链（开发分支，尚未线上执行）

## 范围与证据

宿主不需要重新构建即可生成并上传两个目录和不可变版本包。当前正式客户端仍读取 v1；v2 URL 切换、真实网络/CDN、客户端安装更新端到端另行验收，不能把此脚本通过等同全部插件已接入。

`src/main/pluginPublish.test.mjs` 在临时文件系统执行生产适配器生成的真实 POSIX 命令；只替换 SSH/SCP 进程边界，不连接生产机。覆盖成功/重复发布、同版本冲突、损坏上传、已占用锁、源文件校验/规范 URL/旧客户端兼容隔离、显式发布开关、可读权限、第二目录切换失败。POSIX 演练在 macOS 执行，Windows 跳过这些 shell 测试。Node CLI 防误触测试仍执行。

## 手动发布入口（需独立授权）

1. 先按服务器索引读取目标机器档案，核对当前服务状态与目录所有权。目标根目录必须已存在且不是符号链接。本流程不 reload 或重启任何服务。
2. `node scripts/build-plugin-registry.mjs`：构建 v1/v2；包有变更必须升级版本，不能覆盖同名版本 zip。
3. 审查目录内容与来源许可、包权限、版本、兼容要求。当前默认构建为看板/番茄钟及本地文件（仅v2）；不是32个真实连接器。
4. **得到发布授权后**运行 `bash scripts/publish-plugins.sh --publish`。不带此参数只报用法，不连服务器。支持 `EAS_PLUGIN_OUT_ROOT`、`EAS_PLUGIN_BASE_URL`、`EAS_PLUGIN_PUBLISH_HOST`、`EAS_PLUGIN_PUBLISH_ROOT`；改域名必须同步宿主允许列表。
5. 发布后另行验证公开 HTTPS/CDN 的两个目录正文与逐个包大小/SHA256，打开隔离客户端做刷新、安装/更新和失败回退。脚本成功只证明远端文件晋升，不代表 CDN 或 UI 验收成功。
6. 更新服务器档案变更记录；比对服务状态，不一致按事故处理。

## 写入顺序与恢复边界

- 本地先读取、校验双目录和全部包，保存本次发布的独立字节快照。规范下载地址必须严格对应 `<base>/<name>/<name>-<version>.zip`。
- `mkdir .publish-lock` 互斥，锁内容是当前 release ID。已有锁不会被抢占、删除或自动判断过期。
- 上传前核对所有已存在版本包；同版本不同 SHA256/大小直接停止，旧包不删除。相同内容不重复上传。
- 单文件 SCP 到 `.release-<uuid>`（权限 700），逐个核对大小和 SHA256；全部上传通过后才开始晋升。没有递归 SCP、没有清旧 hash、没有删除旧 zip。
- 版本包通过硬链接独占创建最终路径，已存在即失败，不能覆盖。目录与包晋升前设文件权限 644；新插件目录 755，现有目录权限不修改。
- v2 然后 v1 分别备份旧文件至本次 release 目录，再原子 rename。**这是逐文件原子，不是两份目录的跨文件事务**。第二份失败时 v2 可以是新目录、v1 是旧目录；两者引用的包都保留。
- `.release-<uuid>` 保留旧目录或失败暂存供核对与人工恢复，没有自动垃圾回收。恢复旧目录只应使用已经核对内容的 `previous-registry*.json` 原子替换对应文件；不要删旧包。回滚后再做公开 HTTPS 与隔离客户端验收。
- SSH 超时/断线意味着结果未知：停止，不自动重试上传/替换。先核对锁 owner、release 目录、最终目录 hash/包 hash。可能需要有权限的操作者清理已确认没有活跃发布者的锁，脚本不代做。
- finally 只释放本次已确认取得且 owner 匹配的锁；如果获得锁的 SSH 回复丢失，锁可能保留，刻意不猜测删除。进程被 kill 或磁盘/网络中断也可能留锁/暂存，属于上述人工恢复流程。

## 2026-09-18 已批准路径对齐

构建与发布使用 `/plugins/registry.json`（v1）及 `/plugins/v2/registry.json`（v2），不再产出开发期的 `registry-v2.json`。客户端默认源仍未切换。两个目录同名，暂存分别用 `registry.json` 和 `v2-registry.json` 避免覆盖；备份分别为 `previous-registry.json` 和 `previous-v2-registry.json`。首次发布创建 v2 目录（755），拒绝符号链接；本地构建也拒绝 v2 链接重定向。不删除开发期旧产物，发布前使用独立干净的输出目录。
