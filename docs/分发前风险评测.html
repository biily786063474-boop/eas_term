Verdict

一句话

功能本身没什么大坑，坑在「能不能装上」——现在这个包别人下载后打不开，而且只能在 Apple 芯片上跑。

两个阻塞项

1. Gatekeeper 直接拒绝 —— 实测 spctl -a 返回 rejected， 没有公证 ticket。别人从网上下载 dmg，双击会弹「已损坏，无法打开，您应将它移到废纸篓」。

2. 只打了 arm64 —— Intel Mac 用户完全跑不起来 （node-pty 是原生模块，架构不匹配直接崩）。

Blockers

一、装不上 / 跑不了

这两条不解决，后面的功能再好也轮不到用户体验。

1. 签名：Gatekeeper 拒绝 阻塞

实测结果
spctl -a -vvvrejected
xcrun stapler validatedoes not have a ticket stapled to it（无公证）
签名类型ad-hoc（mac.identity: null，靠 afterPack 钩子自签）

用户会看到什么：从网页/微信/网盘下载的文件带 com.apple.quarantine 属性， 双击弹「"Eas-Term" 已损坏，无法打开」——注意措辞是「已损坏」而不是「无法验证开发者」， 很多人看到会直接扔垃圾桶，不会想到去右键。

三条路，成本递减
  • Apple 开发者账号（$99/年） → Developer ID 签名 + 公证 + stapler。用户双击直接开，零心智负担。要长期分发就走这条。
  • 教用户绕过 → 分发时附一句 xattr -dr com.apple.quarantine /Applications/Eas-Term.app， 或者「右键 → 打开 → 再点打开」。零成本，但每个用户都要过这一关，劝退率不低。
  • 只发给熟人 → 当前状态就够，口头教一次即可。

2. 架构：只有 arm64 阻塞

实测 lipo -archs = arm64，包里的 pty.node 也是 arm64。 Intel Mac（2020 年前的机器）装上直接崩。

修法：package.json 的 mac.target.arch 加 x64， 或者改成 universal。代价是包体翻倍（现在 111MB → 约 220MB），构建时间也翻倍。 取决于你的用户里还有多少 Intel 机器。

会动用户的文件 —— 有一处不一致

这是个真缺陷，一行能修

writeCodexConfig 会先判断 ~/.codex 目录存在才写（没装 Codex 就不碰）； 但 writeClaudeConfig 没有这个判断——用户哪怕从没装过 Claude Code， 启动 app 也会在 home 目录凭空多出一个 ~/.claude.json。 两边行为不一致，而且对不用 AI CLI 的用户来说是莫名其妙的文件。

文件什么时候写有防护吗
~/.claude.json每次启动检查并补写 mcpServers.eas-term 部分
写前备份 + 解析失败跳过，但不判断是否装了 claude
~/.codex/config.toml同上，写 [mcp_servers.eas-term] 好
目录不存在就不写；按行替换保留注释
~/.claude/skills/eas-term/用户点「安装」才写好
~/.codex/AGENTS.md用户点「安装」才写好
标记划段，不碰用户内容

还有一条要知道：卸载 app 后这些配置会残留， eas-term 那条 MCP 指向一个不存在的文件，用户起 claude 会看到一个连接失败的 server。 没有卸载清理机制。

Windows

三、Windows 版基本是未知数

有 GitHub Actions 在构建，但最后一次成功是 2026-07-08——之后 20 天加的所有功能都没在 Windows 上跑过。

功能Windows 上的实际情况判断
浏览器劫持
（open <url>）		整个 shim 机制是 darwin only，Windows 上直接 return null。 终端里 CLI 打开的链接会走系统浏览器，不进画板。失效
退出清场killTree 在 win32 回落到 pty.kill()——只杀 shell， 底下的 claude / 构建进程照样变孤儿。macOS 那套按 tty 清的方案用不了。失效
MCP 桥代码有 win32 分支（runnerFor 回落 Electron），逻辑上应该能跑，但从没验证过。未验证
技能包安装路径用 path.join ✓，但 hasCli 的候选路径写死了 unix 风格 （~/.local/bin、/opt/homebrew/bin），Windows 上只能靠 PATH 兜底。未验证
语音输入WASM 实现，理论上能跑。未验证。未验证
设计模块导出WebCodecs / MediaRecorder，Chromium 自带。理论上没问题。未验证
建议

要么先只发 macOS，Windows 那条线明确标注「暂不支持」； 要么专门跑一轮 Windows 验证再发。现在这个状态发给 Windows 用户， 大概率是「装上了但一半功能怪怪的」，比不发更伤口碑。

Verified OK

四、这些确认没问题

查过了确实没有对本机环境的隐藏依赖。

没有硬编码本机路径

全量 grep /Users/biily，源码里零命中。 唯一出现的是笔纵画板官网域名，那是有意的。

CLI 探测不靠本机 PATH

主进程 GUI 启动时 PATH 很贫瘠， 所以 hasCli / runnerFor 是探常见安装位置而不是 which—— homebrew、/usr/local、~/.local/bin、bun、npm-global 都覆盖了。

语音是 WASM 不是原生模块

sherpa-onnx 走 sherpa-onnx-wasm-nodejs.wasm（20MB）， 跨架构跨平台都能跑。唯一的原生模块是 node-pty。

首次运行有引导

没有项目时侧栏显示「还没有项目，点击 ＋ 选择或新建一个项目文件夹」； 麦克风走系统权限弹窗，NSMicrophoneUsageDescription 已声明。

MCP 不污染 app 外

检测不到 Eas-Term 环境时 tools/list 返回空， 用户在别处起 claude 看不到任何多余工具。

资源随包发

mcp/ 和 skills/ 都在 extraResources 里， 打包后在 Resources 下，路径按 app.isPackaged 分支取。
