建议

分三步走。第一步只动代码（改名、搜索、chip 机制、提示词字段的规格）， 当天就能用上；第二步定分类体系并批量重标；第三步批量补写 242 条提示词。 第二三步都是「模型批量处理数据」，成本可估、可分批、可中断， 不该挡住第一步的交付。

但有一条我不同意照字面做

「用户点击后在输入框中显示的是一个 chip 块」—— 终端里做不到。终端是一条字节流，没有 DOM，插进去的只能是纯文本。

所以 chip 只在 AI 对话的输入框成立；插到终端时仍然是完整提示词的纯文本。 好在这不是妥协：终端那条路本来就是「把提示词交给命令行 agent」，全文反而是对的。

Part 1

① 名词词典 → 辞典

最简单的一件，但有一条边界必须划清楚。

面动不动为什么
界面文案（面板标题、tooltip、设置项、悬浮球）改就是这次要改的东西
提示语里的「词典」（钩子说明、agent 引导）改同上，用户读得到
MCP 工具名 dict_add / dict_pending不改已经写进了用户机器上的 skill 和 AGENTS.md，改了老配置全失效
文件路径 ~/.eas/dict-*.json不改改了等于所有人的自建词条丢失，收益为零
代码标识符 / CSS 类名 dict-*不改内部名，改了只是制造一次大 diff

也就是说：只改用户读得到的字。工作量约 20 处文案替换 + 一次全量搜索确认没有漏网。

Part 2

② 二级分类：按「你想干什么」切，不按「它是什么」切

这一条要你先拍板一级分类，我才能动手重标 381 条。

现在的问题

现在的三类是按技术门类切的：交互行为 / 动效 / UI视觉。 问题是用户找东西时想的不是「这属于哪个门类」，而是「我现在要做一个什么」—— 「列表滚起来卡」「表单要防重复提交」「想要个入场效果」。 按门类切的话，同一个场景的解法散在三类里：做一个「加载中」要同时翻 interaction（骨架屏）、motion（脉冲动画）、visual（占位灰块）。

提议的一级分类（要你确认）

一级 = 场景/意图，二级 = 具体手法。下面是按现有 381 条实际内容归纳的，不是凭空设计。

这一版是提议，不是定案

九个一级分类是我按现有词条归纳的。切法变了，重标就得重来一遍， 所以请先看这九类合不合你的用法，改完再动手。

兼容性怎么处理

  • 词条加 cat1 / cat2 两个新字段，老的 category 保留 —— 自建词条（dict_add 校验 category 落在旧三类里）和已装的 skill 不受影响
  • 界面按新字段展示；没有新字段的词条（比如用户自建的）落到「未分类」，不消失
  • 重标由模型批量做，产出是一份映射表（id → cat1/cat2），人能扫一遍再合并 —— 不直接改 381 条原始数据

Part 4

④ 提示词规格 + chip：这一条最重，也最值

现在 242 条点下去插入的是「解释」，模型拿到那段话不知道要它干什么。

问题有多具体

有 prompt 的（139 条）

「帮我实现一个「入场动画」效果。【外观】内容整块从下方滑入并淡入…… 【实现】GSAP，依赖 gsap。【关键参数】distance=100……【坑】长列表逐项套用会显得拖沓。」

是指令 模型知道要做什么

没有 prompt 的（242 条）

「高频事件触发后延迟 N 毫秒再执行；若期间又触发就重置计时器……典型场景：搜索框联想。」

是解释 模型拿到只会跟你讨论概念

提示词的结构规格（提议）

沿用现有 139 条的骨架并补齐三类都适用的字段。名称 + 实现方法两段式，中位长度控制在 200–350 字：

在{此处}实现「{中文名}」（{英文名}）。

【要达到的效果】 一句话说清用户看到/感受到什么，不解释原理
【触发时机】   什么条件下发生（滚动到视口 / 输入停止 / 点击 / 常驻）
【实现方法】   具体做法：用什么 API、什么结构、分几步
【关键参数】   可调的量和推荐值，带单位
【别踩的坑】   这个效果最常见的做错方式
【可选 · 依赖】     需要装什么库；能用原生就写「无需依赖」
「{此处}」这个占位很关键

你说的「让模型明白某个地方要插入某个效果」—— 提示词开头留一个位置占位，chip 插进对话时它就在你的上下文里， 模型知道是「在你正说的那个地方」加，而不是新起一个 demo。

chip 怎么做

输入框是原生 textarea，里面塞不了 chip。但图片附件已经解决过同一个问题—— .ac-attach-row：输入框上方一行带 ✕ 的小块。chip 直接复用这套。 

┌─────────────────────────────────────────┐
│ [⚡ 防抖 ✕]  [✨ 入场动画 ✕]          ← 复用 .ac-attach-row
├─────────────────────────────────────────┤
│ 帮我把搜索框改一下                        │  ← 你打的字，还是纯 textarea
└─────────────────────────────────────────┘

发送时实际送出：
  帮我把搜索框改一下
  ---
  在上文提到的位置实现「防抖」（Debounce）。【要达到的效果】…
  在上文提到的位置实现「入场动画」（AnimatedContent）。【要达到的效果】…
  • chip 只显示名字，鼠标悬停看全文 —— 满足「输入框里只看到名字」
  • 发送时展开，模型拿到完整提示词 —— 满足「实际发送整个提示词」
  • 可以点 ✕ 撤掉，跟图片附件一致，不用另学一套
  • 终端路径不变：直接写入完整提示词纯文本（终端没有 DOM，见开头那条反对意见）

242 条提示词怎么补

做法成本取舍
模型批量生成（推荐）242 条 × 约 350 字 ≈ 一次几十万 token可分批（按分类，一次 30–50 条），产出先落成草稿文件再人工扫一遍
只补高频的 80 条约三分之一剩下的仍然插解释 —— 用户还是会撞到「这不是提示词」
不补，运行时现生成每次点击都花 token不推荐：点一下等两秒，而且同一条反复付费

Part 5

⑤ 自动沉淀拆掉，改成 skill 驱动

你要求「不要自动去收集了」。但那个钩子实际是两半，只有一半在收集 —— 这个区别不分清会误删。

先分清：scan-commit.mjs 干的是两件事
哪一半干什么花 token 吗这次动它吗
知识手册 扫本次提交新增的代码行，命中已收录的词条 → 写进 docs/knowledge-manual.html + 输出一条简报 零 不动 它不收集新词，只是「这次用到了哪些概念」
自动沉淀 发现没收录的术语 → 记进 ~/.eas/dict-pending.json → agent 事后用 dict_add 补全成完整词条 要 拆掉 这一半才是「自动收集」

为什么拆掉是对的

  • 它猜不准该归哪一类。新分类是二级的、按场景切的 —— 一个从代码里扫出来的英文标识符，机器判不出它属于「加载与等待」还是「反馈与提示」
  • 它产不出 hover 演示。词条要有 SVG 示意图或演示短片，那是这个辞典最有价值的部分。自动补全写不出来，只能给一个占位
  • 它在你没看的时候花钱。默认关着正是因为这条不好交代 —— 与其留一个默认关、开了会偷偷消费的开关，不如让添加这件事变成一次明确的动作

换成什么：一个 skill 走完四步

用户想加一条时主动调它。skill 不自己写词条，它引导补全并在每一步停下来给你确认。

用户：「把『边缘自动滚』收进辞典」

① 定分类   在二级体系里定位 → 提 1-2 个候选让你选
             「列表与滚动 › 拖拽辅助」还是「手势与拖拽 › 边界行为」？

② 补结构   按新数据结构逐字段补：zh / en / keywords / logic
             keywords 要含实际会打出来的写法（edge scroll、边缘滚动、自动滚）

③ 做演示   产出 hover 时看的那张图 —— 这一步不能省
             静态概念 → 内联 SVG；动效 → 短片（走 dict-clip:// 协议）

④ 写提示词 按 ④ 那节的规格写，含「{此处}」占位
             写完当场能被 chip 用

⑤ 收录     调 dict_add 写进 ~/.eas/dict-user.json
             校验通过才落盘，字段缺一不可
这样换的好处

花钱变成一次明确的动作，不再是后台偷偷跑； 分类由你确认，不靠机器猜； 演示图必出，不会再产生「只有名字没有图」的空壳词条 —— 而那正是这条链路上一版就栽过的坑（main/dict.ts 开头记着）。

要拆的零件清单

零件处置
hooks/scan-commit.mjs 里的 sink 那半删掉；手册那半保留
~/.eas/dict-sink.json（开关）不再读；已有文件留着不管，删了反而是动用户的数据
~/.eas/dict-pending.json（候选队列）同上

MCP 工具 dict_add保留 —— 新 skill 的最后一步就调它，只是校验要跟上新数据结构
