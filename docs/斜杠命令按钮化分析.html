斜杠命令按钮化：能做，但绝大多数不该做

把 Claude Code / Codex 的斜杠命令做成一键按钮，技术上没有障碍 —— 现有代码里所有零件都在。 真正的问题是选哪些：132 条命令里，真正配得上一个常驻按钮的只有个位数。

裁决

做，但只做一排 6 个按钮，而且不做成「命令面板」。 技术地基全部现成：写 PTY 的通道、agent 类型识别、忙闲检测、连回车延迟的坑都已经在代码里解决过。 真正的取舍在产品侧 —— 按钮的成本不是实现，是常驻占用的视觉注意力， 而 90% 的命令一天用不到一次。

保留的反对意见

一个真实的缺口：分屏模式下 Eas-Term 不知道终端跑的是 claude 还是 codex。 NodeAgent.kind 挂在画布节点上（store/canvas/types.ts:22）， 分屏的 leaf 没有等价字段。

也就是说「只有开启了对应服务才显示按钮」这条要求，今天只能在画布模式下满足。 分屏要么先补一份状态，要么按钮只在画布出现 —— 这是要先定的，不是实现细节。

Inventory

探到了什么

两个 CLI 都是编译好的单文件二进制（~280MB），斜杠命令只存在于交互式会话， --help 里没有、管道模式下问不出来（claude -p "/help" 直接回 「isn't available in this environment」）。只能从二进制字符串里挖。

Mechanism

按钮怎么把命令发出去

「不经过输入框」在这里的准确含义是：用户不用打字，但字符仍然要进 PTY —— TUI 只认这一条输入通道。

用户点按钮
   ↓
window.api.pty.write(ptyId, '/compact')     ← 先只写文本
   ↓ 等 ENTER_DELAY_MS = 80ms
window.api.pty.write(ptyId, '\r')           ← 回车单独发
   ↓
Claude Code / Codex 的 TUI 收到并执行
这个 80ms 不是保守，是踩出来的

项目里 TerminalInput.tsx:30 已经记着这个坑：文本和回车一次写进去， 对普通 shell 没问题，但 Claude Code / Codex 这类 TUI 收到一段文本后要先渲染进它自己的输入框， 紧跟着的回车常常被当成「还在粘贴」吞掉 —— 表现是命令躺在 agent 的输入框里没发出去。 按钮必须复用同一套写法，不能图省事一次写完。

三种发送方式的取舍

方式怎么做适用判定
写 PTY pty.write('/compact') + 延迟回车 会话中的所有斜杠命令 主力方案
启动参数 拼进 claude --resume … 只在新开终端时可用 已在用
Agent 控制台的「启动」就是这条
CLI 子命令 codex review / codex resume 要另起一个进程，会脱离当前会话上下文 不适用

要不要回显？

写进 PTY 的字符会在终端里回显（TUI 把它渲染进自己的输入框，然后执行）。 这其实是优点：用户看得见「按钮到底发了什么」，而不是一个黑盒动作。 建议保留回显，不要想办法藏起来 —— 藏起来之后出问题没人能自查。

Gating

什么时候显示、什么时候能点

「只有开启了对应的服务才会显示按钮」拆开是三层判断，前两层现成，第三层有缺口。

第 ② 层的缺口要先定方案

NodeAgent 是画布节点上的字段（注释原话：「画布独有 chrome，分屏不渲染」）。 分屏模式下的 leaf 没有「我绑的是哪个 agent」这个信息 —— 因为分屏里根本没有 Agent 控制台， 用户是自己敲 claude 起的。

三条路，代价递增：

  • 只在画布做 —— 零成本，但分屏用户拿不到。分屏恰恰是「专心跟一个 agent 干活」的场景
  • 从终端标题推断 —— Claude Code 空闲时标题是 ✳ 名字，有特征； 但这是在猜，且 Codex 的标题格式没验过。猜错的代价是按钮发错命令
  • 补一份 leaf 级的 agent 状态 —— 干净但要动数据模型， 还要解决「用户手敲 claude 起的，Eas-Term 怎么知道」

还有一层 Eas-Term 判不了

Claude Code 自己的命令带 isEnabled 谓词 —— 比如 /upgrade 只在非 Max 计划时出现、 /install-github-app 要有 GitHub remote、/ultrareview 要开通网页版。 这些条件 Eas-Term 从外面看不见。所以按钮的门控只能做到「装了 + 是这个 agent + 现在空闲」这个粒度， 再细就会出现「按钮亮着、点下去 agent 说没这个命令」。 这是把候选集限制在通用命令上的另一个理由。

Value

哪些真的配得上一个按钮

四个维度筛：用得多不多、要不要参数、误点会不会出事、Eas-Term 是不是已经有更好的入口。

筛选标准

① 频次

一天用几次？一周用一次的东西不配占据常驻位置 —— 那是菜单该干的活。

② 零参数

按钮天然给不了自由文本。要填内容的命令，按钮只能帮你打开输入框 —— 那还不如直接打字。

③ 误点代价

/clear 误点会丢上下文。要么加确认，要么别做按钮。

④ 有没有更好的原生入口

最容易被忽略的一条。同一件事两个入口、行为还不一致，比没有入口更糟。

Dissent

反对做成「命令面板」

一个很自然的想法是：既然有 132 条，做个搜索式命令面板全放进去。这里给出反对理由。

为什么命令面板是负价值
  • 它解决的问题已经被解决了。两个 CLI 自己都有斜杠补全 —— 在输入框打 / 就出候选列表， 还带 isEnabled 过滤（那是 Eas-Term 判不了的）。Eas-Term 再做一个，只会更差
  • 覆盖率永远追不上。命令随 CLI 版本变（/extra-usage 已经改名 /usage-credits）。 维护一份 132 条的清单，等于给自己找一个每月都会过期的活
  • 发现性问题是假的。用户找不到某个命令时的真实动作是问 agent，不是翻面板
按钮真正的价值在哪

不在「省下打字」，在「把只有 Eas-Term 知道的信息，变成一个恰好出现在那里的按钮」。 /compact 的价值不是省 9 个字符 —— 是上下文快满了的时候它自己亮起来。 这件事 CLI 的斜杠补全做不到，因为它不知道你在看什么。 按这个标准，A 档那 6 条里真正非做不可的其实是 /compact 和 /context 这一对。

建议

1 选 A、2 选 A。先把「上下文快满了 → 按钮亮起来 → 一点压缩」这一条链路做通， 它是唯一一条 CLI 自己做不到的。跑一周看你真的点了几次，再决定要不要铺开到 6 条。 按钮这种东西加容易减难 —— 一旦占了位置，删掉会被当成功能退化。
