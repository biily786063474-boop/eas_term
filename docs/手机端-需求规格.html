范围

做什么，明确不做什么

做

  • 看画布上已打开的项目列表，切进某一个
  • 看该项目里正在跑的终端和 AI 对话
  • 给某个终端 / 对话发文本，收它的回复
  • 列出该项目 Frame 里的文档和图片节点，只列名字
  • 点开某个文档 / 图片看内容

不做（这一版）

  • 不开新终端、不新建项目、不删任何东西
  • 不改文件——文档只读，没有编辑框
  • 不跑命令、不给 shell、不传文件上去
  • 不做画布的图形视图（手机上拖节点没有意义）
  • 不做离线缓存（见安全那节：内容不该留在手机上）
一条边界说明

「已打开的项目」= 画布上存在顶层 Frame 的项目，不是 projects.json 里的全部项目。 这跟你在画布上看到的完全一致——没在画布上摆出来的项目，手机上也看不到。

关键发现

跨网这一段，你已经建好了

本来这是整件事里最重的一块（NAT 穿透、要不要写中继、手机在 4G 下怎么找到家里的机器）。 查了一遍你的服务器档案 + 实测本机，发现路已经通了。

事实来源意味着
39.105.40.173 是 WireGuard 中转 Hub，wg0 = 10.9.0.1/24，UDP 51820 服务器档案（2026-07-28 建）已有中转点，不用新买机器
本机是 peer laptop210 = 10.9.0.4，此刻在线 本机 ifconfig 实测：utun0 inet 10.9.0.439.105 现在就能直接够到这台笔记本
mini.biily.top 已在用「nginx 反代 → 10.9.0.2:8080 穿隧道回家」 服务器档案同一套模式已被验证一个多月，连排障套路都是现成的
Hub 故意不做 NAT（无 MASQUERADE），只做内网互通 服务器档案隧道不会变成公网出口，攻击面比想象的小
eas.biily.top 已在 39.105 上，证书 certbot 自动续 项目 CLAUDE.md加子域名只是多一个 .conf，HTTPS 白拿
因此

跨网这一段的工作量从「写一个中继服务 + 配 pm2 + 处理断线重连」 降到「Eas-Term 起一个只绑 10.9.0.4 的 HTTP 服务，39.105 上加一个 nginx .conf」。 服务器侧新增代码 0 行，只加一个配置文件。

功能白名单

四个动作，逐条定死

白名单是桌面端的一张表，不在这张表上的请求直接 400，不进任何业务逻辑。 手机端 UI 上没有的功能，协议层面也必须没有——只靠界面藏起来不算白名单。

动作 1 列项目 · 切项目

方向 手机 → 桌面 → 手机写操作 无
数据来源
canvas.frames 里 parentId 为空的顶层 Frame，取 projectId + name + status
返回什么
项目名、状态标签（进行中/待执行/已完结）、在跑的终端数、在跑的对话数
「在跑」怎么判
复用看板已经在用的那套（ptyRunning / attention），不另造一套判据
失败态
桌面端没开 → 手机显示「Eas-Term 没有运行」，不是转圈

动作 2 收发信息风险最高的一条

方向 双向写操作 有（往会话里注入文本）
发
只发一段纯文本，落到指定的 agent 会话（agentChat:send）或终端（pty:write）
收
该会话的回复流。AI 对话走归约后的 turns；终端只回「在跑 / 停了」和标题，不回屏幕内容（见下）
硬限制
只能发给已经存在且在跑的会话，不能创建；单条长度上限；速率限制
为什么终端不回屏幕内容
终端输出无界（一次 build 几万行），且里面可能有密钥、路径、别人的数据。 往公网通道上推终端屏幕，是把「本地才看得到的东西」变成「网络上传输的东西」——这一条我建议永远不做

动作 3 列 Frame 里的文档 / 图片（只列名字）

方向 手机 → 桌面 → 手机写操作 无
筛选规则
遍历该项目的顶层 Frame 及其子 Frame 的 nodes[]， 取 pane.kind === 'code'（文档）和 'image'（图片）且 filePath 非空的
明确排除
canvas.freeNodes（画布上散落、不属于任何 Frame 的节点）—— 你的原话是「仅显示已经放在 frame 中的文件」，这条就是它的实现
返回什么
只有名字（node.name 或文件名）+ 类型 + 节点 id。 不返回绝对路径——路径本身就是信息（暴露目录结构），手机端不需要它也能工作
排序
按 Frame 分组，组内按节点在画布上的位置（先上后下、先左后右），跟你眼睛扫画布的顺序一致

动作 4 打开某一个，看内容

方向 手机 → 桌面 → 手机写操作 无（只读）
请求参数
只有节点 id，不接受路径。桌面端自己从节点查出 filePath
双重路径校验
① 这个 id 必须是上一步列表里真实存在的 Frame 内节点； ② 解析出的路径必须过 fsGuard 的既有边界（项目根 + 知识库根）。两条都过才读
文档
纯文本返回，大小上限（建议 512KB，超了截断并说明）
图片
服务端压成适合手机屏的尺寸再传，不传原图——原图可能几十 MB， 而且缩图天然去掉了大部分 EXIF
不做
不下载到手机、不分享、不另存。看完就没了

跨网方案

两条路，我建议先走已经通的那条

方案 A · 复用现有 WireGuard推荐先做

服务器新代码 0 行只加 1 个 nginx .conf已验证 mini.biily.top 同款
手机(4G/任意 Wi-Fi)
   │  HTTPS  eas-m.biily.top
   ▼
39.105.40.173  nginx（宝塔管，加一个独立 .conf）
   │  proxy_pass http://10.9.0.4:PORT
   ▼  WireGuard wg0（已在跑，UDP 51820）
本机 utun0 = 10.9.0.4
   │
   ▼  Eas-Term 只监听 10.9.0.4:PORT（不是 0.0.0.0）

为什么必须绑 10.9.0.4 而不是 0.0.0.0： 绑 0.0.0.0 等于同时把这个口开在咖啡厅的 Wi-Fi 上，同网段任何人都能敲。 绑隧道地址，则只有隧道里的机器（也就是 39.105）够得到，这一层是免费的网络级隔离。

代价
笔记本必须连着 WireGuard。现在是连着的，但睡眠 / 换到封 UDP 的网络会断
断了什么表现
手机上 502。跟 mini.biily.top 断隧道时一模一样，排障顺序照抄档案里那三步

方案 B · 出站 WebSocket 中继先别做

服务器新代码 一个 pm2 服务不依赖 VPN

Eas-Term 主动向 39.105 发起 WSS 长连接，中继把手机和桌面配对。 好处是笔记本换任何网络都能用（只要出得去 HTTPS），不需要 WireGuard 一直挂着。

但现在不该做它。A 已经通了，B 是为了解决「A 的隧道不够稳」这个还没被证实的问题。 先用 A 跑两周，真的在外面撞到隧道断，再上 B 也不迟——那时候还知道具体是哪种网络断的， 比现在凭空设计强。

安全

这一节最重要，请完整读完
必须先说清楚的一件事

白名单限的是接口面，不是爆炸半径。

四个动作里，「发消息」是发给一个正在跑的 Claude Code / Codex。 那个 agent 能读写你的项目文件、能跑命令、能联网。也就是说： 拿到手机端凭证的人，等于拿到了一个能对你这台电脑下达自然语言指令的入口。

协议上只有 4 个动词，这是真的；但说「只能收发信息所以很安全」是不对的。 下面每一条防护都是围绕这个事实设计的，不是为了凑数。

七道锁

#锁挡住什么
1网络级：只绑 10.9.0.4，不绑 0.0.0.0 同一个 Wi-Fi 下的其他人。除了隧道对端，物理上没人够得到这个口
2配对：桌面端显示二维码，手机扫一次绑定，一次性有效 没配过对的设备。凭证不靠你手动抄，也就不会被抄错或截图外传
3每设备独立 token，桌面端列出「哪台手机、什么时候配的、最后一次访问」，随时可吊销 手机丢了。点一下就断，不用换整套凭证
4白名单在桌面端强制，不在手机端 改造过的客户端。手机端是不可信输入，它发什么都要在桌面端重新判一遍
5路径双重校验：id 必须来自 Frame 内节点 + 必须过 fsGuard 把 ~/.ssh/id_rsa 读出来。就算构造出合法 id，也过不了第二道
6密钥永不出机器：secrets.json、MCP token、keychain 一律不进这条通道 通道被打穿时的次生灾害。通道里根本没有它们
7桌面端可见：手机发的每一条，在桌面上都留痕（谁、什么时候、发了什么） 悄悄的滥用。你回到电脑前能看见发生过什么
一个必须你来定的取舍：审批闭环怎么办

Eas-Term 有一套 PreToolUse 审批钩子——agent 要跑命令时会停下来等你点「允许」。 人在外面时，这道锁就变成了一个死结：

  • 手机不能审批 → 你发一句话过去，agent 卡在第一个工具调用上，等到你回家。远程控制基本没用
  • 手机能审批 → 这道锁就没了。拿到手机凭证的人可以一路点「允许」

我倾向第三条路：手机能审批，但只对「读」类工具自动放行，「写 / 执行」类仍然必须回电脑点。 这样在外面能让 agent 查资料、读代码、给方案，但改不了东西。 不过这条要按工具分类做一张表，是这个功能里最细致的一块——也可以第一版先做「手机完全不能审批」， 用起来再说。你选。

还有两条我建议直接写死，不给开关

① 终端屏幕内容永不上网。见白名单动作 2 的说明。

② 手机端不做离线缓存。断线就是空白。缓存意味着你的项目内容躺在手机的存储里， 而手机比电脑容易丢得多。

分期

怎么排

第一期 · 只读先证明链路通

白名单 动作 1 / 3 / 4不含发消息

看项目、看会话状态、看文件列表、看文件内容。一个写操作都没有。 这一期跑通，就等于验证了「隧道 + nginx + 配对 + 白名单 + 路径校验」整条链路， 而且万一哪里漏了，最坏后果是信息泄漏而不是被人操控电脑——先趟这条风险低的。

第二期 · 加发消息风险台阶在这里

白名单 + 动作 2审批策略 按你上面的选择

这一期才让手机真的能"控制"。上线前把桌面端的留痕面板一起做好—— 没有留痕就上写操作，出问题时你没有任何依据。

第三期 · 视情况不承诺

原生壳、离线草稿、推送通知（agent 等你审批时手机响一下）、方案 B 中继。 都等前两期用过之后再说——现在列出来只是说明它们没被忘掉，不是排期。

要你拍板的三件事

  1. 审批策略：手机完全不能审批 / 只能批"读"类 / 全都能批（见安全那节，我倾向中间那个，但第一版做第一个也行）
  2. 先做哪一期：按上面分期走（推荐），还是直接连发消息一起做
  3. 域名：用 eas-m.biily.top 这种新子域，还是挂在 eas.biily.top 下的一个路径
另外，一处档案与现实对不上，先报给你

你的全局 CLAUDE.md 里写「本机(192.168.31.210)是密钥金库主机」， 但本机此刻 en0 是 192.168.31.126（WireGuard 身份 laptop210 = 10.9.0.4 仍然对得上）。 大概率只是路由器重新分配了 DHCP。没动你的文件，你确认后我再改。
