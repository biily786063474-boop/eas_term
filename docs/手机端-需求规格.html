建立连接

用户第一次要做什么：扫一次码

这是整个功能的第一印象，也是唯一需要用户"配置"的一次。 目标：从打开设置到手机上看见项目列表，不超过 30 秒，全程不出现一个技术名词。

电脑上 · 第 1 步
设置 → 手机端 → 打开开关
开关一开，电脑端就地生成一对设备密钥，屏幕上出现一个二维码。 在此之前不监听任何端口、不连任何服务器——不用这个功能的人，等于这功能不存在。
手机上 · 第 2 步
用相机扫码
第一次扫会跳到网页版，提示「添加到主屏幕」——装完就是一个正经 app 图标， 全屏运行，没有浏览器地址栏。不用过应用商店。
第 3 步
手机再扫一次（这次是配对码）
二维码里装着三样东西：怎么找到这台电脑、一次性配对码、 这次连接的加密密钥。密钥是用摄像头"看"过去的，从来没上过网—— 这就是中间那台读不懂内容的根本原因。配对码 60 秒过期。
电脑上 · 第 4 步
弹窗确认「是你本人吗」
电脑上弹一个框：「iPhone（某某）请求配对」，你点允许才成立。 扫到码不等于连上——就算二维码被别人拍到，没有你在电脑前点这一下也没用。
完成
以后打开就是连着的
配一次，长期有效。电脑端设置里有一张设备表：哪台手机、什么时候配的、 最后一次访问是什么时候，随时可以踢掉。

日常怎么用

打开手机上的图标 → 自动连上 → 项目列表。没有登录、没有输密码。

顶部永远显示当前走的哪条路： 局域网直连 隧道 电脑没开
这不是装饰——用户有权知道自己的数据这一刻走的是哪条线路。

三种"连不上"分别怎么说

  • 电脑没开 → 「你的电脑没有运行 Eas-Term」，不是转圈
  • 电脑开着但网断了 → 「电脑离线，最后一次在线是 14:32」
  • 没配过对 → 直接给配对引导，不给一个空列表

三种状态用户的下一步动作完全不同， 糊成一个「连接失败」等于什么都没说。

通道

走隧道 —— 而且这个选择比中继更好

你定了走隧道。这不只是换个说法，它把整个功能里最容易写错的那块代码直接消掉了。 下面说清楚为什么。

隧道比中继强在哪：TLS 在你电脑上才解开

中继方案里，中继是一个懂协议的服务——它收到一条消息、看一眼路由号、再发出去。 为了让它读不到内容，我得另外设计一套端到端加密：密钥协商、重放防护、密钥轮换…… 这是整个功能里最容易写错、错了还看不出来的一块。

隧道方案里，隧道只搬字节，它根本不知道自己搬的是什么。 手机和你的电脑之间是一条完整的 TLS 连接， 加密在手机上做、解密在你的电脑上做，隧道两头都不是终点。

结果：端到端加密不是我实现的，是 TLS 本来就有的。 隧道运营方（你）读不到内容不是因为承诺了不读，是因为手里根本没有那把钥匙。 少写几百行密码学代码，安全性反而更高。

两条路，自动选

优先 同一个 Wi-Fi：直连，压根不进隧道零成本

用在 在家 / 在公司隧道流量 0延迟 最低

手机直接连电脑的局域网地址。不出家门、不花一分钱带宽。 这是绝大多数使用场景——也就是说日常用法根本碰不到你的服务器。 地址靠配对时记下的 + 局域网发现自动更新，路由器换 IP 也能找回来。

在外面 反向隧道你要跑的那个

用在 4G / 别的 Wi-Fi方向 电脑主动向外要开端口吗 不要
手机 ──── TLS ──────────────────────────────────▶ 你的电脑
        （这条 TLS 从头到尾是一条，中间不断开）

        实际经过：
        手机 ─WSS─▶ 隧道服务端 ─隧道内─▶ 电脑（出站连上来的）
                        │
                        └─ 它看得到：设备号、字节数、时间
                           它看得到的内容：一坨解不开的 TLS 密文

电脑端是主动往外连的，所以：不用开端口、不用动路由器、 不用有公网 IP，CGNAT（手机热点、部分宽带）下也能用。走 443 端口， 公司网络的防火墙也拦不住。

证书在配对时就钉死了：二维码里带着你电脑那张自签证书的指纹， 手机以后只认这一张。中间任何人想插一脚都会被手机当场拒掉—— 连隧道服务端自己也不行。

隧道有两头 —— 这一节最容易想岔

「走隧道」听起来像是「用户自己建一条就行，你什么都不用管」。 不完全是。隧道有两头，两头的归属完全不同：

客户端 在 app 里，随包发出去

用户装完 Eas-Term 就有了，什么都不用配。 它负责主动往外连——这就是不用开端口、不用动路由器的原因。

服务端 必须在公网上，得有人跑

隧道要「打洞」，就必须有一个双方都够得到的公网地址。 这一头不会凭空出现——不是你跑，就是用户自己有。

于是三种情况，用户的负担和你的负担正好相反

「用户只用建立自己的隧道」在情况 ② 和 ③ 下成立，在 ① 下不成立。

而 ② 才是最接近你设想的那个：用户在手机和电脑上装同一个 VPN、登同一个账号， 两台设备就进了同一个虚拟局域网——这时手机看你的电脑，跟在家连同一个 Wi-Fi 没有区别， 走的是「局域网直连」那条路，压根不需要你提供任何服务。 你自己这台就是这种情况（utun0 = 10.9.0.4）。

关于「同账号」：要说清楚是谁的账号

VPN 的账号 —— 对，就是这么用的

手机和电脑登同一个 Tailscale（或别的）账号 → 同一个虚拟局域网 → 直接互相看得见。 这正是上面的情况 ②，也是你说的「设置好了就能远程操控」。

Eas-Term 的账号 —— 没有，也建议别加

这个 app 现在没有任何账号体系（额度那套读的是 Claude/Codex 自己的登录，不是你的）。

为手机端加一套账号意味着：注册、登录、找回密码、 以及一份存在你服务器上的用户身份数据。而它换来的东西，扫码配对已经给了—— 两台设备靠光学交换密钥直接互认，比账号更简单也更私密。纯负债，不建议。

我的建议：第一版不出服务端

发布时只做 局域网直连 + 情况 ②（自带 VPN）， 文档里写清楚「要在外面用，装个 Tailscale，三分钟」。你一分钱带宽都不花，一台服务器都不用管。

然后看真实反馈：有多少人是真的需要在外面操控，又有多少人卡在装 VPN 这一步。 数字出来了再决定要不要做情况 ①。 不要在验证需求之前就承诺跑基础设施——那是一旦开始就很难停的承诺（用户已经在用了）。

明确不做的两条

不做端口转发引导。让普通用户去路由器上开端口， 等于把他的电脑直接暴露在公网——这个建议本身就不负责任。

不在隧道服务端终止 TLS。一旦在那儿解开，上面那整段「读不到内容」就全废了。 这条是架构红线，不是优化项。

安全

分发之后，这一节的分量完全不同
必须先说清楚的一件事

白名单限的是接口面，不是爆炸半径。

四个动作里「发消息」是发给一个正在跑的 Claude Code / Codex。 那个 agent 能读写项目文件、能跑命令、能联网。也就是说： 拿到手机端凭证的人，等于拿到了一个能对那台电脑下自然语言指令的入口。

协议上只有 4 个动词，这是真的；但说「只能收发信息所以很安全」是不对的。 分发之后这句话更要紧——出事的不是你的电脑，是用户的。

#锁挡住什么
1默认关：不开这个开关，一个端口都不监听、一个服务器都不连 不用这功能的用户。对他们来说这段代码等于不存在
2TLS 端到端：手机↔电脑一条完整 TLS，隧道只搬字节；证书指纹配对时钉死 隧道运营方（也就是你）。不是承诺不读，是手里没有钥匙——这是能安心分发的前提
3配对要电脑端点确认，配对码 60 秒过期 拍到二维码的人。光有码不够，还得有你在电脑前那一下
4每台设备独立凭证，电脑端列表可见可吊销 手机丢了。点一下就断，不影响别的设备
5白名单在电脑端强制，不在手机端 改造过的客户端。手机是不可信输入，电脑端要重新判一遍
6路径双重校验：id 必须来自 Frame 内节点 + 必须过 fsGuard 读 ~/.ssh/id_rsa。就算构造出合法 id，也过不了第二道
7密钥永不出机器：secrets.json、MCP token、keychain 一律不进这条通道 通道被打穿时的次生灾害。通道里根本没有它们
8电脑端留痕：手机发的每一条都记下来（哪台设备、什么时候、发了什么） 悄悄的滥用。回到电脑前能看见发生过什么
一个必须你来定的取舍：审批闭环怎么办

Eas-Term 有一套 PreToolUse 审批钩子——agent 要跑命令时会停下来等人点「允许」。 人不在电脑前时，这道锁变成死结：

  • 手机不能审批 → 发一句话过去，agent 卡在第一个工具调用上。远程控制基本没用
  • 手机能审批 → 这道锁就没了。拿到手机的人可以一路点「允许」

我倾向第三条路：手机能审批，但只对「读」类工具自动放行，「写 / 执行」类必须回电脑点。 在外面能让 agent 查资料、读代码、给方案，但改不了东西。 要按工具分类做一张表，是这功能里最细的一块——第一版也可以先做「手机完全不能审批」。你选。

三条建议直接写死，不给开关

① 终端屏幕内容永不上网。见白名单动作 2。

② 手机端不做离线缓存。断线就是空白——手机比电脑容易丢。

③ 隧道服务端不记日志内容，也不终止 TLS。只记连接数和字节数这类运维指标。 你不该有能力回答「某某用户昨天在干什么」这个问题 —— 而走隧道之后，这不再靠自律， 技术上就做不到。

分期

怎么排

第一期 · 局域网 + 只读零服务器

通道 只有局域网直连白名单 动作 1 / 3 / 4你要跑的服务 无

同一个 Wi-Fi 下，扫码配对，看项目、看会话状态、看文件列表和内容。 一个写操作都没有，一台服务器都不用。 这一期跑通就验证了配对、白名单、路径校验、以及整套手机界面—— 而且最坏后果是同一个 Wi-Fi 内的信息泄漏，不是被人远程操控。

第二期 · 加发消息风险台阶

白名单 + 动作 2审批策略 按你的选择

这一期才让手机真的能"控制"。上线前把电脑端的留痕面板一起做好—— 没有留痕就上写操作，出问题时用户没有任何依据。 这一期仍然可以只支持局域网，先不碰隧道服务端。

第三期 · 自己出隧道服务端看数据再定，不是必做

新增 一个隧道服务TLS 绝不在这里终止

这一期比 v1 的中继方案轻得多：不用设计端到端加密协议（TLS 本来就是端到端的）， 隧道服务端只做一件事——把出站连上来的电脑和请求进来的手机接成一条字节管道。

这一期不一定要做。前两期发出去之后，如果大部分想在外面用的人 都能接受装个 Tailscale，那这一期可以永远不做——你零成本。 只有当「卡在装 VPN 这一步」的人多到成为主要流失点，才值得自己出服务端。

真要做，上线前想清楚三件：带宽成本怎么兜、滥用怎么限、隧道挂了用户看到什么。 你自己那台不用等这一期——现成的 WireGuard 就能先跑。

第四期 · 视情况不承诺

原生壳、推送通知（agent 等审批时手机响一下）、离线草稿。 都等前三期用过再说。

要你拍板的四件事

  1. 先做哪一期：按上面走（第一期局域网只读，推荐），还是别的组合
  2. 第一版要不要自己出隧道服务端：我建议不出——先只发「局域网直连 + 自带 VPN」， 看真实需求再定（见通道那节最后一段）
  3. 审批策略：手机不能批 / 只能批"读"类 / 全都能批（我倾向中间那个）
  4. Codex 的对话解析要不要补：不补的话，终端里跑 Codex 时手机只能发不能收（见动作 2 那张表）
  5. 手机端形态：PWA（推荐，不过商店、一套代码）还是直接上原生
