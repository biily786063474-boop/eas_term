为什么是「当库用」而不是「fork」

我们要的最终形态是画布上的一个模块节点 —— 能和终端、AI 对话并排、能被 AI 用 MCP 工具操作、 跟着项目走。任何独立应用 fork 过来都要先剥掉它自己的窗口、菜单、状态管理， 剥完剩下的正好就是「一个图数据 + 一个渲染器」。那还不如直接取数据自己画。

运行调用图：不需要新依赖

你要的第二样是「运行调用图」。这件事在这个项目里比一般项目容易， 因为验证链路已经在用 CDP 了。

目标进程取数手段已具备
主进程node --cpu-prof → .cpuprofile（含完整调用树）Node 自带
渲染进程CDP Profiler.start / stop已在用 scripts/eval-in-app.mjs 就是走 CDP
子进程（CLI / PTY）不采 —— 那是别人的进程范围外
要先说清的期望

.cpuprofile 是采样式的调用树，不是「每一次调用都记」。 它能回答「这段时间里谁调了谁、各花了多少」，不能回答「A 这个函数一共被调用过几次」。 要后者得上插桩，代价高一个数量级。先做采样版，够用再说。

PLAN

落地方案：三步，每步独立可用

刻意排成「每一步做完都能用」，不做完不能验的那种大爆炸。

第一步 · 静态依赖图（最小可用）

  • 主进程新增一个分析器：调 cruise()，产出 {modules, edges, cycles}
  • 渲染层新增节点类型 codegraph，把图画出来（力导向或分层，先分层）
  • 入口写死那四个（main / preload / renderer / island）—— 实测里踩到的那个坑
  • 能力：看结构、点节点看它的进出边、高亮循环依赖

第二步 · 叠上我们自己的图纸语义 这才是差异化

通用工具给的是「文件 A 依赖文件 B」。而 docs/architecture/10-模块领地图.md 里 已经有一套没有任何工具知道的知识：

  • 风险等级（🟢🟡🔴⛔）→ 节点染色
  • 领地归属 → 自动分组，一眼看出「哪块地在跨界引用」
  • 禁区与跨文件同步清单 → 画成特殊边，改动时提前示警
  • 类型引用 vs 值引用 → 区分开，store 那组「循环」才不会被误报成病

这一步做完，这个模块就不再是「又一个依赖图工具」， 而是这个仓库自己的体检表 —— 也是任何 fork 来的工具给不了的东西。

第三步 · 运行调用图

  • 面板上一个「录一段」按钮 → 采样 → 出调用树 / 火焰图
  • 与第一步的静态图对照：静态上有边、运行时从没走过 = 可能的死代码
  • 反过来：运行时有调用、静态图上没有边 = 动态 import 或事件解耦，值得标出来

RISKS

先说清楚的四件事

都是实测中已经露头、或按这个仓库的历史一定会遇到的。

① 入口配错会静默少掉 90% 的代码

实测已经踩到：按目录扫只得 34 个模块，且不报任何错。 配置必须固化并加断言（模块数低于某个阈值就当失败）， 否则某天图变空了没人知道。

② 「循环依赖」不等于「病」

store 那组 8 条边多半是类型循环，TS 里完全无害。 不区分就会给出一张全是红色的图 —— 而全是红等于没有红， 真正的问题反而被淹掉。

③ 新增依赖要过图纸 01 那条红线

dependency-cruiser 是纯本地分析、不出站， 但它是新的第三方依赖（当前依赖总数 36）。 装之前按规矩在图纸上登记一笔。

④ 别做成第二个「跟着代码漂移的图」

docs/architecture/ 已经有一套手写图纸，靠纪律维护。 这个模块要补充它（自动的那半），不是取代 —— 两套并存而口径不一致，比只有一套更糟。
