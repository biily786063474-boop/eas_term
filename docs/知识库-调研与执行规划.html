裁决一 · 视频这块比想象中容易

你要把「博主的参考视频」放进知识库 —— 卡帕西那套只处理文本，覆盖不了。 但这个 app 已经内置了离线语音识别（sherpa-onnx + SenseVoice 模型， 支持中/英/日/韩/粤，language: 'auto'），现在用于语音输入。 视频 → 用 Electron 自带的 Chromium 解码出音轨 → 喂给它 → 拿到转录文本 → 交给 agent 写成笔记。 零新依赖、零 token、全离线。

裁决二 · cc / codex 兼容根本不用写代码

卡帕西那套的精髓是「知识库就是一个 markdown 文件夹」。 所以兼容方案是：在知识库根目录同时放 CLAUDE.md 和 AGENTS.md，内容相同， 写明目录约定、front-matter 格式、链接写法、ingest/lint 的规矩。 Claude Code 自动读 cwd 的 CLAUDE.md，Codex 自动读 cwd 的 AGENTS.md —— 在知识库目录里起终端，两边立刻都懂规矩。不需要 MCP，不需要适配层。

裁决三 · 修订：图谱不是可有可无，但它服务的是「体检」不是「查询」

我初版的判断被原文部分推翻了，如实更正。 我原来说「图谱是最少被用来干活的功能，降到最后一期」。卡帕西原话是： 「Obsidian's graph view is the best way to see the shape of your wiki — what's connected to what, which pages are hubs, which are orphans.」

但注意他说的用途：看清形状、找出枢纽页和孤儿页 —— 这些正是 lint 要处理的东西。所以准确的定位是：

回答什么问题用的频率该排哪
反向链接「这篇被谁引用了」每天，读笔记时顺手看 第 1 期
图谱「整个库长歪了没、哪些页是孤儿」偶尔，做体检时 和 lint 同期

结论仍是图谱排后面，但理由变了：不是「它没用」， 而是它和 lint 是一对，该一起做 —— 光有图谱看到一堆孤儿页却没有 lint 去修， 等于只给你添堵。执行规划第 4 期本来就是「图谱与体检」，这个安排正好对上，不用改。

实现上：项目里没有 d3，但 konva 已是依赖（设计模块在用）， 力导向那点数学手写一百来行就够，不必为此加库。

裁决四 · 「AI 帮我整理杂乱文件」是这套方案里最危险的一环

这个功能的失败模式不是「分类不准」，是「我那个文件去哪了」。 一旦发生一次，用户再也不会往收件箱里放东西 —— 功能就死了。 所以它必须满足三条硬约束：先出计划让人过目、绝不删除原件、每次归档一个 git commit 可整体回滚。 详见「收件箱」一节。

卡帕西的 LLM wiki 是什么

先说清楚它解决什么问题、和 RAG 的区别在哪，以及我这份调研的可信度边界。

核心思路：把 LLM 当编译器，而不是检索器

传统 RAGLLM wiki
存什么原始文档切块 + 向量已经被消化过的 markdown 笔记
问的时候检索相似片段，拼进上下文直接读已经写好的笔记
新增一份资料切块、嵌入、入库读它 → 写一篇新笔记 → 顺手更新被它牵动的老笔记
需要的基建向量库、嵌入模型、检索调参一个文件夹
会腐烂吗会（旧块永远躺在那）也会 —— 所以有 lint

三层架构（原文的说法）

层谁负责关键约束
Raw sources 原始素材你负责搜集 不可变 —— 「the LLM reads from them but never modifies them」。这是你的真相来源
The wiki 笔记层LLM 全权拥有 「You read it; the LLM writes it.」你几乎不该手写 wiki
The schema 约定文件你和 LLM 一起共同演进 就是 CLAUDE.md / AGENTS.md。原文称它是 「让 LLM 成为一个守纪律的 wiki 维护者，而不是一个通用聊天机器人」的关键配置

三个动作

Ingest  把原始资料丢进 inbox → LLM 读完 → 写成结构化的笔记，
        并且回头去改相关的老笔记（交叉链接、标记矛盾）

Query   提问时不检索原文，直接读已经消化好的笔记回答
        而且：好答案要**归档回 wiki 成为新页面**——
        你的每次探索也参与复利，不是消散在聊天记录里

Lint    让 AI 体检：找矛盾、找过期、找孤儿页（没人链接它）、
        找该连没连的交叉引用

为什么这个模式值得抄：它把「整理」这件事从一次性劳动变成了 agent 的日常动作。 你每加一份资料、每问一个问题，知识库都更厚一点 —— 而且厚的是已经想明白的部分， 不是原始材料的堆积。对一个人干所有活的超级个体来说，这正是最稀缺的东西。

它约定的结构

wiki/
├── _templates/     笔记模板
├── projects/
├── research/
├── reference/
├── meetings/
└── inbox/          还没整理的粗料

每篇笔记开头一定有 一句话摘要 + 标签， 用意是让 agent 不读全文就能判断这篇相不相关 —— 这是整个模式能在几百篇规模上跑起来的关键。 笔记之间用 Obsidian 那种 [[双链]] 互指。

两个特殊文件（原文点名，我初版漏了）

文件是什么怎么用
index.md 内容目录：每页一行链接 + 一句话摘要，按类别分组。每次 ingest 后 LLM 更新 回答问题时先读它再决定深入哪几页。原文说这个做法 「在 ~100 份源、几百页的规模下出奇地好用，省掉了整套 embedding RAG 基建」
log.md 只追加的时间线：每次 ingest / query / lint 记一条 原文给了个实用技巧：每条以固定前缀开头 （## [2026-04-02] ingest | 文章标题）， 这样 grep "^## \[" log.md | tail -5 就能看最近五条

原文还有一句提醒值得抄：「别过度设计。」 以及一句更重要的自我定位 —— 「这份文档故意写得抽象。它只负责传达这个模式， 具体怎么落地由你和你的 agent 一起定。」所以下面那套目录结构是我给的起点，不是标准答案。

一个对这个软件极有利的巧合

原文描述他自己的工作方式：「我一边开着 LLM agent，一边开着 Obsidian。 LLM 根据我们的对话改文件，我实时浏览结果 —— 跟着链接走、看图谱、读更新过的页面。 Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。」

这正是 Eas-Term 已经有的形态：一侧终端跑 agent，一侧面板浏览。 别人要开两个应用来回切，这里天生就是一个窗口。 这不是附加功能，这是这个软件最贴合的用法之一。

Gap

照搬过来，有三个地方对不上

卡帕西的场景是研究者读论文读文章。超级个体的素材长得不一样。

差异原方案你的实际情况怎么补
素材形态 文章、论文、图片 参考视频是主力之一（博主的剪辑手法、口播节奏、镜头语言） 离线转录成文本再进 wiki，原件归档到 素材/。 用已有的 sherpa-onnx，见裁决一
主要实体 按主题组织（research / reference） 你是围绕「人」在学 —— 某个博主的思维模型、行为习惯、代表作 把「人物」提成一级目录。这是这套知识库和通用 wiki 最大的结构差异
跨领域 单一领域深挖 编程 / 设计 / 剪辑 / 文案四条线并行，而且经常互相借鉴 「方法」目录按可迁移的做法组织，而不是按领域切开 —— 剪辑的节奏感和写代码的节奏感是同一类知识
「人物」为什么值得单开一级

因为你的学习路径是「跟人学」，不是「查主题」。 你会问的是「这个博主遇到这种情况会怎么做」，而不是「关于转场的所有笔记」。 人物页把某个人的思维模型、口头禅、代表作、你的实测反馈聚在一起， 正好是 agent 回答这类问题时最该先读的那一页。

Panel

六席评审

各自只对自己那个维度负责。交锋点在后面的表里。

席 1 知识管理 · 这套模式的边界

「它在几百篇的量级最好用，再往上会喘。」 原文给了具体刻度：约 100 份源、几百页，靠一份 index.md 就够， 「省掉了整套 embedding RAG 基建」。再往上就需要真正的搜索 —— 原文点名推荐了 qmd （本地 markdown 搜索，BM25 + 向量混合、端上跑，同时提供 CLI 和 MCP server）。 所以第一期照抄 index.md 就行，别过度设计；等真的越过那个刻度， 再接 qmd —— 它既能被 agent shell 出去调，也能当 MCP 工具，两条路都通。

席 2 多模态 · 视频怎么进来

「别指望 agent 直接看视频。」 现实路径是转录成文本 + 关键帧截图。好消息是转录这块本机已经有了。 但要提醒两件事：① 一个小时的视频转录要跑几分钟， 必须是后台队列 + 进度可见，不能卡住界面； ② 转录稿是中间产物不是知识 —— 直接把三万字逐字稿塞进 wiki 等于污染，必须让 agent 再消化一遍成笔记， 逐字稿单独存到 素材/ 里备查。

席 3 架构 · 落到现有代码上

「大部分零件都是现成的。」 文件树复用 FileTree，markdown 渲染层已经有（零依赖那份）， 终端模式加一个面板类型和加「名词词典」是同一个改法（PaneKind 加一项）。 真正要新写的只有三样：知识库左抽屉、收件箱归档流程、图谱。 唯一的架构决定是知识库到底是不是一个「项目」 —— 我的意见是不是：它是全局的，跨项目共享，不该混进项目列表。

席 4 数据安全 · AI 动用户的文件

「这是整个方案里唯一可能造成真实损失的部分。」 归档 = 移动文件 + 改名 + 写新文件。任何一步出错，用户丢的是他自己的原始素材。 三条不可让步：先出计划让人过目（哪个文件去哪、生成什么笔记）、 原件绝不删除（只移动，且落点固定在 素材/）、 知识库 git 化，每次归档一个 commit —— 出问题一条命令全退回去。 不接受「AI 应该不会出错」这种论证。

席 5 产品 · 取消「基本操作」的代价

「那四个工具不能凭空消失。」 左抽屉现在装的是 选择 / 矩形 / 箭头 / 便签。 换成知识库我同意 —— 知识库是天天用的，画矩形是偶尔用的，占一整个抽屉确实亏。 但删掉它们会让「在画布上圈一下、写个便签」这件事无处可做。 建议把这四个收成右下角缩放条旁边的一条紧凑图标栏（四个图标，一行，不占抽屉）， 右键菜单里也保留「新建便签」（那条本来就有）。

席 6 怀疑论 · 这功能会不会又变成一个没人用的抽屉

「先承认：大多数个人知识库最后都变成了数字仓鼠窝。」 收集的快感远大于使用的频率。判断这套东西成不成立，只有一个标准： 你是不是真的会在干活时去问它。所以我提两条否决性意见：

  • 入口必须在干活的地方，不是一个要专门去的页面。左抽屉 ✓、终端模式下拉 ✓ —— 这两个位置选对了，说明产品直觉是对的。
  • 第一期必须包含「问知识库」这个动作，不能只做「往里放」。 只做收集端的知识库，三周后一定是死的。哪怕最简陋 —— 在知识库目录起一个终端、agent 自动带着 wiki 约定 —— 也算闭环。

另外给一条可验证的成败判据：一个月后，你问知识库的次数是不是超过往里放的次数。 如果放 100 次问 3 次，这就是个仓鼠窝，该砍。

交锋点

争议正方反方裁决
知识图谱做不做 你点名要；视觉上确实是知识库的门面 席 1/6：图谱是最贵、最少被用来干活的一块；反向链接才是日用品 降级 反向链接进第一期，图谱排最后一期，做一个简版
知识库算不算一个「项目」 复用项目 Frame 的全套能力，省事 席 3：它是全局的、跨项目共享，混进项目列表会让「项目」这个概念变脏 不算 独立配置项，但可以在画布上开一个知识库 Frame 干活
逐字稿要不要直接进 wiki 信息最全 席 2：三万字逐字稿是中间产物，直接进等于污染知识库 不进 逐字稿存 素材/，wiki 里只放消化过的笔记 + 回链
归档要不要自动跑 无感知最省心 席 4：静默移动用户的文件，出一次事这功能就死了 必须人工确认 出计划 → 过目 → 执行 → git commit
四个画布工具怎么办 — 席 5：不能凭空消失 收成图标栏 移到缩放条旁边，见「界面」一节

Shape

知识库长什么样

目录结构、笔记格式、链接约定，以及怎么让两个 CLI 自动懂规矩。

目录结构

<你选的位置>/
├── 00-收件箱/        ← 你唯一需要记住的目录。杂乱素材全丢这
├── 人物/               博主 / 作者：思维模型、行为习惯、代表作、你的实测反馈
├── 方法/               可迁移的做法：脚本结构、剪辑节奏、配色逻辑、调试套路
├── 领域/               编程 / 设计 / 剪辑 / 文案 —— 各自的主题笔记
├── 项目/               和 Eas-Term 里的项目对应，放决策记录和复盘
├── 素材/               归档后的原件：视频、图、PDF、逐字稿
├── _模板/
├── CLAUDE.md           ← 给 Claude Code 的规矩
└── AGENTS.md           ← 给 Codex 的同一份规矩

六个顶层目录，比卡帕西那套多一个「人物」少一个 meetings —— 按你的实际用法调的。 「别过度设计」这条建议照抄：不够用了再加，比一开始铺二十个目录强。

## 要点

## 相关
- [[三秒法则]]
- [[某某]]

summary 和 tags 是硬约定，不是装饰 —— agent 靠它们决定要不要读全文， 没有它们，知识库一过一百篇就开始卡。

cc / codex 兼容：零代码

知识库根目录放两份内容相同的说明文件：

  • CLAUDE.md —— Claude Code 在该目录起会话时自动读
  • AGENTS.md —— Codex 在该目录起会话时自动读

里面写清目录约定、front-matter 字段、双链写法、ingest / lint 的动作定义。 在知识库目录里开终端，两个 CLI 立刻都懂规矩 —— 不需要 MCP 工具，不需要适配层， 也不会因为哪家 CLI 改了接口而失效。这正是「知识库就是个文件夹」这个设计的红利。

这两份文件由 app 在初始化时生成，并在版本升级时提示更新（按标记替换，不覆盖用户自己加的内容 —— 和技能包那边一个套路，那套已经验过）。

Inbox

收件箱 → AI 归档

这是最有价值也最危险的一环。安全设计写在功能设计前面。

流程

你做的事：把任何东西丢进 00-收件箱/

① 扫描      识别类型：视频 / 音频 / 图 / PDF / 文本 / 网页存档
② 预处理    视频音频 → 离线转录（本机 sherpa-onnx，零 token）
                图 → 记录尺寸/EXIF；PDF/文本 → 直接读
③ 出计划    每个文件：归到哪个目录、改成什么名字、生成哪篇笔记、
                会牵动哪些已有笔记 —— 全列出来，等你过目
④ 你确认    可以逐条改或剔除
⑤ 执行      移动原件到 素材/ → 写笔记 → 更新相关笔记的双链
⑥ 落一个 commit  整批一次，信息写清这次归了什么
三条不可让步的约束
约束为什么
先出计划，人确认后才动 失败模式不是「分类不准」，是「我那个文件去哪了」。发生一次，用户再也不敢往里放东西
只移动，绝不删除、绝不覆盖 重名一律加后缀而不是覆盖。原件永远能找到，落点固定在 素材/<年月>/
知识库 git 化，每批一个 commit 这是唯一能整体撤销的机制。AI 改了十篇笔记的双链，靠人工回滚是不可能的

git 是可选但强烈建议的：初始化时问一句「要不要用 git 管这个知识库（推荐）」。 不用 git 的话，「AI 帮我整理」这个功能建议直接关掉 —— 没有撤销的自动整理不值得冒险。

成本与耗时（要如实告诉用户）

  • 转录：本机跑，不花 token。但一小时的视频要几分钟 —— 后台队列 + 进度条，不能卡界面
  • 写笔记：这一步花 token，量随素材数线性增长。归档计划里要给出预估条数， 大批量时提醒分批
  • 更新相关笔记：这是 Karpathy 模式最贵也最值钱的一步。建议默认只更新直接相关的， 全库交叉更新放到 lint 里手动触发

Timing

agent 什么时候来整理

用户提到才整理？定时整理？还是结合？——结论是结合，但切分的那条线不在「频率」上。

切分的那条线

不是按「多久一次」切，是按「花不花钱、动不动文件」切。

自动的部分绝不写 wiki、绝不花 token；花钱或动文件的部分，一定有人在场。

这条线一划，「定时 vs 手动」就不再是个二选一的问题了 —— 该自动的部分自动到底，该有人的部分一次都不能少。

阶段谁触发花 token动文件为什么这么定
① 发现
收件箱里有新东西		 全自动
静默		否否 只是数一下文件数。零成本零风险，没有任何理由要人点

为什么第 ④ 步不能定时自动跑

原作者自己就不这么干

原文：「我个人偏好一次 ingest 一份、并且全程参与 —— 我读摘要、检查改动、指导 LLM 该强调什么。」 他把批量无监督 ingest 列为「你也可以这样」，而不是推荐做法。

自动化掉的正好是人该干的那部分

原文对分工写得很清楚：人负责搜集素材、指导分析、提好问题， LLM 负责其余的杂活。「什么值得留」本身就是判断 —— 把它自动化，产出的是量，不是知识。

睡一觉多出 30 页你没读过的东西

那不叫知识库，叫失控。 你会不再确定里面有什么 —— 而「我知道里面有什么」正是它比搜索引擎强的唯一理由。 一旦丢掉，这东西就退化成一个更慢的网盘。

提醒的分寸

徽章而不是弹窗，而且可以永久关掉。 这个提醒的目的是「别让收件箱烂掉」，不是催工。 如果用户连着忽略三次，就该降低频率而不是加大声量 —— 那说明他现在不需要，不是他没看见。

一个例外：用户明说了就立刻做

「整理一下收件箱」「把这个视频归档」—— 这类明确指令直接进第 ③④ 步，不用等攒够、不用等提醒。 提醒机制只服务于「用户没主动想起来」的情况。

Spec

让 agent 主动想起知识库

规范全文已写成 docs/知识库-agent规范草案.md。这里只讲两个设计决定和一个必须堵的洞。

决定一 · 规范要写两份，不是一份

全局触发规则库内 schema
装在哪 ~/.claude/skills/eas-wiki/
~/.codex/AGENTS.md 标记段		 <知识库>/CLAUDE.md
<知识库>/AGENTS.md
何时被读到任何项目、任何会话只有工作目录是知识库时
管什么什么时候该去看看到之后怎么读、怎么写、怎么维护
长度必须极短（常驻，每轮都在花钱）可以长（按需加载）

一份写不了。你在代码项目里问「这个交互以前是怎么定的」， agent 的工作目录是代码项目，根本读不到知识库里的 CLAUDE.md。 所以「什么时候该去看」必须住在全局；而详细读写约定放全局，就是每轮都在烧 token。

决定二 · 触发条件要具体，且第一步必须便宜

命中任一即查：
· 「怎么做…」「有没有更好的做法」这类方法问题
· 提到某个人名 / 博主 / 作者
· 问过去的决定、踩过的坑、复盘
· 让你产出文案 / 脚本 / 设计 / 剪辑方案（先看有没有现成方法可用）
· 明说「查知识库」

动作：
先只读 index.md （一个文件，全是一行摘要） → 挑 1–3 篇相关的读 → 回答时注明出处

不查：纯代码调试 / 纯执行任务 / 同一轮已经查过

硬规矩：索引里没有就直说没有，不要用知识库里不存在的内容假装引用

「先只读 index.md」这一条是成本控制的关键 —— 它让「要不要深入」这个判断只花一个文件的钱。这正是原文设计 index 的用意。

洞：规则失效是静默的

三个会让规则悄悄失效的缺口
缺口后果对策
规则里嵌着知识库路径，而技能包是安装那一刻写死的 先装技能包、后建知识库 → 规则里没有路径 知识库初始化 / 改位置时主动重写规则，不等用户再点一次
用户当初点过「永远不要提醒我」或拒装 知识库建好了，agent 却永远想不起它 知识库抽屉里显示规则安装状态，没装就明说
用户手动删了 skills 目录 / 换了台机器 静默失效，不报任何错 每次打开知识库抽屉校验一次

为什么这三条值得单列：规则失效不会报错 —— agent 只是「没想起来」去查，用户看到的现象是「这知识库没什么用」， 然后就不用了。功能死于一个静默的配置问题，而不是死于设计不好。 所以抽屉里那行状态不是装饰：

规则已就绪  Claude ✓  Codex ✓
规则未安装  agent 不会主动查知识库  [安装]

好消息：投递通道已经建好并跑通了

本机实测：~/.claude/skills/eas-term/SKILL.md 在（6116 字节）， ~/.codex/AGENTS.md 里有 eas-term:begin 标记段。 也就是说「把规则装进两个 CLI」这件事已经验证过一整轮（技能包 + 钩子都走的这套）， 知识库规则直接复用，不用重新趟一遍。

Governance

多个模块都要往系统规则里写，怎么不打架

MCP 配置、画板技能包、知识钩子、知识库规则 —— 已经四个模块要动用户的全局配置了， 以后还会更多。先定纪律，不然迟早变成一坨。

先说个现在就存在的问题（实测）

本机 ~/.codex/AGENTS.md 共 3306 字符， 我们的托管段占了 3284 字符 —— 99%。而这个文件是 Codex 的常驻上下文，每一轮都在花钱。

原因：画板技能包那份内容是照着 Claude 的 skill 机制写的 （按需加载，平时只露一行描述），安装到 Codex 时被原样整份灌进了常驻文件。 结果是：你在 Codex 里干任何事 —— 哪怕只是改一行代码 —— 都要先付这 6KB 的画板使用指南。Claude 那边几乎不花，Codex 这边每轮都花。

知识库规则如果照这个路子再加一段，就是雪上加霜。所以纪律得现在定。

四条纪律

#纪律怎么落地
1 每个 CLI 只允许有一个托管区 不是「一个模块一段标记」，而是整个 Eas-Term 共用一段， 内容按当前启用的模块整段重新生成。 这样永远不会出现第二个 begin，加模块减模块都只是重写这一段。 用户写在区外的内容一个字不碰
2 常驻区只放「触发条件 + 去哪读」，不放「怎么做」 这是解决体积的关键。触发条件必须常驻（模型得知道什么时候该动）， 但详细约定、示例、边界说明放磁盘按需读。 Claude 那边天然如此（skill 的 description 就是触发器）； Codex 没有这个机制，就手工做成这个形状
3 一个事实只写一处 画板怎么用写在画板那份，知识库怎么读写在知识库那份，不互相抄。 需要引用就写路径，不复制正文。复制过的东西必然分叉 —— 改了一处忘了另一处，过段时间就开始互相矛盾
4 有一处总账，能一眼看到我们动过什么 「扩展能力」面板列全部触点：改了哪个文件、装了什么、常驻区占多少字符、 能逐个卸。现在这个面板只管技能包，钩子和知识库都在别处 —— 分散的开关等于没有开关

常驻区应该长什么样

<!-- eas-term:begin 由 Eas-Term 维护，勿手改；删掉整段即可移除 -->
# Eas-Term 扩展能力

你运行在 Eas-Term 里。下面是已启用的能力和各自的触发条件，
详细约定按路径去读，不用背下来。

画板：产出了给人看的东西（报告/预览/图）→ 用画板工具摆到用户眼前，别只说"已生成"
      详细：~/.eas/agent/canvas.md

      → 先读 <知识库>/index.md，挑 1–3 篇相关的看
      详细：<知识库>/AGENTS.md

约 300 字符，现在是 3284 —— 缩到十分之一，触发能力不变
为什么「触发条件」不能也挪到磁盘

因为按需读盘要求模型先意识到该读。 详细做法可以晚点读，但「什么时候该动」必须在它眼前 —— 这条挪走了，agent 就永远想不起来去查知识库， 退回到那个静默失效的老问题。

所以切分线是：常驻「什么时候 + 去哪」，磁盘放「具体怎么做」。

Claude 侧几乎不用改

~/.claude/skills/<模块>/ 天生就是一模块一目录、按需加载、能独立删。 知识库直接新建 skills/eas-wiki/ 即可，和现有的 eas-term/ 互不干扰。 要改的只有 Codex 侧那一段。

Onboarding

第一次用怎么知道有这功能

分发场景。复用刚做完的首启引导那套机制，不另起炉灶。

时机做什么
第一次进画布 左缘 guide 直接写「知识库」，未初始化时点开是一屏引导： 这是什么、能干什么、一句话说清「把杂东西丢进收件箱，AI 帮你归位」
选位置 给一个默认建议（~/Documents/Eas 知识库）+「选个别的地方」。 绝不能默认建在 app 内部 —— 卸载/升级会连人带货一起没。 路径存在 userData，跟着用户走
初始化 建六个目录 + _模板/ + CLAUDE.md / AGENTS.md + 一篇「怎么用这个知识库」的示例笔记（让它一开始就不是空的， 空知识库的启动摩擦极大）
git 问一句「用 git 管它吗（推荐，AI 归档出错时能整体撤销）」。 选否则「AI 归档」功能保持关闭并说明原因
已有 Obsidian 库的用户 允许直接指向现有目录。约定文件不覆盖已有内容，按标记插入 —— 这类用户是这个功能最天然的受众，别把他们挡在门外

Dissent

保留的分歧

没有达成一致，或达成一致但风险仍在。不抹平。

分歧 1 · 知识图谱的优先级

你点名要图谱，评审团建议降到最后一期。 代价说清楚：图谱是有观赏价值的，做完能让这个功能「看起来很完整」； 但它对「我干活时想不起某件事」这个真实场景帮助有限。 如果你要的是产品完整度（比如要拿去做演示），那它就该往前排 —— 这是产品定位问题，你定。

分歧 2 · 会不会变成数字仓鼠窝

席 6 的保留意见：个人知识库的经典死法是「只进不出」。 建议做一个极轻的本地计数：放入次数 vs 查询次数。 一个月后如果放 100 次问 3 次，说明它没长成工具，只长成了仓库 —— 那时候该做的是砍掉收集端的花活，而不是继续加功能。

风险 · 知识库变大之后 agent 读不动

Karpathy 模式靠「摘要行 + 标签」筛选，几百篇之内没问题， 上千篇之后光扫一遍目录就吃掉大量上下文。 对策要在第一期就埋下：每个目录一份 INDEX.md，由 lint 维护， agent 先读索引再决定深入哪几篇。等真的长到那个规模再补，改造成本会大得多。
