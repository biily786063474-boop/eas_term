建议

主树两级不变深，把「出现在哪儿」拆成分面。 一级 = 场景（前端·组件 / 前端·视觉 / 前端·动效 / 前端·数据 / 后端·服务）， 二级 = 沿用现在那 40 个「手法」名（它们质量不错，直接换个爹）。 「区块」「端」作为正交标签横切，不进树。 原型图预设是另一个实体（不是词条），它引用区块，区块再引用词条 —— 这才是你要的「页面关系」。

一句必须先说清的

这份改造会推翻 8-31 那份《辞典改造方案》里定的一级分类。 不过那次的活没白干：现在这 9 个一级的下一层（40 个二级）原样保留， 只是上面换了一层。真正作废的只有 9 个一级的名字。

Interpretation

你说的四件事，拆开是四种不同的东西

你一口气说了四层，但它们在数据模型上不是同一类。混着做会做成一棵长不出来的树。

你说的它其实是为什么
「一级分类按场景分，应用在后端还是前端，是视觉风格还是动效」 树 · 一级 成立，直接做。它回答的是「我现在在干哪种活」，一条词条只属于一种活。互斥 → 适合做树。
「前端设计里面的组件」 树 · 二级 现有 40 个二级名（输入与补全 / 玻璃与模糊 / 缓动曲线…）就是这一层，一个字不用改，换个父节点即可。
「对应的前端区块里面，比如出现在金刚区、标签栏、pop up」 分面 · 标签 不能做成三级。「毛玻璃」同时用在导航栏、弹层、卡片；「防抖」同时用在搜索、表单、按钮。 实测 115 条（30%）同时命中 ≥2 个区块，另有 158 条（41%）不属于任何区块（缓动曲线、噪点、金属质感 —— 它们是通用手法）。 塞进树里，这 273 条都要被扭曲。
「预设一些基本的原型图，桌面端和移动端分开，展现页面的关系」 新实体 · 蓝图 这是词典里现在没有的第四种东西。它不是分类也不是词条，是「一张页面由哪些区块按什么顺序组成」。 它引用区块，区块再引用词条 —— 关系是组合，不是归属。

一句话区分「归属」和「组合」

分类树答的是「这条词条是什么」——「弹簧动效」是一种运动规律，只能是一种。
分面标签答的是「这条词条能用在哪」—— 可以用在很多地方，也可以哪都不特指。
蓝图答的是「一张页面由什么拼起来」—— 这是第三个问题，跟前两个都不是一回事。
把第二、第三个问题塞进第一个问题的树里，是分类系统最常见的塌方方式。

Facts

三个先于设计的事实

这三条都是跑数据跑出来的，其中第三条是我在做 POC 时踩到才发现的。

① 区块维度是正交的 —— 数据说得很清楚

一条词条命中几个区块条数占比含义
0 个（不属于任何区块）15841%通用手法：缓动曲线、噪点、金属虹彩、玻璃模糊。它们本来就不该被逼着选一个区块
1 个10828%做成树也没问题的那部分
2 个及以上11530%做成树就在这里崩 —— 要么在多个分类下重复出现，要么被迫二选一丢信息

平均每条命中 1.09 个区块。这个数字本身就在说：它是标签的分布，不是层级的分布。

② 「后端」那一支现在是空的

用后端关键词（接口 / 数据库 / 鉴权 / 限流 / 队列 / 事务 / 幂等 / 网关…）扫全库，命中 38 条。 但逐条看下来，它们全是前端的数据获取手法 —— 乐观更新、游标分页、指数退避重试、SSE、请求去重。 这些属于「前端 · 数据」，不属于后端。

要如实说的

「一级分前端 / 后端」不是重新分类，是开一个空货架。 改完之后点进「后端 · 服务」会是 0 条。
这不是不能做，但它的成本是写 40 条新词条 + 一套新的提示词模板（见后面「要补什么」）， 不是改个分类表就完事。所以我在 MVP 里把它单独拆成一期。

③ 自动打标必须切掉【坑】段 —— 那里写的是反话

词条的 prompt 结尾有一个【坑】段，写的是「别用在哪」。用正则全文扫会把它当成「适用于哪」， 打出来的标签意思正好相反。这不是理论担心，是我跑 POC 时撞到的：

# 被误打上「首屏 Banner」标签的词条，看它们的【坑】段写的是什么：
粒子      →【坑】想要首屏强冲击力时不够看，它刻意很安静。
淡入      →【坑】首屏主标题套上会让用户先看到一片空白。
入场动画  →【坑】长列表逐项套用会显得拖沓，首屏关键信息别靠它延迟露出。
网格      →【坑】想要视觉冲击的 Hero 别指望它，静止时几乎看不见。

切掉【坑】段重跑，效果立刻可量：

指标全文扫（错的）切掉【坑】段说明
「首屏 Banner」候选数26206 条是反话
「页脚」候选数10唯一那条也是反话 —— 页脚其实一条都没有
有区块标签的词条239 (63%)223 (59%)覆盖率降了，但降下来的是假的
这条要写进实现里

任何拿词条文本做自动判断的地方（打标、搜索排序、蓝图推荐）， 都要先按【坑】切一刀。这个坑很隐蔽：不切也能跑出结果，只是有一部分结果的意思是反的。

蓝图：原型图预设（新实体）

它不是词条，也不是分类。一张蓝图 = 一个端 + 一串区块的顺序 + 每个区块的说明。 词条不写在蓝图里 —— 蓝图只引用区块名，界面上点区块时再去词库里按标签实时捞。 这样新增词条会自动出现在所有相关蓝图里，不用回头改蓝图。

  "name": "移动端 · 首页",
  "platform": "移动",
  "slots": [
    { "block": "导航栏",       "note": "沉浸式，向下滚动时渐显底色" },
    { "block": "搜索",         "note": "常驻 or 点击展开，二选一" },
    { "block": "首屏 Banner",  "note": "首屏唯一视觉重心" },
    { "block": "金刚区",       "note": "4 或 5 列，别超两行" },
    { "block": "列表 / 信息流", "note": "无限滚动，注意长列表性能" },
    { "block": "标签栏",       "note": "固定底部，注意安全区" }
  ]
}

为什么蓝图里不直接列词条 id

列了就得维护。381 条词库还在长，每加一条动效都要回头想「哪几张蓝图该加上它」—— 那是必然会烂掉的活。蓝图只声明结构，词条由标签动态匹配，加词条零维护成本。
代价：某个区块标签打错，会在所有蓝图里同时错。所以打标质量比蓝图本身更要紧。

POC 的结论

MVP

三期，第一期两天内能见效

按「改完立刻有用」排序，不按「模型完整」排序。每期都能单独停下。

第一期 · 骨架
一级换成场景，二级原样挂过去
改 dictTaxonomy.ts 的分类表 + dictionary-bundle.json 里每条的 cat1 批量重写（脚本，一次跑完）。 UI 一行不用改 —— 现在的导航就是「一级按钮 + 二级 chip」，换了内容照样跑。
产出：点开词典，一级变成「前端 · 组件 / 视觉 / 动效 / 数据」。零风险，可回滚（映射表是纯数据）。
第二期 · 分面
区块标签：脚本打初稿 + 人工过一遍
给词条加 blocks: string[]。正则只当初稿（POC 里已经看到「按钮」打得过宽）， 381 条我过一遍收敛，重点收「表单 / 按钮 / 卡片」这三个过宽的格子。
UI 加一排区块 chip（和现有二级 chip 同一个组件，多选）。
产出：能按「我在做弹层」筛词条。
第三期 · 蓝图
原型图预设：10 张（移动 5 + 桌面 5）
新增 blueprints.json + 一个蓝图视图：左边选蓝图，中间画区块顺序（简单的竖排方块，不做真实渲染的原型图）， 点区块 → 右边出该区块的词条。
前置：第二期的标签质量。标签不准，蓝图里推的词条就不对。
单独一期 · 可以不做
后端 · 服务
从 0 条开始，要写 ~40 条新词条 + 一套新的提示词模板（见下节）。 它和前三期没有依赖关系，想做随时能加，不想做前三期照样完整。

MVP 明确不做的

  • 端分面（桌面/移动） —— 正则判不准，人工过一遍 381 条的收益不如先把区块做对。蓝图自己带 platform 字段，够用了。
  • 真实渲染的原型图 —— 你说的是「展现页面的关系」，竖排方块 + 顺序 + 说明就够。画成像素级的原型图是另一个量级的活，而且会立刻过时。
  • 删掉旧的 category 字段 —— 它是 'interaction'|'motion'|'visual'，用户机器上已装的 skill 还在按它写（types.ts 里明确注了）。只能加不能改。

三个会咬人的地方

坑 ① · 加字段只改一半，会把已有数据洗掉

dict.ts 的 dict:add 开头就 readUser()，然后把结果整个写回去。 readUser() 有字段白名单 —— 给 UserTerm 加了 blocks 却忘了往白名单里加， 结果不是「读不到」这么简单：此后每加一条新词，就把已有条目的 blocks 洗掉一遍。
2026-08-31 加 cat1/cat2/prompt 时正是这么踩的，dict.ts 第 84 行还留着当时的注释。

坑 ② · 有两份 bundle，没有脚本同步

hooks/dictionary-bundle.json 是提交钩子自带的手工副本， 没有任何脚本会生成或同步它，而且现在已经漂了（条目数比正本少）。
好消息：这次加的 blocks 字段钩子用不上（它只按 zh/keywords 匹配）， 所以这次可以不同步。但如果顺手改了词条的 zh 或 keywords，就必须手工同步过去。

坑 ③ · 一级改名会让已装的 skill 写入失败

dict_add 校验 isValidCat(cat1, cat2)，一级名一改， 用户机器上已装的旧 skill 传的老一级名会当场被拒。
两个办法：(a) 在 isValidCat 里留一张老名 → 新名的别名表（推荐，几行代码）； (b) 校验放宽成「二级有效即可」。
注意 category（interaction|motion|visual）那个老字段无论如何都别动 —— types.ts 里明确写了老 skill 还在按它写。

① 一级到底几个

我给的是 5 个（组件 / 视觉 / 动效 / 数据 / 后端）。
