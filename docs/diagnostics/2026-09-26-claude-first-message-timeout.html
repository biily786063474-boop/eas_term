实际链路

1 · 首次发送

AgentChatView.tsx 调用 agentChat:start；主进程创建会话后立刻返回 ok:true，此时不代表 CLI 已启动。

2 · 启动准入

session.ts:823–852 将 Claude 启动标为 interactive:true 送入运行资源调度器。交互型绕过后台并发上限，但在 critical-pressure 下仍被挡住。

3 · 超时和提示

scheduler.ts 默认 60 秒后抛 wait timeout；startupFailure.ts 翻译成用户看到的文案。消息没有交给 Claude Code。

4 · 界面状态

界面在 start 返回成功后即清空输入框并显示用户气泡。异步准入失败只追加错误，不把原文还原到输入框，也没有针对这条失败消息的一键重发。

发现与证据

优先级发现证据 / 边界建议
P1warning 被升级为 criticalruntime/controller.ts：critical = pressure === 'critical' || pressure === 'warning'；manager.ts 的交互闸门只在 critical-pressure 关闭。模拟 warning 时 0 次启动、60 秒后得到同一提示；normal 可立即启动。明确 warning 的交互准入策略；只把真正 critical 当作硬拦截，并增回归测试。
P1失败原因被错误翻译startupFailure.ts 用 /timeout/i 匹配任意启动错误。模拟 spawn timeout、network timeout 都被误报为“等待资源超时”。用结构化的队列超时错误码，而不是字符串模糊匹配。
P1首条消息恢复体验不足AgentChatView.tsx 在进程尚未获准启动时清空输入框；异步失败无一键重发。自动重试被刻意禁用，避免用户不知情地延迟执行。保留原消息，并提供用户确认的“重新发送”；不要静默自动重试。
P2事后难以定因资源监视可在排队时看到策略原因，但错误文案和 agent-sessions.log 不记录当时的压力等级、平台校准状态与队列原因；最近任务记录重启即消失。增加脱敏的准入结果/超时诊断记录，便于客服辨别资源、采样或其他启动错误。

排除与限制

  • 这句文案不是 Claude Code 的回复；真正的登录失败、CLI 未安装或模型报错走不同路径。
  • CLI 安装/登录进程自身不进入此资源队列，但可间接造成机器内存压力；没有客户读数，不能认定本次确实发生。
  • 资源准入只在 Darwin 25 + arm64 且采样校准通过 时启用；其他系统会禁用该闸门。若客户不符合此条件，优先怀疑“任意 timeout 被误译”或版本/现场信息不一致。
  • 本机当前 macOS 压力为 normal，不能借本机现状推断客户 60 秒内的状态；本轮未取得客户设备日志。
