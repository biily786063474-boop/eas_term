密钥管理器

在 Eas-Term 里放一个带锁的密钥柜：AI 能用它们干活，但密钥本身永远不进入对话、 不上传给模型厂商。AI 遇到需要新密钥的场景时，直接弹窗让你填。

裁决

按 「密钥不进对话」 而不是 「LLM 读不到」 来定位，这个功能立刻从 「安全幻觉」变成「实实在在解决问题」。核心机制复用现有的 PTY 注入， 六位码改成「人在场证明」而非加密密钥，v1 只支持环境变量场景。

必须先说清的一条

「LLM 不能直接读密钥管理器」这个目标做不到。只要密钥能在 AI 跑命令的终端里被使用，AI 就能读到它：

  • 注入成环境变量 → echo $OPENAI_API_KEY 一行就出来了
  • 只给路径 → AI 有 Read 工具，拿到路径就能读文件内容
  • 只给变量名 → env | grep -i key 一样能翻出来

这不是实现好坏的问题，是同一个进程里的东西没法对该进程隐藏。 任何声称「AI 能用但读不到」的设计，都会在第一次 prompt injection 时破功—— 而那时用户还以为自己是安全的。

一句话威胁模型

信任「我主动让它在这台机器上跑命令的那个 AI」， 不信任「密钥被上传到第三方并长期留存」。

这个边界是诚实的，也守得住。而且它和你已有的处境一致——你本来就让 AI 读你全部代码了， 再纠结它能不能 echo 一个 key 意义不大；但让 key 永久留在别人服务器上，是另一回事。

UI 文案红线

界面上不能出现「AI 无法读取」「密钥对 AI 不可见」这类表述。 正确说法是「密钥不会出现在对话里，也不会上传」。 这一条要写进 UI 评审清单——一句话写歪，整个功能的诚信就没了。

Passcode

六位码：当「人在场证明」，不当加密密钥

六位数字只有 100 万种组合，本地离线暴力破解只要几秒。如果加密密钥从它派生，等于没加密。

错误做法

六位码 → KDF → 加密密钥 → 加密的密钥库文件

库文件一旦被拷走（备份、同步盘、恶意脚本），几秒钟就能爆破出全部密钥。 再高成本的 KDF 也只是把「几秒」拖成「几分钟」。

建议做法

真正的保护交给系统钥匙串
（macOS Keychain / Windows DPAPI）

它有硬件加密和系统级访问控制，密钥库文件被拷走也没用。 六位码只负责「证明是人在操作」。

六位码真正的职责

  • 防「你去倒杯咖啡，AI 自动化地把所有密钥全注入了」
  • 防「同事借你电脑用一下」
  • 给一次危险操作（注入、导出、删除）一个明确的人工确认点
忘了六位码怎么办（2026-07-31 定）

换一个新码，密钥一条不动。UI 上是「忘记六位码了？」→ 警示页 → 设新码。

看着像后门，其实不是，理由就是上面这一节：六位码从来不是加密边界。 密钥是钥匙串加密的，跟这六位数没关系 —— 把 secrets.json 的 lock 段删掉、重启、设个新码，所有密钥照样解得开。 能编辑那个文件的人本来就能绕过，不在 GUI 上铺这条路挡不住任何真会来的人， 只会让忘了码的自己人把几十条云凭证全部重新生成一遍。

两个刻意的设计：（1）警示文案必须说清「换完柜子就是开的」， 绝不写成「找回密钥」—— 它不是找回，是换一把新锁。 （2）连续输错的指数退避不管这条路：退避防的是在线猜码，而换锁根本不用猜。 真正的摩擦放在那一页警示上。

被否掉的两个方案：「重置即清空」——安全上更干净，但代价是全丢重录， 而它挡住的攻击者本来就有别的路，等于只惩罚自己人； 「重置前过 Touch ID」——最正确，但 Electron 没有内建 API， macOS 要靠带 ACL 的钥匙串条目触发系统弹窗、Windows 侧要另接 Windows Hello， 对单人项目工程量不成比例。将来真需要再说。

因为不承担加密强度，它可以做得很快——不需要 KDF 拖慢，体验好。配套的：

策略建议值理由
解锁有效期15 分钟无操作自动锁够用完一轮活，又不至于忘了锁
错误尝试5 次后锁 5 分钟，指数退避让在线猜测不可行
敏感操作导出 / 删除 / 批量注入需重新输码解锁态不等于可以做任何事
忘记密码不提供找回，只能清库重建有「找回」就有绕过路径

Injection

注入机制：这条路你已经铺好了

Eas-Term 现在就在做同样的事——pty:create 时往终端注入 MCP 的端口和令牌，那两个值从没出现在任何对话里。

现有机制（src/main/mcpBridge.ts:31）

export function mcpEnv(ctx: Ctx): Record<string, string> {
  return {
    EAS_TERM_PORT: String(port),
    EAS_TERM_TOKEN: token,     // ← 令牌从没进过对话，但终端里能用
    ...
  }
}

// src/main/pty.ts:237
Object.assign(env, mcpEnv({ ptyId: id, project: cwd }))

密钥走同一条路

用户 在 GUI 勾选「这个终端需要 OPENAI_API_KEY」
  ↓ 六位码确认
主进程 从钥匙串取值
  ↓
pty:create 注入 env  （和 EAS_TERM_TOKEN 完全一样的路径）
  ↓
AI 在终端里 curl -H "Authorization: Bearer $OPENAI_API_KEY"
     它只知道有这个变量名可用，值没在对话里出现过
实现时改掉的一处（2026-07-31）

一条 = 一组变量，不是一条 = 一个变量。 最初按「一条一个变量」写完了，试 AK/SK 场景时发现是设计错误： AccessKeyId 和 AccessKeySecret 本来就是一个凭证，拆成两条会出现 删了一半、自动注入只开了一半这种半残状态，而这两种状态都只会在 终端里报一个看不懂的鉴权错误。受影响的不止 AWS——阿里云、腾讯云、 数据库那套 host/user/password、OAuth 的 id/secret，全是成组的。

改完后一次提交能填多个变量，另配了三家云的预设和「从 .env 整段粘贴」。 变量名跨条目也必须唯一——它们最后注入的是同一份 env，重名会互相盖掉， 所以保存时挡住并说清是被哪一条占了。老格式（v1）读进来自动包成单元素的组，值不动。

关键设计

按终端授权，不是全局注入。 「给这个终端一个 GitHub token」和「给那个终端一个数据库密码」互不干扰。 这既是最小权限，也限制了恶意依赖包能偷到的范围。

需要配套的细节

问题处理
已经开着的终端怎么加密钥？env 无法追加到已存在的进程。要么开新终端，要么给一条 export 命令由用户自己粘（那样会进 history，需提示）
终端节点上要看得出注入了什么节点头部显示钥匙徽章 + 数量，hover 列出变量名（只列名字不列值）
变量名冲突入库时校验；同一终端内不允许重名
子进程全继承无法避免。文档里明说，并在注入确认弹窗里提示一次

Request Flow

AI 主动索要密钥：这个设计我认为是对的

比现在的流程（AI 说「你去申请然后贴给我」→ 你贴进对话）安全得多，而且省事。做成一个 MCP 工具。

request_secret(name, purpose, docs_url?)

  AI 调用 → 弹窗：
    ┌────────────────────────────────────────┐
    │ ⚠ AI 请求你提供一个密钥              │
    │                                        │
    │ 变量名   OPENAI_API_KEY                │
    │ AI 的理由 「需要调用 GPT 做摘要」       │
    │ 申请地址 platform.openai.com/api-keys  │
    │                                        │
    │ [密钥输入框 ●●●●●●●●]                   │
    │ 作用范围 ○ 仅此终端  ○ 保存备用         │
    │                       [取消] [保存]     │
    └────────────────────────────────────────┘

  返回给 AI 的只有 → { saved: true, name: "OPENAI_API_KEY" }
                        值从未经过 AI
两个必须防的坑

1. AI 可能伪造用途骗你填别的东西。 比如谎称「需要你的银行验证码来完成部署」。弹窗必须：

  • 醒目标注「这是 AI 发起的请求」，视觉上和系统弹窗区分开
  • 原样显示 AI 给的理由，不要帮它润色成看起来更正当的样子
  • 对高危名称（含 password / 身份证 / 验证码 等）额外警告

2. 限流。不然一个跑飞的 agent 能连弹几十个窗。建议每分钟最多 1 次、连续取消 2 次后本轮会话禁用该工具。

实现时砍掉的一处（2026-07-31）

「仅此终端」这个作用范围做不到，已删。 上面那张图里画了「○ 仅此终端 ○ 保存备用」，实现时才发现前者在架构上不可能： 进程的环境变量在 spawn 那一刻就定死了，PTY 已经在跑，没有任何办法从外面塞进去。

唯一的歪路是往终端里敲一行 export VAR=值 —— 那会把密钥明文写进 shell history，正好毁掉整个方案的立足点。不做。

所以改成：只有「存进密钥柜」一种，并且明确告诉 AI「当前终端读不到，得开新终端」。 这句提示是必需品不是客套 —— 不说清楚的话 AI 存完立刻去读 $VAR， 读到空值然后开始瞎猜，最后多半会绕回「你把 key 贴给我吧」。 用户侧弹窗里也写了同一句话。

The Hard Part

配置文件类工具：v1 建议不做

这是整个方案里最脏的一块。很多工具根本不读环境变量。

工具读哪能用 env 吗
AWS CLI~/.aws/credentials能 AWS_ACCESS_KEY_ID 等
npm publish~/.npmrc部分 NODE_AUTH_TOKEN 需配合配置
Docker push~/.docker/config.json不能 得先 docker login
kubectl~/.kube/config不能
SSH / Git~/.ssh/不能 但有 ssh-agent

三条路，各有代价：

A. 写明文配置文件

用完即删。
问题：中途崩溃就留在盘上了；而且窗口期内任何进程都能读。

不推荐

B. 借力原生 agent

ssh-agent / git credential helper 这类本来就是干这个的。
问题：每个工具一套，覆盖面窄。

推荐（按需逐个加）

C. 只给引导

GUI 里放一键「打开 docker login」并把密钥填进去，由官方工具自己落盘。
问题：不算「管理」，只是省了翻找。

v1 折中

建议

v1 只做环境变量，把边界在 UI 上说清楚（「这类工具需要你自己 login 一次」）。 不要为了覆盖率去做 A 方案——写明文配置文件会把整套保护的意义抵消掉， 而且失败模式（崩溃残留）很难测。

P1 的验收标准

  • 密钥库文件被拷到另一台机器 → 打不开（钥匙串保护生效）
  • 翻遍 ~/.claude/projects/*.jsonl → 搜不到任何密钥明文
  • 注入过密钥的终端里 history → 搜不到密钥
  • 锁定状态下调 request_secret → 要求先解锁，不静默失败
  • 15 分钟不操作 → 自动锁，已注入的终端不受影响（进程 env 已经在那了）

下一步

这份文档只到「设计成立」为止。动手前还有两个决定要你拍。

决定一：存储后端

纯钥匙串（每条密钥一个 Keychain item）——最安全，但 Windows 侧要另写 DPAPI 实现，跨机器同步不了。

钥匙串存主密钥 + 自己加密的库文件——一份实现两个平台，将来能加同步，但多一层自己写的密码学（出错风险在这）。

决定二：入口放哪

标题栏图标——和「扩展能力」并排，随时可达。

画布左抽屉——和知识库同一层，但画布模式才有；终端模式下够不着。

复制这条粘回对话
开工 P1，存储用纯钥匙串，入口放标题栏

改哪个词都行——比如「存储用加密库文件」「入口放画布抽屉」「先只做 P1 的存储层，注入下一轮再说」。
