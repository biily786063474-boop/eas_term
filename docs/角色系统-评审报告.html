裁决一 · 词典

不会更新，而且比你想的更靠前一步：那个 hook 根本不产生新词。 它是「命中记录器」不是「造词器」—— 拿提交的新增代码行去匹配那 242 条固定词典， 把本项目第一次出现的词记进 <项目>/docs/knowledge-data.json。 就算它真产出了新词，气泡也读不到：词典是 Vite 静态 import 编译进包的，运行时不碰磁盘。 两层都要改，工程量都不大。

裁决二 · 角色系统

做，但不按「人设」做。 评审团一致认为：角色的价值不在「你是一个资深架构师」这种提示词， 而在于把每次开终端要重复交代的东西固化下来 —— 用哪个模型档位、能碰哪些工具、产出物落在哪、什么算做完。

角色 = 可执行的五元组，不是一段人设文案。 人设那部分模型本来就会演，固化它没有收益；工具白名单和输出契约固化下来才真的减负 —— 也才真的能把「生图只走笔纵/Lovart」这类红线编码进系统，而不是每次靠提示词提醒。

反对意见 · 已保留，未消解

1. 不建议单开第三个顶级标签页。 你用角色的时机永远是「我要开个终端干活」，那一刻你人在画布上。 单开标签页会让它变成一个要专门去访问的地方，而它本该是个顺手的选择。推荐做成画布抽屉的一个分区。 —— 但这条你说了算，标签页方案我也设计完整了，见「放在哪」。

2. 「专门使用工具的」不该是角色。 它不是一类岗位，它是每个角色都有的一个字段（工具白名单）。 单独立一个「工具人」角色，等于承认其它角色不会用工具 —— 那是错的。建议取消。

裁决三 · 分发（补充追加）

「让用户无感知地装上 Claude Code / Codex」做不到，也不该做 —— 第三方付费 CLI、要用户自己的账号登录、静默装全局 CLI 会被安全软件判定为恶意行为。 能做到的是「一次点击 + 全程看得见」：把安装做成画布上一个预填好命令的终端节点。 另外发现一个当前的洞：两个 CLI 都没装时，app 什么提示都不给，用户只看到一堆点了没反应的控件 —— 这是分发阻塞项，排到第 0 期。详见「分发与获取」。

③ 的两个坑，必须先解决

坑一：现在这个 hook 分发出去 100% 失效。 ~/.claude/settings.json 里它的命令是 /opt/homebrew/bin/node '/Users/biily/Biily/Projects/复盘skill（总结名词）/scripts/scan-commit.mjs' —— 绝对路径指向你本机的另一个项目，还写死了 Homebrew 的 node。 要装给别人，脚本必须随 Eas-Term 打包进 Resources，并且用运行时探测到的 node。

坑二：写 settings.json 必须是合并，不能是覆盖。 技能包那边是独立文件（Claude）或带标记的段落（Codex），怎么写都安全； hook 要塞进用户 settings.json 的 hooks.PostToolUse 数组里 —— 那是用户自己的配置文件。必须按标记幂等增删、写前备份。 这类活我们已经踩过一次：之前用正则改 Codex 的 TOML，把你真实配置截断了，最后改成逐行扫描才稳。这次直接用逐条比对，不碰正则。

顺带发现：Codex 现在也有 hooks，可能也有 skills

codex --help 里有 --dangerously-bypass-hook-trust，说明 Codex 已有 hook 机制和「hook 信任」模型； ~/.codex/skills/ 目录也已存在（当前为空）。 而 agentSkill.ts 的注释还写着「Codex 没有 skill，全局指令走 AGENTS.md」。 做 ③ 之前先复核一遍 Codex 侧的现状，别按过时假设写。

Panel

评审团讨论

五席，各自只对自己那个维度负责。下面是各席的核心主张和相互交锋。

席 1 产品 · 认知负担

「用户是一个人，不是一家公司。」 你列的 8 项里有一半是同一件事的不同说法。一个人能稳定记住并主动切换的角色， 经验上是 5–7 个，超过就退化成「反正都差不多，随便选一个」。 更关键的是：角色必须能在开终端的那一步顺手选，多一次跳转就没人用。

席 2 Agent 工程 · 什么真的起作用

「人设是最弱的那根杠杆。」 同一个模型，给它「你是资深架构师」和不给，行为差异远小于 「你只能读不能写」和「你能写」的差异。 真正改变产出的是三样：工具白名单（能碰什么）、 输出契约（产物是什么形状、落在哪）、完成判据（什么算做完）。 角色系统应该固化这三样，人设那句话可以有，但别当主菜。

席 3 架构 · 落到现有机制上

「地基已经打好了，别另起炉灶。」 NodeAgent 已经按终端节点存了 kind / model / effort / session， 角色无非是多一个 roleId 字段 + 一张角色定义表。 但有个硬约束：Claude Code 的 --resume 不重放 system prompt。 所以「改角色」不能就地生效，必须提示新开会话 —— 这个约束要写进 UI，不能藏着。

席 4 成本 · token 预算

「主席团是这里面唯一贵的东西。」 一次评审起 4 个视角的 session，就是 4 倍成本。 普通角色不额外花钱（本来也要开终端），但主席团必须显式标注成本并让你确认， 不能变成一个手滑就烧掉一次的按钮。另外：低价值角色应该默认降档 —— 写文案用 Opus 极限档是纯浪费。

席 5 怀疑论 · 这是不是伪需求

「先承认一件事：你现在没有角色系统，活照样干完了。」 所以要老实回答它到底省了什么。我的判断是省了两样，都是真的：

  • 省重复交代。每次新开终端都要说一遍「产物放 docs、改完要验证、别碰生产代码」，角色把这些变成默认值。
  • 省越权事故。「生图只走笔纵/Lovart」现在靠全局 CLAUDE.md 提醒，模型可能漏读。做成工具白名单就是硬约束。

但它不省的：不会让模型变聪明，不会让你少想。 如果指望「选个架构师角色就能出好架构」，那会失望。角色是护栏，不是加速器。 这一点必须在 UI 措辞上摆正，否则期望管理会崩。

硬约束 · 改角色不能就地生效

--resume 不重放 system prompt。 也就是说：一条会话开始时是什么角色，它这辈子就是什么角色。 在 UI 上改一个正在跑的终端的角色，模型那边什么都不会变。

所以改角色时必须明确二选一：① 就地改（只影响下次全新启动，当前会话不变）； ② 换角色并新开会话（当前会话另存）。 不能默默地改，那会让人以为生效了。这一条我在实现时会做成一次明确的二选一弹窗。

工具白名单靠什么落地

三层，从强到弱，建议全上：

  • MCP 层 —— eas-mcp.mjs 按角色过滤 tools/list 返回值。模型根本看不到不该用的工具。这是最硬的一层，也是画师红线的落点。
  • CLI 层 —— Claude Code 的 --allowedTools / --disallowedTools。管的是内置工具（Write / Bash 之类），验官的「禁改代码」靠这层。
  • 提示层 —— --append-system-prompt 写清产出契约和完成判据。最弱，但负责传达「什么算做完」这种没法用开关表达的东西。

Distribution

用户什么都没装，怎么办

这是分发场景下最核心的一个问题。先划边界：有些事做不到，硬做会毁掉信任； 剩下的部分能压到一次点击。

先说做不到的

「用户无感知地把 Claude Code / Codex 装上」——做不到，而且不该做。不是工程难度问题：

  • 它们是第三方付费 CLI，必须用用户自己的账号登录。装上了没账号也是废的。
  • 静默在别人电脑上装一个全局 CLI、改 PATH —— 这是恶意软件的行为特征。 macOS Gatekeeper、Windows Defender 都会盯上，我们刚做完签名公证，不值得为这个赔进去。
  • 就算装上，第一次运行还是要开浏览器登录。这一步永远绕不过去。

所以目标不是「无感知」，是「一次点击 + 全程看得见」。

方案：把安装做成画布上的一个终端节点

Eas-Term 有个别的 GUI 应用没有的优势 —— 它本身就是个终端。安装这件事不需要藏在后台， 可以直接摆在用户眼前跑：

认知成本低用户不需要知道「用 npm 还是 brew」「装哪个包名」—— 命令替他填好了，他只按回车
完全透明跑的每一个字都在屏幕上。不是「后台正在安装…」的转圈，是真实终端输出
出错可自救公司网络 / 代理 / 权限问题导致失败时，报错就在眼前，可以直接复制去问 —— 而不是一句「安装失败」
不越权命令是用户自己敲回车执行的，我们只是填了内容。责任边界干净，也不会被安全软件判定为静默安装
实现前必须核对的一件事

预填哪条命令，取决于用户机器上有什么。不能写死一条。

  • 有 node/npm → 走 npm 全局安装（两家都提供）
  • 没有 node → 走各自的原生安装脚本（不依赖 Node 运行时），Windows 走 PowerShell 那条
  • 有 Homebrew（mac） → 可以优先 brew，用户后续更新更顺手

具体命令在实现时必须去官方文档现查一遍再写死， 这类安装入口会变，凭记忆写下去的后果是用户第一步就卡住。检测逻辑可以复用 agentSkill.ts 里现成的 hasCli()。

CLI 装不了是外部约束；但我们自己产出的配置是可以做到零感知的 —— 前提是分清哪些该静默、哪些必须问。 这条线不是洁癖，是有代价的：我们已经用正则改 Codex 的 TOML，把你本机真实配置截断过一次。

对「一条提示就装好」的保留意见

你希望把这几件事合并成一条提示 —— 大部分可以，但 hook 那条我建议单独问。 技能包只是「模型多读一份说明」，hook 是在用户每次跑命令时插入我们的代码。 这两件事的量级不一样，混在一个「一键配置」里，等于用一个泛泛的同意换走了一个具体的授权。

建议的分法：首启一条提示搞定「MCP + 技能包 + 角色」（都是低侵入或我们自己的地盘）； hook 等到用户第一次真的用到词典时再就地问一次 —— 那时候他知道这是干嘛的，同意才有意义。

一个 CLI 都不装的用户怎么办

现在的行为是：什么都不说。 needsAttention 的判据是 hasCli && 没装技能包 —— 两个 CLI 都没有时它永远是 false，不弹提示、不给解释。 用户看到的是一堆点了没反应的 agent 控件，不知道为什么。这是当前最该补的一个洞。

改法：agent 层整体降级，而不是坏在那儿。

  • Agent 控制条、角色分区 整体隐藏，换成一行「装 Claude Code 或 Codex 解锁 agent 能力 →」
  • 角色系统降级成终端预设（工作目录 + 环境 + 命名），仍然有用
  • 终端、画布、文件预览、词典 全部照常 —— 这才是这个 app 的地基，不该被 agent 绑架

Agent Choice

拖角色进去时能选 Claude 还是 Codex 吗

能，而且几乎不用加新 UI —— 现有结构已经把这件事准备好了。

答案

NodeAgent 里 model 和 effort 本来就是按 kind 各存一套 （{claude: 'opus', codex: 'gpt-5-codex'}），角色照抄这个结构即可。 切换 agent 时两边配置互不覆盖 —— 这个坑之前已经踩过并修好了，直接复用。

场景行为
角色指定了 CLI 拖进去直接用它。适合有明确偏好的角色（比如你觉得某个 CLI 写代码更顺手）
角色设为「跟随」默认 装了哪个用哪个；两个都装 → 用全局默认；全局没设 → 用上次用的那个
拖进去之后想改 不用加 UI —— Agent 控制条上的 [Claude | Codex] 段控件就在那儿， 按 ▶ 启动前随时能翻。翻完模型/档位胶囊自动跟着换
只装了一个 CLI 另一个置灰并给出说明，不是隐藏。隐藏了用户永远不知道有这功能
启动之后再改 受「--resume 不重放 system prompt」约束 —— 和改角色一样， 必须走那个二选一弹窗，不能默默改

唯一要新增的：角色卡上加一枚 agent 选择器（Claude / Codex / 跟随）， 三选一。这是角色五元组之外的第六个字段，也是唯一因为分发场景才需要加的字段。

Placement

放在哪：两案并陈

这是保留的分歧之一。你要的是 A，评审团推荐 B。两案都设计完整，你拍板。

A 案 单开顶级标签页 （你的原始需求）

标题栏： 终端 │ 画布 │ 角色

┌─ 角色页 ──────────────────┐
│ 左：7 张角色卡（可编辑）      │
│ 中：本项目分工看板           │
│    · 哪些角色有活跃会话      │
│    · 各自在跑什么            │
│ 右：一键「按角色起终端」      │
│    → 在画布对应 Frame 建节点 │
└──────────────────────────┘

好：角色是一等公民，编辑和总览的空间充裕，将来扩展（角色统计、成本归因）有地方放。
坏：多一个顶级视图 = 多一层认知；用角色的时机在画布上，跳过去再跳回来； 分工看板对一个人来说信息量偏虚 —— 你本来就知道自己在跑什么。

B 案 画布抽屉里加一个分区 （评审团推荐）

右侧资源抽屉：
  项目
  文件
  组件
  角色  ← 新增分区

用法：
  · 拖角色 → 落 Frame = 按该角色起终端
  · 点角色 → 编辑它的五元组
  · Frame 头部「新建终端」按钮
    改成带角色下拉的分裂按钮

好：零新增顶级入口；和「拖项目/拖文件/拖组件入画布」的心智完全一致； 选角色就发生在开终端那一刻，不用跳转。
坏：抽屉已有 3 个分区，加第 4 个会挤；角色编辑界面塞在窄抽屉里不舒服（可点开弹独立面板缓解）。

我的推荐

B 案，但把「角色编辑」做成弹出的独立面板，避开抽屉太窄的问题。 理由是席 1 那句：角色的使用时机永远是「我要开个终端干活」，把它放在那一刻手边，比给它一个专属房间更有用。

如果你还是想要 A 案，那我建议两个都做但有主次：抽屉分区负责「用」，标签页负责「管」（批量编辑、成本统计）。 先做抽屉，标签页等角色真的用起来、确实需要一个总览的时候再加 —— 而不是现在就为一个还没被验证的需求造一个顶级视图。

Dissent

保留的分歧与风险

这些没有在评审中达成一致，或者达成了一致但风险仍在。不抹平。

分歧 1 · 标签页 vs 抽屉

见上一节。你说了算，但请知道代价：顶级视图一旦加了就很难删， 而它的价值取决于「角色分工看板」对单人有没有用 —— 这一点评审团内部没有共识。

分歧 2 · 角色会不会变成摆设

席 5 的保留意见：护栏型功能的典型失败模式是「第一周认真选，第三周全用杂役」。 判断它是否成功的唯一标准是 —— 三周后你还在选角色吗？ 建议做一个极轻的埋点（本地计数，不上报）：各角色被启动的次数。 如果三周后杂役占比超过 70%，这个系统就该砍掉或重做，不要留着装点门面。

风险 · 角色定义文件被改坏

roles.json 是用户可编辑的。改坏了不能让画布起不来 —— 按 canvasSlice.ts 里 sanitizeCanvas 已有的思路：逐条规范化，坏的那条丢掉而不是整个文件失败， 全坏就退回内置 7 角色。这个教训你们已经付过学费了，直接复用。
