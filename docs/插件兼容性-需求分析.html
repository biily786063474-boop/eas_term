2026-08-24 订正 · 实施后回填

本文最初是动手前写的分析，实施过程中四处推断被实测推翻，已就地改正。原文保留结构，改动点都标了「订正」：

  1. L2 的范围小一半 —— Codex 那边不需要做任何事
  2. OAuth 不用我们管 —— Codex 在安装时就处理了
  3. 插件有两种形状 —— 连接器型本地什么都没有
  4. ChatCut 那类插件的界面有解 —— 走已有的网页节点
裁决

需求要拆成两半看，一半不成立、一半成立。

  • 不成立 「插件作为独立模块或分屏被插入」—— Codex 与 Claude Code 的插件 都不包含任何界面代码。它们贡献的是提示词（skills）、工具（MCP server）、行为（hooks）。 没有可渲染的东西，所谓「插入一个模块」无从谈起。
  • 成立 「装了插件后能在 Frame 双击菜单里选到、并在画布上用起来」—— 这条完全可行，而且 Codex 插件自带完整的展示元数据（显示名 / 图标 / 品牌色 / 分类 / 默认提示词）， 我们不需要为每个插件写适配。
必须先纠正的一个预期

如果你期待的是「点一下 Linear 插件，画布上出现一个 Linear 的看板界面」—— 那需要我们自己定义一套 Eas-Term 插件协议（见 L3），而不是兼容 Codex 插件。 Codex 插件里的 .app.json 只有一个远程 app id（asdk_app_69a0…）， 指向 ChatGPT 那边托管的界面，我们这边渲染不了。

Codex 插件的 interface 块 —— 这是好消息

以 linear 为例，清单里现成就有渲染一个条目所需的全部字段：

  "category":         "Productivity",

  "composerIcon":     "./assets/linear-icon.svg",
  "logo":             "./assets/app-icon.png",
  "defaultPrompt":    ["Triage or update relevant issues for this task…"],   ← L1 的关键

}

而它的工具面是一个远程 HTTP MCP + OAuth：

"mcpServers": {
  "linear": {
    "type": "http",
    "url":  "https://mcp.linear.app/mcp",
    "oauth_resource": "https://mcp.linear.app/mcp"    ← 认证由谁走？见风险
  }
}
关键否定发现

两个生态的插件都不含 UI 代码，一行都没有。 Codex 的 .app.json 是 {"apps":{"linear":{"id":"asdk_app_…"}}} —— 一个指向远端的标识符，不是可执行的界面。 所以任何形如「把 codex 插件渲染成画布模块」的方案，本质上都是 我们自己写那个界面，插件只提供数据源。这一点必须在动手前对齐， 否则会做到一半才发现要给每个插件手写适配。

为什么 L1 单做会是空壳

L1 只负责「开一个会话并预填提示词」。如果 L2 没做，那个会话里 根本没有 Linear 的工具 —— 模型会照着提示词去找工具、找不到， 然后回一句「我没有访问 Linear 的能力」。 这和我们 2026-08-23 刚修完的画板 MCP 那个 bug 是同一个形状： 规则说你能做，工具却不在。不要再犯第二次。

Conflict

与刚落地改动的已知冲突

L2 会直接撞上两天前刚定的两个决策，必须一起想清楚。

订正 ①②③

下面这节说的问题只对 Claude Code 成立。 2026-08-24 实测：

  • codex exec 不带任何 MCP 限制（adapter 只传 --json --sandbox -m -c）， 读的是用户全局 toml —— 插件在 AI 对话里本来就能用。 实测在会话里拿到 mcp__codex_apps__github._get_profile。
  • OAuth 由 Codex 在安装时处理（市场条目里 policy.authentication: "ON_INSTALL"）， 不需要我们弹窗 —— 原文那条风险取消。
  • 插件有两种形状：连接器型（如已装的 GitHub，清单里只有远程 app id， 本地既无 .mcp.json 也无 skills/）与本地型（如 linear、claude-mem）。 只有本地型有东西可合并。

冲突一：--strict-mcp-config 会挡住插件的 MCP仅 Claude

AI 对话那条路无条件带 --strict-mcp-config（adapters/claude.ts）， 语义是「只用 --mcp-config 给的，忽略其它一切」。 而我们生成的 agent-mcp.json 现在只放 eas-term 和 bizone-canvas 两个。

结果：用户在 Codex 里装的插件，其 MCP server 在 AI 对话会话里不存在。

三个选项：

做法代价
把选中插件的 MCP 合并进 agent-mcp.json推荐 工具面仍然可控，只多了用户明确点选的那个
去掉 --strict-mcp-config不建议 工具面变成用户全局的全集，不可控 —— 这正是当初加它的原因
只在终端里用插件，AI 对话不管保守 但那样「双击菜单里的插件选项卡」就没有意义了

冲突二：每个插件 MCP = 每会话一份连接

2026-08-23 实测：每个 AI 对话会话已经挂着 eas-term（19MB）+ bizone-canvas（31MB）两个 MCP 进程。插件的 MCP 多为 远程 HTTP（如 https://mcp.linear.app/mcp）， 不额外起本地进程，这一点比想象中好 —— 但每会话仍是一条独立的 HTTP + OAuth 连接。

要定的规矩

不要「装了就全带上」。 180 个插件如果都进工具面， 系统提示词会被工具定义撑爆（画板 52 个工具已经让单轮输入涨了约 39k token）。 规矩应该是：只带用户在这次会话里明确点选的那一个。

给 LLM 的操作手册要改哪几面

项目已有成熟的「六个注入面」规范（.claude/skills/agent-onboarding/SKILL.md）。插件这件事落在其中三面。

面名称这次要不要动写什么
1常驻规则（托管区）要 加一条触发条件：用户提到某个集成（Linear / Slack / Figma / Notion…）时， 先查该插件装没装，别直接说「我做不到」。
按面 1 的纪律：只写触发条件 + 去哪读，正文一个字不放。
2技能包正文（按需读）要 怎么列已装插件、怎么在 Frame 里开一个带插件的会话、 两阶段确认的话术、装插件的命令只给不跑。
3MCP 工具看 L2 怎么定 如果采纳「只带点选的那一个」，这里要写清合并规则与何时重启会话 （MCP 配置是会话启动时定的，中途改不了）。
4提交钩子不动与插件无关
5库内说明书不动与插件无关
6会话驱动（入方向）可能要 若插件属于 Codex，L1 点选后必须用 codex 起会话而不是 claude —— adapter 选择要跟着插件归属走。
一条必须写进手册的纪律

LLM 不许代跑 codex plugin add / claude plugin install。 理由与 agentInstall.ts 里的既有纪律同源： 「静默装全局 CLI + 改 PATH 是恶意软件的行为特征」。 正确做法是把命令预填进终端交给用户按回车，和现在装 CLI 的做法保持一致。

Risks

风险与未决问题

前三条会影响方案形状，必须动手前定；后两条是实现期再处理。

已答 chatcut 是什么

用户 2026-08-24 确认：是 Codex 插件，并且自带一个 Web 剪辑界面 （素材库 / 时间轴 / 预览，跑在浏览器里）。本机仍搜不到它（不在 openai-curated 的 180 个快照里），所以未能实测其清单。
形状已明确：插件给工具，界面是独立 Web 应用 —— 正好对应 L3 那行的订正， 用 canvas_open_url 开成画布节点即可，不需要自建插件协议。

已消 OAuth 谁来走

不用我们管。 市场条目里写着 policy.authentication: "ON_INSTALL"（180 个里 177 个如此）—— 授权在安装那一刻由 Codex 自己走完，会话里不会再撞到登录。 剩下 3 个是 ON_USE。

要定 工具面爆炸

180 个插件全带 = 系统提示词失控。 建议硬规矩：一次会话只带一个点选的插件。 需要多个时，让用户明确加，并显示当前会话带了哪些。

实现期 插件清单怎么读

两条路：跑 codex plugin list 解析输出（脆，格式会变）， 或直接读 ~/.codex/plugins/ 与 ~/.claude/plugins/cache/ 的清单文件（稳）。 建议读文件，与项目现有做法（读 ~/.claude.json 而非跑命令）一致。

实现期 图标要落地化

composerIcon 是插件目录里的 SVG 相对路径。 渲染层读本地文件要走已有的协议注册（同 bizone.ts 的 registerBizoneScheme），不能直接 file://。

实现期 一个还没装插件的机器

本机 ~/.codex/config.toml 里没有插件段， 即一个都没装。「插件」选项卡的空状态要给出路： 告诉用户怎么装，而不是显示一个空列表。
