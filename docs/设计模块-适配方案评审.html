结论先行

这套 composer 是个自治盒子——它的契约（CONTRACT.md §6）明令禁止 import 任何宿主 store，对外只走 6 个 prop，落盘由宿主负责（onExport(blob, format)）。所以「结合本软件适配」的接口面极小、极干净。

  • 动效渲染 + 导出整条链不依赖 Konva（纯 Canvas 2D）——这是最省事的部分，几乎零改动可复用。
  • 静态设计画布强依赖 Konva（KonvaCanvas.jsx 3026 行）——要交互式设计就得装 konva + react-konva。
  • taptv 专有耦合极少：硬耦合只有 composerStateMigration（可带过来），AI 可干净剥离，其余 1–2 行桩掉。
  • 量级：MVP 约移植 12–14K 行（多为照搬 + 改前缀/路径，非重写）+ 自写 150–300 行宿主胶水。
  • 推荐：方案 B（精简 MVP）——完整交互式「设计 + 预设动效 + 导出 demo/」，砍掉钢笔/布尔/SVG/文字轮廓等高级功能与其 3 个依赖。

1 · 它是什么

UnifiedComposer = 两个编辑器合体：designer（Konva 静态设计）+ animate（Canvas 2D 关键帧动效）。顶层单一状态 blob 挂在节点上：

type UnifiedState = {
  v: 1, mode: 'design' | 'animate',
  designState: { objects[], canvasWidth, canvasHeight, backgroundColor } | null,
  motionState: { layers[/* 带 keyframes + presets */], duration, fps, ... } | null,
}

2 · 三个分层方案

方案 A · 程序化导出核心最轻

只搬 animate 渲染+导出链（renderer / presetEngine / presets / exporter / exporterMp4 / precompRender / rebuildMotion，约 2,300 行，零 Konva，只装 mp4-muxer）。把一个 _unifiedState 直接渲成 PNG/WebM/MP4 落到 demo/。

没有交互式设计 UI——状态得由代码/上游喂入。适合「一键把某状态导出成图/视频」，不适合「用户在里面画」。

方案 B · 精简 MVP（推荐）推荐

完整交互式「基础设计（形状/文本/图片 + 图层）+ 预设动效 + 导出 demo/」。砍掉钢笔路径 / 布尔运算 / SVG 导入 / 文字转轮廓等高级功能（约 1,240 行 + 3 个 npm 依赖 svgpath/polygon-clipping/imagetracerjs），剥离 AI（约 680 行）。

  • 移植：designer 核心（Konva，约 6K 行）+ animate 核心（无 Konva，约 5.5K 行）+ 胶水（index/rebuildMotion/ErrorBoundary）+ 带上 composerStateMigration。
  • 新增依赖：konva、react-konva、mp4-muxer（zustand 已有）。
  • Eas-Term 侧自写：画布节点类型 + modal 挂载 + onExport→demo/ 落盘（约 150–300 行）。
方案 C · 完整移植最重

方案 B 全部 + 钢笔/布尔/SVG/文字轮廓 + 组件库 +（可选）AI 动效。约 16K 行全量搬，装全部依赖。功能对齐 taptv，但打包体积、依赖面、验证成本都最大，且 AI 部分在 Eas-Term 没有对应基建。

4 · 集成方式（Eas-Term 侧）

  • 作为画布组件：新增一个 CanvasComponentDef（和「版本管理」节点同机制，见 features/canvas/components/registry.tsx），节点里挂 composer（或点开进全屏 modal 编辑）。
  • 状态持久化：_unifiedState 存进节点 component.props，随 canvas.json 落盘，重开还原。契约的 onSaveState 正好对上。
  • 导出落盘：onExport(blob, format) → 渲染层 blob.arrayBuffer() → IPC → 主进程新 handler fs.writeFile('<项目>/demo/design-<时间戳>.{png|webm|mp4}')（按 blob.type 推扩展名，目录不存在则先建）。约 30–60 行。

5 · 风险与必验点

  • Konva 打包体积：设计态引入 konva + react-konva，包会变大（可接受，但要知道）。
  • MP4 走 WebCodecs：需 Eas-Term 的 Electron 37 / Chromium 支持——taptv 在 Electron 36 已验证可用，37 只会更好，但要在 dev 亲测导出一次。
  • composerStateMigration：带全套 286 行最稳；若想极简桩成 identity，需确认不破坏 restore。
  • 无深耦合：契约禁止 import 宿主 store，没有对云/资产/i18n/路由的耦合——这是最大的利好。

6 · 推荐路径

选方案 B，分三步走、每步在 dev 眼验：

  • Step 1：移植 animate 无 Konva 导出核心 + 写 onExport→demo/ 落盘胶水 → 先把「一个状态导出成 WebM/MP4/PNG 到 demo/」跑通（低风险、快见效，等价方案 A）。
  • Step 2：装 konva/react-konva，挂 designer 交互画布（砍高级功能）→ 用户能画形状/文本/图片 + 图层。
  • Step 3：接 animate 预设动效 + 设计→动画同步（rebuildMotion）→ 完整「设计 + 动效 + 导出」。

这样即使中途你想收手，Step 1 已经是一个能用的「导出到 demo/」能力，不浪费。
