# 文件路径边界评估

> 起因是「要不要给 `fs:read*` 加路径边界」。查下来结论要调个头：
> **读那条先别动，先看写这边的一致性缺口。**

## 一、原议题：`fs:read*` 没有路径校验

`fsGuard` 只覆盖写操作。这五条读通道零校验：

| 通道 | 渲染层调用处 | 性质 |
|---|---|---|
| `fs:readDir` | 2 | 返回目录内容给渲染层 |
| `fs:readTextFile` | 2 | 返回文件内容给渲染层 |
| `fs:readImageFile` | 2 | 返回图片内容给渲染层 |
| `fs:openPath` | 6 | 交给系统程序打开，**不回传内容** |
| `fs:showInFolder` | 8 | 在访达里定位，**不回传内容** |

### 建议：维持现状，但把理由写清楚

三个理由：

1. **后两条与前三条性质不同。** `openPath` / `showInFolder` 不把内容送回渲染层，
   它们做的事等价于「用户自己双击了这个文件」。给它们加边界，收益接近零。
2. **前三条的调用点全部是用户显式动作**：文件树点开、画布节点预览、粘贴图片。
   而画布的核心用法就是「把任意位置的文件拖进来看」—— 加边界会直接打断它，
   这是功能性倒退，不是安全加固。
3. 真要收紧，正确形态不是「限制在项目根内」，而是「限制在**用户本次会话显式指认过**的路径」，
   那需要一套 recently-granted 机制，不是加个 guard 能解决的。

**所以这条不是待办，是一个应当被记录的设计取舍。** 已写进
[03-agent角色边界](architecture/03-agent角色边界.md) 的运行时文件边界一节。

## 二、真正该看的：写这边的一致性缺口

`fsGuard.ts` 文件头写着它存在的理由：

> 渲染进程能被网页内容影响（画布里的 `<webview>` 开任意网址、`file://` 预览、
> MCP 桥接外部 agent），而 `fs:rename` / `fs:trash` 原来对路径零校验 ——
> 一句 `window.api.fs.trash('/Users/xxx')` 就能把整个 home 扔进废纸篓。

按这个理由，**凡是「路径由渲染层传入 + 主进程落盘」的通道都该有守卫**。
但有一条不符合：

### `design:exportToDemo`（`src/main/design.ts`）

```
projectPath ── 渲染层传入，零校验
filename    ── path.basename 兜底 ✅
              ↓
   mkdir(<projectPath>/demo, {recursive:true}) + writeFile
```

`filename` 防住了路径穿越，`projectPath` 没有。也就是说这条通道能在**任意位置**
建一个 `demo/` 目录并往里写文件。

**这不是已证实可利用的漏洞** —— 调用方 `DesignNode.tsx` 传的是节点自己的 cwd，
正常路径下就是项目目录。它是个**一致性缺口**：fsGuard 存在的前提（渲染层不可尽信）
如果成立，这条就该有守卫；如果不成立，fsGuard 本身的理由也就不成立。两者只能选一个。

### 次一级：`wiki:init`（`src/main/wiki/index.ts`）

只校验 `path.isAbsolute`，之后 `initWiki()` 建目录写文件。
但它的语义是「用户自己选一个目录建知识库」，路径来自系统目录选择框，
风险比上一条低一档。**记录即可，不必改。**

## 三、建议的优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | 给 `design:exportToDemo` 的 `projectPath` 加守卫 | 改动极小（复用 `guardDir`），消除一致性缺口 |
| 2 | 把这三条的取舍写进图纸 | 已做 —— 免得下次又有人从头评估一遍 |
| 3 | `fs:read*` | **不做**，理由见上 |
| — | `wiki:init` | 记录，不改 |

第 1 项的实际改法只有一行：在 `mkdir` 之前调一次 `guardDir(projectPath)`。
需要确认的是 `demo/` 落在项目根内时守卫会放行（会 —— `guardDir` 允许命中根目录本身）。

## 四、这次评估顺带纠正的一个说法

图纸最初写「`fsGuard` 是全项目**唯一**的写路径白名单」，是错的。
实际有三条独立写边界，各管一摊、刻意互不复用：

- `fsGuard.ts` —— 项目根 + 知识库根
- `skillLibrary/write.ts` + `skillLibrary/index.ts` 的 `skillWriteRoots()` —— skill 目录
- `projectPaths.ts` —— 项目根改名，守卫比 fsGuard **更窄**

三份源码的文件头都写了「为什么不复用 fsGuard」。**别为了"统一"把它们并回去** ——
放宽 fsGuard 一次，等于把 `fs:*` 所有写口子一起放宽。
