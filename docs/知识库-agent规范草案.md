# 知识库 · Agent 规范（草案）

> 状态：草案，等确认后由 Eas-Term 在知识库初始化时自动生成并安装。
> 关联：`docs/知识库-调研与执行规划.html` · 一手来源 `docs/reference/karpathy-llm-wiki.md`

---

## 为什么是两份，不是一份

这是整个规范设计里最关键的一个决定。

| | 全局触发规则 | 库内 schema |
|---|---|---|
| **装在哪** | `~/.claude/skills/eas-wiki/SKILL.md`<br>`~/.codex/AGENTS.md`（带标记的一段） | `<知识库>/CLAUDE.md`<br>`<知识库>/AGENTS.md` |
| **什么时候被读到** | **任何项目、任何会话**都可能被读到 | 只有 agent 的工作目录是知识库时才读 |
| **管什么** | **什么时候该去看知识库** | 看到之后怎么读、怎么写、怎么维护 |
| **长度约束** | **必须极短**（它常驻在模型的可选列表/上下文里，每轮都在花钱） | 可以长（只在真正干知识库的活时加载） |

一份写不了：你在写代码的项目里问「这个交互以前是怎么定的」，
agent 的 cwd 是代码项目，**根本读不到知识库里的 CLAUDE.md**。
所以「什么时候该去看」这条必须住在全局；而详细的读写约定放全局就是每轮都在烧 token。

## 一、全局触发规则（要短）

### Claude Code：`~/.claude/skills/eas-wiki/SKILL.md`

用 skill 而不是往 `~/.claude/CLAUDE.md` 里塞，理由是 skill 的 `description`
**本身就是触发机制**：模型平时只看到一行描述，判断相关才加载正文。
塞进全局 CLAUDE.md 则是每轮都在上下文里。

```markdown
---
name: eas-wiki
description: 查用户的个人知识库。当用户问「怎么做」类的方法问题、提到某个博主/作者/人名、
  问过去做过的决定或踩过的坑、或者要你产出文案/脚本/设计/剪辑方案时使用。
  也在用户明说「查知识库」「wiki 里有没有」时使用。
---

# 用户的知识库

位置：`{{KB_PATH}}`

## 怎么查（按顺序，别跳步）

1. 先读 `{{KB_PATH}}/index.md` —— 全库目录，每页一行摘要。**只读这一个文件**。
2. 从索引里挑出真正相关的页面（一般 1–3 篇），读它们。
3. 回答时说明你参考了哪几篇（写文件名，方便用户自己去翻）。

## 什么时候**不要**查

- 纯代码调试、跑构建、改配置这类执行类任务
- 用户已经把上下文给全了、不需要额外背景的时候
- 同一轮对话里已经查过了

## 硬规矩

- 索引里没有相关内容 → **直说没有**。不要用知识库里不存在的内容假装引用。
- 不要在这里写知识库。要沉淀新东西时，**提议**用户去知识库目录开一个会话，
  或者问他「要不要把这个结论存进知识库」——得到明确同意才写。
```

> `{{KB_PATH}}` 由 Eas-Term 在生成时替换成用户实际选的路径。

### Codex：`~/.codex/AGENTS.md` 里带标记的一段

Codex 的 `~/.codex/skills/` 目录存在但（本机 0.145 实测）是空的，
按需加载的 skill 机制不确定可用。所以走已经验证过的老路：
在 `AGENTS.md` 里插一段带首尾标记的内容，**幂等替换、可整段移除**。

因为它是常驻的，这段必须比 Claude 那份更短——只留触发条件和第一步：

```markdown
<!-- eas-wiki:begin 由 Eas-Term 自动维护，勿手改；删掉整段即可移除 -->
## 个人知识库

位置 `{{KB_PATH}}`。当用户问方法类问题、提到某个人名/博主、问过去的决定或踩过的坑，
或要你产出文案/脚本/设计方案时：先读 `{{KB_PATH}}/index.md`（全库一行摘要目录），
挑 1–3 篇相关的读，回答里注明参考了哪几篇。索引里没有就直说没有，不要编。
不要在别的项目里写知识库——要沉淀先征得用户同意。
<!-- eas-wiki:end -->
```

## 二、库内 schema（可以长）

`<知识库>/CLAUDE.md` 和 `<知识库>/AGENTS.md` 内容相同，
agent 的工作目录是知识库时自动加载。这份定义**动作怎么做**。

```markdown
# 这个知识库怎么用

你是这个知识库的维护者，不是通用助手。用户负责搜集素材、提问题、判断价值；
你负责所有的整理、归档、交叉引用和记账。

## 目录

- `00-收件箱/` 用户丢进来还没整理的原始素材
- `人物/`     博主/作者：思维模型、行为习惯、代表作、用户的实测反馈
- `方法/`     可迁移的做法（跨领域，不按学科切）
- `领域/`     编程 / 设计 / 剪辑 / 文案
- `项目/`     与 Eas-Term 项目对应的决策记录与复盘
- `素材/`     归档后的原件与逐字稿（**只读，永不修改**）
- `index.md`  全库目录：每页一行链接 + 一句话摘要
- `log.md`    只追加的时间线

## 三条不可违反

1. **`素材/` 和 `00-收件箱/` 里的原始文件只读。** 可以移动位置、可以重命名，
   **绝不修改内容、绝不删除**。它们是真相来源。
2. **重名不覆盖**，加后缀。
3. **归档前先出计划给用户过目**：哪个文件去哪、生成哪篇笔记、会牵动哪些老笔记。
   用户确认后才动手。

## 笔记格式

每篇都要有 front-matter，`summary` 和 `tags` 是硬要求——
索引和检索全靠它们，缺了这个库一过百篇就没法用。

    ---
    summary: 一句话说清这篇讲什么
    tags: [口播, 节奏]
    source: 素材/2026-07/xxx.mp4
    people: [[某某]]
    created: 2026-07-29
    updated: 2026-07-29
    ---

正文用 `[[双链]]` 互指。人物、方法、概念第一次出现就该有自己的页面。

## 三个动作

### Ingest（归档）
读素材 → 和用户讨论要点 → 写摘要页 → 更新 `index.md` →
更新被牵动的人物/概念页（一份素材通常会碰 10–15 页）→ 往 `log.md` 追加一条。

默认**一次一份、人在场**。用户明确要求批量时才批量，并先给出条数和成本预估。

### Query（查询）
先读 `index.md`，挑相关页读，回答带出处。

**好答案要归档回知识库**：用户觉得有价值的对比、分析、结论，
问他「要不要存成一篇」，同意就写成新页并更新索引。
探索本身也该参与复利，不要让它消散在聊天记录里。

### Lint（体检）
用户要求时才跑。检查：页面之间的矛盾、被新素材推翻的旧结论、
没有任何入链的孤儿页、反复被提到却没有独立页面的概念、该连没连的交叉引用。
**只出报告，不自动改**——改什么由用户点头。

## log.md 的格式

每条以固定前缀开头，方便 `grep "^## \[" log.md | tail -5` 看最近动静：

    ## [2026-07-29] ingest | 某某-如何做口播
    ## [2026-07-29] query  | 口播节奏怎么把控
    ## [2026-07-30] lint   | 发现 3 处矛盾、2 个孤儿页
```

## 三、同步：规则怎么保证真的到了 agent 手里

### 现状（已验证）

本机两条通道都是通的：

- `~/.claude/skills/eas-term/SKILL.md` —— 在，6116 字节
- `~/.codex/AGENTS.md` —— 有 `eas-term:begin` 标记段

也就是说**投递机制已经建好并跑通了**，知识库规则复用同一套即可。

### 但有三个会让规则失效的缺口，必须在实现时堵上

| 缺口 | 后果 | 对策 |
|---|---|---|
| **规则里嵌着知识库路径**，而技能包是「用户点安装那一刻」写死的 | 用户先装技能包、后建知识库 → 规则里没有路径，或路径是旧的 | **知识库初始化 / 改位置时，主动重写这两份规则**，不等用户再点一次 |
| 用户当初点了「永远不要提醒我」或直接拒装 | 知识库建好了，但 agent 从别的项目里永远不会想起它 | 知识库抽屉里显示**规则安装状态**（同词典那条开关的做法），没装就明着说「装了 agent 才会主动查」 |
| 用户手动删了 `~/.claude/skills/`、或换了台机器 | 静默失效，且**没有任何报错** | 每次打开知识库抽屉校验一次，缺了就提示重装 |

### 一条不能省的自检

规则失效是**静默**的——agent 只是"没想起来"去查，不会报错，
用户只会觉得"这知识库没用"。所以知识库抽屉里要有一行状态：

    规则已就绪  Claude ✓  Codex ✓        ← 绿
    规则未安装  agent 不会主动查知识库 [安装]  ← 黄
