代码地图加 AST 符号级可视化

从「文件依赖谁」下沉到「函数调用谁」。结论是值得做，而且比预想便宜得多 —— TypeScript 5.6 已经是本项目依赖，全仓 529 个文件跑一遍 2.5 秒、调用点解析率 96.6%， 零新依赖。真正的难点不在解析，在画面。

Verdict

一句话：解析这一层几乎白送，画面这一层才是活

裁 决

做，但只做 TS/JS，且分三期。 第一期只做「文件内结构 ＋ 死代码清单」—— 数据现成、画面简单、当天能看到东西。 第二期做「谁调用了这个」的邻域视图，那是理解代码最有用的一个问句。 第三期（跨文件全局符号图）建议不做，理由在第五节。

反对意见 · 必须先说清

「AST 可视化」这个说法本身会误导。 真把语法树画出来（SourceFile → ClassDeclaration → MethodDeclaration → ...） 对读代码几乎没有帮助 —— 那是编译器开发者的视图，不是理解业务的视图。

本报告讨论的是符号级依赖图：节点是函数/方法，边是「谁调用谁」。 AST 只是拿到它的手段。如果你要的是真·语法树浏览器，那是另一个东西， 价值低得多，我不建议做。

Pitfalls

四个「看着对其实全错」的坑

这一节是这份报告里最值钱的部分。四个坑全是我在测的过程中撞出来的 —— 每一个的共同点是：不报错、数字看着像那么回事，只是全错。 真动手时按这四条写测试，能省掉一轮返工。

坑 1  不解 alias → 每条跨文件调用都变成自环

checker.getSymbolAtLocation() 在 registerAgentHandlers() 上返回的符号， 它的 declarations[0] 是调用方文件里那条 import 语句，不是函数本体。

// index.ts:22  import { registerAgentHandlers } from './agent'
// index.ts:405 registerAgentHandlers()
                     ↑ getSymbolAtLocation 给的声明处是 index.ts 自己

修法  sym.flags & ts.SymbolFlags.Alias ? checker.getAliasedSymbol(sym) : sym

症状：死代码清单报出 644 个假阳性（真实数是 24）。 而且跨文件调用图会全变成一堆自环，看着像「每个文件都高度内聚」。

坑 2  「调用点」≠「被使用」

只数 CallExpression 会漏掉所有把函数作为值传出去的用法：

setInterval(reapIdleSessions, 60_000)      // 不是 CallExpression
<button onClick={handleSend}>              // JSX 属性
export { foo }                             // 再导出

修法  数 Identifier 的符号引用，不是数调用点

症状：reapIdleSessions / recoverInterrupted 被判成死代码，而它们正跑在 setInterval 里。修完之后 57 → 24。

坑 3  checkJs:false 的区域，符号解析静默失效

本仓库 tsconfig.web.json 是 allowJs:true ＋ checkJs:false， design 模块那一大片 .jsx 不进类型检查。checker 在那里不报错，只是解析不出来。

症状：DesignerView 有 10 处真实引用，却被判成死代码。 必须在结果里按文件标出「这块不可信」，不能混在一起给用户。

坑 4  动态 import 的解构绑定连不上

const { transcribeFile } = await import('../features/wiki/transcribe')

这是静态分析的固有边界，和 JS 那侧「import('./x' + name) 连不上」同类。 量不大（本仓库 1 处），但要在界面上如实说「这类连不上」，不要让用户以为图是完整的。

Architecture

加在哪一层

完全照现有代码地图的分层走，不新建平行体系。 现有的三层（纯判定 / 分析器 / IPC）都是 2026-09-03 这两天刚定型的， 符号图直接插进同一套。 

┌─ 现有 ─────────────────────────────────────────────┐
   src/shared/codeGraph.ts        纯判定 · 领地 · 循环定性
   src/shared/langImports.ts      Python/C/Swift 的 import 提取
   src/shared/gitignore.ts        目录该不该扫
   src/main/codeGraphAnalyze.ts   JS/TS 分析器（dependency-cruiser）
   src/main/multiLang.ts          另三种栈的路径解析
   src/main/codeGraph.ts          IPC 口（唯一碰 electron 的）
└────────────────────────────────────────────────────┘

新增 ↓

   src/shared/symbolGraph.ts       契约 ＋ 纯判定
                                  · SymbolNode / SymbolEdge 的形状
                                  · 「这个文件可不可信」（checkJs 判据 → 坑 3）
                                  · 死代码定性（导出/内部/入口豁免）

   src/main/tsSymbols.ts           TS Compiler API 那一层
                                  **零 electron，可 node --test**
                                  · 建 Program（两个 tsconfig 各一个）
                                  · 解 alias（→ 坑 1）
                                  · 数 Identifier 引用而非调用点（→ 坑 2）

   src/main/codeGraph.ts          复用同一个 IPC 口，加一个 mode 参数
                                  —— 不新开 channel，preload 那侧不用动
为什么不新开 IPC channel

现有 codeGraph:analyze 已经有「路径可不可信」那道门槛（ fs.statSync ＋ 目录判定），新开一个就要把那道门槛再写一遍。 加个 mode: 'module' | 'symbol' 参数，preload 和渲染层的类型都跟着现有的 CodeGraphResult 走。

为什么 tsSymbols 必须零 electron

和 multiLang.ts、omp/launch.ts 同一条纪律。 这一层全是判断，而判断错了的表现极其隐蔽（图照画、只是少几条边）—— 上面那四个坑没有一个会抛异常。只有能 node --test 裸跑，才可能给它们写回归测试。

顺带一提：这条纪律今天刚在 omp 那块兑现过一次 —— launch.ts 因为 import 了 mcpBridge 而无法单测，那段角色禁用逻辑一条测试都没有； 拆开之后补了 12 条。

The Hard Part

真正的难点：2756 个节点怎么画

解析已经证明便宜了。难的是现有的环形图装不下 —— 它在领地级是 23 个点、下钻到文件级已经要截到「耦合最重的 24 个」。 符号级是 2756 个。

这是最容易做砸的地方

直接把 2756 个函数扔进环形图，得到的是一团毛线 —— 而毛线回答不了任何问题。 这和之前那条判断是同一个道理：一张全是红的图等于没有红。 所以第三期（全局符号图）我建议不做，不是做不出来，是做出来没用。

三个能用的视图（按价值排序）

视图回答什么问题规模画法建议
文件内结构 这个文件里有哪些函数、谁调谁 单文件 5–30 个 现有环形图直接能用，不用新写布局 第一期
死代码清单 哪些函数没人用了 列表，本仓库 5 条 表格，不用画图 第一期
邻域视图 谁调用了这个 / 这个调用了谁（1–2 跳） 典型 10–40 个 环形图 ＋ 中心节点，需要「选中一个符号」的交互 第二期
全局符号图 整个项目的函数调用全景 2756 个 要换力导向 ＋ 聚类 ＋ WebGL 建议不做

邻域视图为什么值钱

「我要改这个函数，谁会受影响？」——这是读代码时最高频的一个问句， 而且现在只能靠全局搜索加人脑过滤。有了符号图它是一次查询。

这也是它和现有模块图的分工：模块图回答「哪块地在跨界拉扯」（宏观、找架构问题）， 邻域视图回答「动这里会碰到什么」（微观、找改动风险）。两者不重叠。

Other Stacks · 已修正

接现成的语言服务器（LSP），不要自己写解析
这一节被用户推翻了 · 原结论是错的

本报告初稿在这里写的是「Python / C / Swift 的符号级建议不做」， 理由是「tree-sitter 只给语法树不给符号表，解析准确率没法看」。

那个理由建立在一个错误前提上：以为只能自己写解析。 用户指出应该「根据各语言开源工具的状态去集成」—— 这是对的，而且指向一个 比 tree-sitter 好一个数量级的方案：LSP。

关键事实：LSP 标准里就有调用图

需要的三个查询，LSP 全都有标准方法，而且各语言的服务器都实现了：

谁调用了这个callHierarchy/incomingCalls邻域视图（最值钱的那个）
这个调用了谁callHierarchy/outgoingCalls邻域视图
还有没有人用textDocument/references死代码清单

本机实测：不用装任何东西，两个最难的语言已经就位

端到端实测 · 不只是「声明支持」

起一个 clangd，喂一个三层调用的 C 文件，走完整流程 （initialize → didOpen → prepareCallHierarchy → incomingCalls）：

static int helper(int x) { return x * 2; }
static int middle(int x) { return helper(x) + 1; }

prepareCallHierarchy → helper
谁调用了 helper → middle   ← 答对了

这条路为什么比 tree-sitter 强一个数量级

tree-sitter（初稿的方案）LSP（用户的方案）
拿到的东西语法树 —— 「这里有个调用，名字叫 foo」 符号表 ＋ 类型信息 —— 「这个 foo 是哪个 foo」
同名函数区分不了区分得了
方法调用 / 动态派发区分不了区分得了
包体代价每种语言 +1~5MB wasm0 —— 服务器是外部进程
加一门语言的成本找语法 ＋ 写 query ＋ 写解析 加一行配置（可执行文件名 ＋ 启动参数）
维护语言演进要自己跟各语言社区替你跟

本项目已经有这套通信的现成经验

LSP 是 JSON-RPC over stdio ＋ Content-Length 分帧 —— 和 omp 那条 ACP 传输是同一种协议形态。 src/main/agentChat/omp/transport.ts 就是一个写过、测过、 踩过坑的双向 JSON-RPC 状态机（零 electron、可 node --test 裸跑）。 新写一个 LSP 客户端可以直接照它的形状来，包括那些已经用事故换来的纪律 （空闲时也要泵队列、进程死了要合成终止事件、超时要能区分「没回」和「回了坏包」）。

代价必须说清楚 · 三条
  1. 服务器得装。C/Swift 在这台 Mac 上白送（Xcode 带）， Python/Go/Rust 要用户自己装。没装就如实说「装了 pyright 才能画 Python 的调用图」， 不要静默降级 —— 那正是现在「按目录 / 按入口」标记在做的事。
  2. 服务器要项目配置才准。clangd 要 compile_commands.json、 sourcekit-lsp 要构建过的索引、pyright 要认得出 venv。 缺了不会报错，只是答得少 —— 这是最危险的失败模式，必须在界面上标出可信度。
  3. 索引要时间。大项目首次起服务器要几秒到几分钟。 不能像现在这样「点开就同步扫完」，得做成异步 ＋ 进度。

修正后的建议

新的分期

第一期照旧走 TS 直连 —— typescript 包已经在依赖里， 2.5 秒、96.6%，比起一个 tsserver 更快更准，没必要为它引 LSP。

第二期把邻域视图做成 LSP 客户端的形状， TS 那条作为「内置 provider」接进同一个接口。 这样加 C/Swift/Python 就真的只是加配置 —— 而不是各写一套。 这个抽象要在第二期就定下来，第三期再改会很贵。

Phasing

分期与工作量

工作量的参照系是今天刚做完的多语言支持： langImports.ts ＋ multiLang.ts ＋ gitignore.ts ＝ 3 个新模块、47 条测试、约半天。

第一期 · 约 3–4 小时
文件内结构图 ＋ 死代码清单
新增 shared/symbolGraph.ts（契约 ＋ 可信度判据）、 main/tsSymbols.ts（建 Program、解 alias、数引用）。 界面上给代码地图的下钻视图加一个「符号」开关 —— 环形图不用改， 单文件 5–30 个节点它本来就画得好。死代码是一张表。
验收：本仓库那 5 个真死函数报得出来，8 个 checkJs:false 的必须被标成「不可信」而不是混进清单。
第二期 · 约 4–6 小时
邻域视图（谁调用了这个）
需要一个「选中符号」的交互入口 —— 从文件内结构图点一个函数， 或者从死代码清单点一条。加 1–2 跳的邻域查询与布局（中心 ＋ 环）。
验收：随便选一个函数，列出的调用方和 grep 出来的一致。
第三期
全局符号图 —— 建议不做
2756 个节点要换布局引擎（力导向 ＋ 聚类）、要 WebGL 才不掉帧， 而画出来是一团毛线。成本最高、价值最低。 真需要全局视角时，现有的模块级依赖图已经在回答那个问题了。

要提前定的两件事

  1. Program 缓存策略。2.5 秒是冷启动。改一个文件重扫要不要复用 Program？ TS 有 createIncrementalProgram，但要自己管 watch。 第一期先不做缓存，2.5 秒可接受；等真嫌慢再说。
  2. 别人的项目怎么办。本仓库有 tsconfig，别的 TS 项目也大多有。 没有 tsconfig 的纯 JS 项目 → 用默认 compilerOptions 兜底，但准确率会掉 （没有类型信息，方法调用解析不了）。这种情况要在界面上标出来， 和现在「按目录 / 按入口」那个标记同一个位置。
