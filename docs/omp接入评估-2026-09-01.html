Verdict

三句话结论

先给能拿去做决定的判断，论证在后面每一节。

裁决 · 1 · 接得进来，但「便宜」只对一半成立

AI 对话那一面是真的零 UI 改动——toolbarModel.ts 的文件头就写着这条硬约束： 「加第三个 CLI 时，只要它的 adapter 如实填好 capabilities，这个文件和它的调用方都不需要改一行」。 我核对过，工具栏确实一处 CLI 身份判断都没有。
但画布终端那一面完全不是这样：CanvasAgentBar.tsx 把 'claude'|'codex' 写死在 20 处， 连命令行都是两个手写函数（buildClaudeCmd / buildCodexCmd）。那才是主要工作量。

裁决 · 2 · 走 ACP，不走 RPC

v2 实测坐实 这是本评估里最硬的一条： docs/rpc.md 全文没有 approval / permission 任何一个字——RPC 模式没有审批面。 审批只在 ACP 上：session/request_permission，client-gated 的 bash / edit / delete / move。
选 RPC 等于新 CLI 天生比 Claude 弱一档（capabilities.approval: []，只能退回沙箱级）。 而 ACP 的 12 个 session 方法里，session/set_config_option 带 MODEL_CONFIG_ID = "model"， 换模型也覆盖得到——ACP 是我们要的能力的超集。
实测：审批请求真的发出来了，载荷比我们现在的 approval.request 还丰富（见下一节）。

警示 · 3 · 真正的代价不在写 adapter，在 AgentKind 这个联合类型

export type AgentKind = 'claude' | 'codex' 在非测试代码里被引用 54 处。 加第三个值会让 TypeScript 全线爆红——这是好事（编译器帮你把该改的地方全找出来，不会漏）， 但意味着这不是一个「加个文件就完事」的增量改动，而是一次必须一口气改完的横切。

Field Test

实测：三项判据全过，外加三件文档里没写的事

环境全程隔离：PI_CONFIG_DIR 指到一个临时目录、自定义 provider 走智谱免费档， 没有碰用户的任何现有凭证（~/.codex/auth.json 时间戳仍是 8-30）。验完即删。

判据结果实测到什么
① omp acp 能握手过 initialize 回 agentInfo: oh-my-pi 18.0.11、protocolVersion 1； agentCapabilities 报 loadSession / fork / resume / close 全有， MCP 支持 http + sse
② 审批真的从 ACP 发出来过 让它跑一条 bash ls，session/request_permission 如约而至，载荷带 toolCallId / title / kind:"execute" / rawInput:{command:"ls"} + 四个选项。我们回 allow_once 之后，工具真的从 pending → in_progress → completed 跑完
③ 认不认 .claude/CLAUDE.md过 在工作目录塞了一份写着暗号的 CLAUDE.md，直接问它「暗号是什么」——答对了。 我们注入项目规则那块工作量确实是 0

跑起来才知道的三件事

意外 · 1 · 审批有两条通道，只答一条会整轮挂死

同一次 bash ls，omp 问了两遍：

→ session/request_permission   // 结构化，带 toolCall + 四个选项
← {outcome:{outcome:"selected",optionId:"allow_once"}}
→ elicitation/create           // 第二条！形状完全不同，是个 JSON Schema 表单
   {mode:"form", message:"Allow tool: bash\nCommand: ls",
    requestedSchema:{properties:{value:{enum:["Approve","Deny"]}}}}
← {action:"accept", content:{value:"Approve"}}
→ tool_call_update: in_progress → in_progress → completed

我第一次只答了第一条，session/prompt 干等到 180 秒超时。 第二条只在客户端声明了 elicitation.form 能力时才发——不声明的话它会**直接拒掉那次工具调用** （我更早一次 task 调用报 failed，就是这个原因，当时误以为是模型太笨）。
接入时两条都得答。这件事两份报告和 omp 的 docs/ 里都没写。

意外 · 2 · 模型清单是动态的，我们的 capabilities 是静态的

没配 provider 时，session/new 只回两个 configOptions（mode / thinking）； 配上之后才出现第三个 model。也就是说「有哪些模型可选」是会话建立时才知道的，而且随用户配了什么变。
我们的 CliAdapter.capabilities 是挂在 adapter 上的静态对象， 在起会话之前就要交给 UI 渲染。
影响 要么照 Codex 那样 models: [] 给自由输入（能用但丢了 omp 的一大优势）， 要么给 CliCapabilities 加一条「会话建立后可修订」的路。这是第三步真正要设计的地方，不是写 adapter。

意外 · 3 · 三个小坑，每个都够卡半小时
  • PI_CONFIG_DIR 是相对 HOME 解析的。我传了绝对路径 /private/tmp/…， omp config path 回的是 /Users/biily/private/tmp/… —— 前面拼了 HOME。 不是它读不到配置，是它在另一个地方找。要不是有 omp config path 这条命令，这个能查很久
  • ACP 没有 turn_start 事件。要自己在第一条实质更新时合成， 否则我们的 reduce.ts 里 turnActive 永远置不起来，界面上「正在处理」不出现
  • tool_call_update 的 in_progress 会来好几次（一次 bash 来了两条）。 每条都当完成的话，执行卡片会在「跑着」和「跑完」之间来回跳

顺带确认的两件好事

审批选项比我们现在的丰富

它给四个：allow_once / allow_always / reject_once / reject_always。 我们的 approval.resolved 只有 'allow' | 'deny' 两档。
translator 里我只用 *_once —— *_always 会在 omp 那侧记住， 等于我们替用户改了他的配置。

prompt 缓存是通的

第二轮起 cachedReadTokens: 10944，实际计费 input 掉到 75。 omp 塞的系统提示词很大（首轮 24578 token），有缓存才用得起。

Two Surfaces

先认清：我们有两个互不相干的 CLI 接入面

这是整份评估的前提。你问「接成 cc 和 codex 的同级」，但我们这儿「cc 和 codex」同时存在于两个地方， 两边的扩展性天差地别。不分开谈会把工作量估错一倍。

接入面是什么怎么扩展接 omp 的成本
A · AI 对话
能力驱动		 AgentChatView + src/main/agentChat/。结构化对话：气泡、执行卡片、审批卡、用量。 进程由 session.ts 统一 spawn，输出经 translator 翻成 ChatEvent 写一个 CliAdapter 放进 adapters/index.ts 的数组。 adapters/index.ts 头上写着「这里不许写任何 CLI 特有逻辑」 低 一个 adapter 文件 + 一个 translator。工具栏、模型下拉、审批卡全部自动跟上
B · 画布终端
写死两档		 CanvasAgentBar.tsx（就是你截图里「角色 / 模型 / 思考 / 启动」那一条）。 它不走 adapter，直接拼一条 shell 命令喂给 xterm 没有扩展点。type Kind = 'claude' | 'codex' 写在文件第 36 行， 下面 19 处按它分支，命令行是两个手写函数 中高 要么补第三个分支（欠债 +1），要么顺手把它也改成能力驱动
保留的分歧 · 别顺手把 B 也重构了

「既然要改，不如把 B 也改成 adapter 驱动」听起来很对，但 B 和 A 的语义不一样： A 是「我们托管这个进程、解析它的输出」；B 是「用户自己在终端里跟 CLI 打交道，我们只帮他把命令拼对」。 B 的命令里还夹着角色契约文件、工具 allow/deny、MCP server 开关——这些在 A 那边是 StartOpts 的字段， 在 B 那边是 shell 参数。
我的建议是先只做 A，B 留着两档不动。理由：A 做完就能验证 omp 到底好不好用； B 的重构在「还不确定要不要长期用 omp」的阶段是纯负债。

Protocol

RPC 还是 ACP：审批把这道题做完了

omp 有四个进程入口（TUI / -p 一次性 / --mode rpc / acp）。 对我们只有后两个是候选。它们不是「差不多的两条路」，能力面差得很远。

能力omp --mode rpcomp acp我们需要吗
逐次审批 没有 rpc.md 全文 0 处 approval/permission 有 session/request_permission；bash/edit/delete/move 由客户端把关 必须。Claude 有、Codex 没有，新 CLI 若也没有就只能退回沙箱级
换模型 set_model / cycle_model / get_available_models session/set_config_option（MODEL_CONFIG_ID="model"） 要。对应我们的 paramChange 能力位

协议稳定性 omp 自己的私有 NDJSON，随它演进 ACP 是外部标准（Zed 那套），omp 只是实现方 ACP 更稳——对上游一天 31 个提交的项目，这一条分量很重
值得单独说 · set_host_tools 是个诱惑，但先别咬

RPC 的 set_host_tools 能让我们把画板那 52 个 MCP 工具直接注册进 omp 的工具表， 不经 MCP 进程、不占 xd://。听起来能省掉整条 MCP 桥。
但它只在 RPC 上有，而 RPC 没有审批——把我们的工具交给一个没有审批面的会话， 等于绕过我们自己那套 fsGuard 之外的第二道闸。这笔交易不划算。 先走 ACP + 现成的 MCP 配置注入（StartOpts.mcpConfigPath 那条路已经在跑）。

Model Wiring

「模型填入那边」要做什么

你专门问了这条。答案分两半，因为前面说的两个接入面在这件事上也是分开的。

A 面（AI 对话）：填 capabilities，别写清单

工具栏渲染什么，全看 adapter 的 capabilities。omp 有 60+ provider， 硬编码一份模型清单三天就过期。照抄 Codex 的做法——它的 models: [] 后面跟着一句注释： 「由 -m 传任意模型名，不预设列表——不是没填，是设计如此」。

capabilities: {
  models: [],                       // 空数组 = UI 给自由输入框，不给下拉
  effortLevels: [ ... ],            // 映射 omp 的 ThinkingLevel 档位
  compact: 'native',                // ACP 有 compact 命令，不是靠 slash
  contextUsage: true,
  approval: ['exec','patch','tool'], // ← 只有走 ACP 才敢这么填
  // approval 非空时不需要 sandboxLevels（adapters.test.ts 有断言钉这条）
}
// approvalHook 字段：**留空**。那是 Claude 专属的 PreToolUse hook 文件机制，
// omp 的审批走 ACP 协议，不装任何 hook。shared/agentChat.ts 里为这件事
// 写了整段注释：capabilities.approval 与 approvalHook 是两件事，混成一个布尔是事故的根。

换模型的能力位要新增一个取值。现在 paramChange?: 'slash' 只有一档（Claude 认 /model x）。 omp 走 session/set_config_option，既不是 slash 也不是「只能重启」， 要加第三个取值（比如 'acp-config'）。调用点判的是这个字段不是 CLI 名字，这条纪律已经写在类型注释里了。

B 面（画布 AgentBar）：动的是数据结构，不只是 UI

模型和思考档位按 kind 各存一套：

export type AgentKind = 'claude' | 'codex'          // ← 加值的地方
model?:  Partial<Record<AgentKind, string>>          // 切 agent 互不覆盖
effort?: Partial<Record<AgentKind, string>>
session?: Partial<Record<AgentKind, string>>         // 每个 kind 一条会话绑定

好消息：这个结构本来就是为「多个 CLI」设计的，加一个键不需要迁移旧存档（都是 Partial）。 但画布上「继续上次会话」那套按 kind 找绑定的逻辑、以及 canvasSlice.ts 里 migrateAgent 那段把老字符串转成对象的迁移代码，都要跟着认第三个键。

前端要做的匹配事件，一句话清单
  • 模型下拉：不用做。toolbarModel.ts 读 capabilities.models，空数组自动变自由输入
  • 思考档位：不用做。同上，读 effortLevels
  • 审批卡片：不用做。approval 非空就渲染，判的是能力不是身份
  • 「审批保护已开启」那个 chip：不用做，但必须确认它不出现——它问的是 usesApprovalHookFile(approvalHook)， 我们 approvalHook 留空，所以自动不显示。这正是当初把这两个字段拆开的原因
  • 登录 / 安装面板：要改 CliLoginPanel、CliSetupPanel、 AgentChatView 三处 as 'claude'|'codex' 断言写死了两档
  • 模型换了的回显：接 model_changed → 重推一次 session.ready，否则自动降级后界面显示的模型是假的

Dissent

反对意见与风险：不抹平

每一条都可能改变你的决定。

反对 · 1 · omp 默认 yolo，而我们的用户不是开发者心智

tools.approvalMode 默认值是 yolo：read / write / exec 全自动放行。 更细的一条：bash.patterns 的 deny 规则只管 bash 工具，同一条命令通过 eval 起子进程跑，在 yolo 下会被判成普通 exec 直接放行。
我们要接的话，第一天就得把默认改掉并显式配 tools.approval.eval。 这不是 omp 的 bug（它是开发者工具），但我们的画布上一个节点就是一个会话， 用户不会去读它的配置文档。

反对 · 2 · Bun 是硬依赖，而且我们正好卡在下限

omp 要 Bun ≥ 1.3.14，代码里大量用 Bun.file / Bun.$ / bun:sqlite。 这台机器上 bun --version 正好是 1.3.14——一格不多。
对用户意味着：装 Eas-Term 之后还要装 Bun 才能用第三个 CLI。 我们的 agentInstall 面板要多一层前置检查，否则用户点了安装、跑一条 bun install -g、 然后看到 command not found: bun。

警示 · 3 · 上游一天 31 个提交，而且真的会改格式

有确凿证据：会话格式做过 v1→v2→v3；会话目录命名在 17.2.5 改成哈希式、17.2.9 又被回滚； pi-native 这个名字先是一种工具调用方言，v16.0.10 换格式、v16.2.2 直接删掉、名字被复用给了别的东西。
这正是选 ACP 而不是 RPC 的第二个理由——ACP 是外部标准，omp 只是实现方； RPC 是它的私有协议，跟着它一起动。我们的 cliContract 自检机制要给 omp 也配一份。

警示 · 4 · 这两份报告都没实跑过

报告作者自己写了：「我没有安装、没有运行、没有跑测试」。 性能数字（Grok 4 Fast −61% token 之类）是 README 自述。
我这份评估同样是源码与文档核对——omp 侧我读的是它的 docs/rpc.md 与 approval-mode.md 原文和 ACP 实现里的方法名，我们侧是逐文件 grep。 但我一次都没有真的把 omp 跑起来。下一节第一步就是这个。

反对 · 5 · 「同级」这个目标本身值得推敲

cc 和 codex 是同一类东西：一个 headless CLI，吃 prompt 吐事件流。 omp 不是——它是一个 harness 底座，自带子 Agent 集群、记忆管线、A2A 总线、Agent Hub UI。 把它塞进「第三个 CLI」这个位置，等于只用它 20% 的能力，还要为剩下 80% 做隔离 （关子 Agent 订阅、关记忆、关 collab、关桌面控制…）。
另一种可能性：omp 的价值对我们不在「多一个 CLI 选项」，而在它的几个设计可以搬进我们自己的内核—— 会话 append-only 树 + leaf 指针、URL 寻址、提示词一律 .md 不进代码。 这三样与语言栈无关，报告自己也把它们标成「可移植性最高」。
