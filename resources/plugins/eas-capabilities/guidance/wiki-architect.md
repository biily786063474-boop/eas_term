# 重新设计知识库

这份文件是「用户想按自己的分类重建知识库」的引导流程 —— 从声明纪律到读现状、问分类、
定方案、建库切换，每步该问什么、该调什么工具、配置写错会在哪被拒绝。SKILL.md
判断出用户要换分类后来读这份。

## 先声明：不动用户现有的库

**老库不搬、不改、不删。** 整个流程做的事是「建一个新的、切过去」——旧库连一个字节都不碰，
还在原来的磁盘位置，以后什么时候想指回去都行（走第四步同一个「位置设置」入口）。
开场就把这句话说给用户听，不要让他担心「重来一遍会不会把原来的东西弄丢」。

## 第一步：读现状

先搞清楚三件事：现在有没有库、有多少篇笔记、这些笔记怎么分布在各个目录里。

调 `wiki_query`：

- 响应里**没有** `path` 字段 → 没有旧库可参考，直接跳到第二步。这包括两种情况：
  真的还没配过库（`configured: false`），或者配了但读不出来（`configured: true`
  但没给 `path`——目录被移走了或者网络盘没挂上）。是后一种的话跟用户提一句，
  不影响继续往下建新库。
- 响应里**有** `path` 字段 → 库存在且读得出内容。拿这个 `path` 直接去看盘上真实的样子。
  响应里如果有 `library` 字段，那就是这个库已经自定义过的分类（`dirs` 这时候没用——
  它固定是内置八目录的形状，不反映自定义库的真实目录）；没有 `library` 字段才说明
  `dirs` 反映的是这个库的真实情况。不管哪种，数分布还是用 shell 更准：

  ```sh
  ls <path>                                                                     # 顶层目录叫什么、有几个
  find <path> -mindepth 2 -maxdepth 3 -name '*.md' \
    | sed "s|<path>/||" | cut -d/ -f1 | sort | uniq -c | sort -rn               # 每个目录堆了多少篇
  ```

  两条对照着看：`ls` 里有、但计数里没出现的目录，就是几乎空的那些。

把结果摊给用户看：一共多少篇，哪个目录堆得最多，哪个几乎是空的。这不是替他做决定，
是让他接下来说「怎么分」的时候有依据，不是凭空想。

## 第二步：问清怎么分

**一次一个问题**，问完等答案，不要一口气把下面几条都甩给用户。

核心问题，**原话问，别改写成别的**：

> 你平时往里放的东西，大致分几类，每类一句话怎么描述？

**不能问成「你要几个文件夹」。** 后者会得到一堆没有 `purpose` 的空目录名；`purpose`
才是要写进 agent 说明书正文、决定东西该往哪放的那句话，是整份配置里最该斟酌的字段，
必须让用户自己说清楚，不能你替他编。

拿到分类之后，视情况再单独追问（同样一次一个，别和上一个问题揉在一起问）：

- **收件箱**：这些类别里有没有一类是「还没来得及整理、先丢进去」的？知识库必须有且
  只能有一个这样的目录（`role: "inbox"`）。用户的回答里如果没有，就直说会加一个
  「00-收件箱」，问他这个名字行不行。
- **原始素材**：如果用户提到了「素材」「附件」「原始文件」这类不算笔记、只是存档的
  类别，问要不要标成 `role: "raw"`（不进索引、不算反链，和收件箱一个待遇）。用户已经
  说清楚某类就是「纯存档、不会写成笔记」时才问，不是每次都要追问。

**不要替用户想分类方案。** 问清楚、记下来，拍板的是他。

## 第三步：给方案等确认

把第二步收集到的内容整理成一份可以直接拿去建库的草案，给用户看：目录清单（含角色
标注）+ 每个目录的一句话 + front-matter 字段。例如：

```
目录            角色         一句话
00-收件箱        inbox       丢进来还没整理的原始素材
课题                        一个课题一篇，记它的进展与结论
文献                        读过的论文与书，一篇一条，含出处
_模板            templates   新建笔记的模板

front-matter 必填：summary、tags
```

每个目录的一句话直接用用户在第二步说的原话整理，别自己润色成不一样的意思——那句话
以后要一字不改地写进 agent 说明书。`front-matter` 没有特殊需求就用 `summary`、`tags`
两个：体检（`wiki_lint`）认的就是这两个字段名，换别的名字体检也不会去找它们。

**给完方案等用户表态，不要问完问题就直接建。** 用户要改名字、拆合类别、调整一句话，
回到方案里改，改完再确认一遍——直到他明确说「可以」或者等价的话，才进第四步。

## 第四步：建库

① **定位置**：建议一个新目录，不要挑在老库文件夹内部，也不要就用老库现在那个目录
（这个目录很可能就是应用自己默认建议的那个位置，老库大概率已经占着）。路径尽量不带
空格和中文——它会被拼进 shell 命令和 agent 的规则文本，多一处引号漏了就出错。没有
强烈偏好就建议放在 `~/Documents/` 下起个英文名，问用户一句「建在这可以吗」。

② **建骨架**：在新目录下为方案里的每个目录建文件夹（`mkdir -p`），包括标了
`inbox`/`raw`/`templates` 的那些。

③ **写配置**：在新目录根下写 `.eas-wiki.json`，字段和值严格照用户在第三步确认过的
内容，格式对照下一节「配置格式与校验规则」——写完自己按那份清单过一遍，别等用户
指出来才发现填错了。

④ **指过去**：**这一步只能用户自己在 Eas-Term 界面里点，没有工具能替他做**，也别想着
直接改 app 的配置文件抄近道——那不在你的工具范围内，瞎改会绕开这一步唯一的安全阀：
用户亲眼确认要切的是这个目录。告诉他：画布左边有个「知识库」抽屉，点开——

  - 如果他从没配置过库（抽屉显示的是引导页）：点「选别的地方…」，在弹出的目录选择器
    里翻到刚建的那个目录，选中确认；
  - 如果他现在正用着老库：点抽屉右上角齿轮「位置设置」→「换个位置」，同样选中刚建
    的目录。

  点完这一下，Eas-Term 会自动把骨架里漏掉的目录补齐，并生成四份说明书（`CLAUDE.md` /
  `AGENTS.md` / `index.md` / `START-HERE.md`），内容严格按 `.eas-wiki.json` 里的分类
  来——**这四份文件不用你去写**。它们走的是有版本标记的托管区机制，手写的文本没有那个
  标记，以后 app 升级时更新不到它们，库会永远停在今天这个版本上。

⑤ **收尾确认**：等用户说切好了，回头核对：`wiki_query` 的 `path` 是不是已经变成新
目录；去新目录 `ls` 一眼，骨架目录和四份说明书是不是都在；`wiki_inbox` 应该是空的
（新库）。把「建了几个目录、说明书里写的是什么分类」念给用户听，收尾。老库还在原来
的位置，之后想指回去，走的是同一个「位置设置」。

## 配置格式与校验规则

`.eas-wiki.json` 放在库根目录（和 `CLAUDE.md`、收件箱目录同一层）。一份合法配置：

```json
{
  "version": 1,
  "dirs": [
    { "name": "00-收件箱", "purpose": "丢进来还没整理的原始素材", "role": "inbox" },
    { "name": "课题",     "purpose": "一个课题一篇，记它的进展与结论" },
    { "name": "文献",     "purpose": "读过的论文与书，一篇一条，含出处" },
    { "name": "_模板",    "purpose": "新建笔记的模板", "role": "templates" }
  ],
  "frontMatter": { "required": ["summary", "tags"], "optional": ["status", "source"] }
}
```

- `version`：数字，不写就当 1。
- `dirs`：非空数组，每项 `name` + `purpose` 必填，`role` 可选。
- `frontMatter.required`：不能是空数组——没有特殊需求就写 `summary`、`tags`（原因见
  第三步）。`frontMatter.optional` 可以是空数组，随便加，没有强制检查。

会被拒绝的情况（照代码里 `validateTaxonomy` 抄的，别自己编别的理由）：

- 配置不是一个对象
- `dirs` 得是非空数组
- `dirs` 里有不是对象的项
- 有目录没有 `name`
- 目录名不能含斜杠（`/` 或 `\`）——会建出嵌套
- 目录名不能以点开头——会被 `walkNotes` 当隐藏项跳过，等于永远读不到
- 目录名重复
- 某个目录没写 `purpose`——**那句话要写进 agent 说明书，空的等于没说**
- `role` 只认三个值（不写也行，写别的会被拒绝，见下表）
- **必须恰好有一个收件箱目录**——收件箱有专属机制（徽章计数、记录「这份素材原来在
  哪」），没有它整理流程会断
- 模板目录最多一个
- `frontMatter.required` 不能为空

`role` 的三个取值：

| role | 干什么 |
|---|---|
| `inbox` | 收件箱。必须恰好一个。用户丢进来、还没整理的原始素材，有徽章计数和来源记录 |
| `templates` | 新建笔记的模板来源。最多一个，不写也行 |
| `raw` | 原始素材区，和收件箱一个待遇——**不进索引、不算反链**，不会被当成笔记扫描。用户有「素材/附件」这类只存档、不当正文的目录，标它 |
| 不写 | 普通笔记目录，正常参与索引、图谱、体检 |

配置解析失败（读不到、JSON 解析不了、校验不过）时，Eas-Term **不会**回落到内置八目录
去建库——那样会把用户在第三步确认过的分类真的改写成内置形状，不可逆。实际行为是
**原地停手**：不建目录、不改任何说明书，知识库抽屉会出现一条提示说明配置读不出来。
所以第③步写完 `.eas-wiki.json` 后，**先自己核对一遍再让用户点第④步的按钮**：
点完如果新目录下没有出现骨架和四份说明书、抽屉也在提示配置有问题，就是配置没通过
校验——回去核对上一节的校验规则，改好 `.eas-wiki.json` 后让用户在「位置设置」里
把同一个位置重新点一遍。
