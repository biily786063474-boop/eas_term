# 往辞典里加一条

用户说「把 XXX 收进辞典 / 记进辞典 / 加到辞典里」时读这份。

## 先说清楚这件事的边界

辞典是 Eas-Term 里那本前端术语手册（标题栏右上角「辞典」）。它现在有 381 条，
每条都有：中英文名、检索词、一句话解释、**hover 时看的示意图**、
**点一下挂进对话的完整提示词**、以及两级分类。

**新加的一条必须长得和它们一样。** 缺字段的半截词条混进去，既帮不上忙又稀释整本的可信度 ——
上一版有个「自动沉淀」的功能就是这么废掉的：它扫出术语名就往里写，
产出一堆点开什么都没有的空壳，最后整个拆掉了（2026-08-31）。

所以这五步**一步都不能省**，而且每一步都要停下来让用户确认，不要自己一路跑完。

---

## ① 定分类：给 1–2 个候选，让用户选

一级 = **用户想干什么**（场景），二级 = 具体手法。不是按技术门类切的。

先在下表里定位，然后这样问：

> 「边缘自动滚」我看有两个位置说得通：
>   A. 列表与滚动 › 吸附与锁定 —— 如果你把它当成「滚动怎么停」的一种
>   B. 手势与拖拽 › 拖放与排序 —— 如果重点是「拖着东西到边上」
> 你按哪个找它？

**判据是「用户会去哪儿找它」，不是「它技术上属于什么」。** 拿不准就问，别自己定。

## ② 补结构：逐字段填，别猜

| 字段 | 要求 |
|---|---|
| `en` | 英文原名，用业界通行写法（`Scroll Snap` 不是 `ScrollSnap`） |
| `zh` | 中文名。已经有通行译法就用它，没有就直白描述，别生造 |
| `keywords` | **含实际会打出来的写法**：中文名、英文名、英文缩写、常见别称。「边缘自动滚」要含 `edge scroll` / `自动滚动` / `边缘滚动` |
| `logic` | 80–140 字，说清**它是什么 + 怎么实现**。不许同义反复（「防抖就是防止抖动」这种一律重写） |
| `category` | 老的三类之一：`interaction` / `motion` / `visual`。**必填**，是为兼容留的 |
| `cat1` / `cat2` | ① 里定好的那一对。可选，但**给了就必须是表里真实存在的一对**，写错当场被拒 |

填完把这几个字段念给用户听一遍再往下走 —— `logic` 写歪了，后面的图和提示词都会跟着歪。

## ③ 做演示图：这一步不能省

hover 到词条上看到的那张图，**是这本辞典最有价值的部分**。没有图的词条就是个名字。

要求一张**极简内联 SVG**：

```
viewBox="0 0 240 120"，font-family="sans-serif"
标注文字 #8a8f99 · 强调/输入 #e0a45e · 输出/结果 #6ea8fe
```

画什么：**画这个概念的行为，不是画一个图标**。「防抖」画的是「输入连打五下 → 输出只有一下」，
不是画一个弹簧。左边标「输入」、右边标「输出」这类对照最好用。

**四条硬约束**（写入前会被清洗，踩了等于白画）：

- **不许用 `<style>` 标签** —— 会被整个删掉。所有样式写成元素属性（`fill="#8a8f99"`）
- **不许用 `<use>`、`<image>`、`<iframe>`、`<foreignObject>`** —— 同样被删
- **不许有 `href` / `src` 外链**（`#` 开头的锚点除外）、不许有 `on*` 事件属性、不许 `<script>`
- 整段**不超过 8000 字符**，超了会被整个丢掉，你不会收到任何提示

画完把 SVG 用 `canvas_open_html` 摆到画布上让用户看一眼再往下走 ——
**别让用户凭一段 XML 想象它长什么样**。

## ④ 写提示词：写指令，不是写解释

用户点这个词条时，它会作为一个 chip 挂到对话输入框上，**发送时展开成全文**发给模型。
所以你写的不是解释，是**一条能直接照着动手的指令**。

自检标准：把这段话单独发给一个不认识这个术语的模型，它能不能直接开始写代码？
会不会反过来跟用户讨论概念？会 → 你写成解释了，重写。

**结构（六段，顺序固定，中文方括号，段间不换行）：**

```
<开头句>【要达到的效果】…【触发时机】…【实现方法】…【关键参数】…【别踩的坑】…【依赖】…
```

**开头句必须指向「上文」** —— 用户点 chip 时诉求已经写在上文了，二选一：

- 效果 / 组件 / 交互类：`在上文提到的位置实现「{zh}」（{en}）。`
- 机制 / 性能 / 规范类：`按「{zh}」（{en}）的要求处理上文提到的代码。`

| 段 | 写什么 | 不要写 |
|---|---|---|
| 要达到的效果 | 一句话：用户**看到/感受到**什么 | 原理、术语定义 |
| 触发时机 | 什么条件下发生（滚动到视口 / 输入停止 300ms / 点击 / 常驻） | 含糊的「需要时」 |
| 实现方法 | 用什么 API、什么结构、分几步。**这段最长** | 「使用相关库即可」 |
| 关键参数 | 2–4 个，`名=值（说明）`，**带单位**。没有数值可调的就写判定依据 | 没有推荐值的空列举 |
| 别踩的坑 | 这件事**最常见的做错方式**，具体到症状 | 「注意性能」这种正确的废话 |
| 依赖 | 真实存在的库名；**能用原生就写「无需依赖」** | 编造库名 |

长度 450–500 字（汉字计）。**不许编造 API** —— 记不清参数名就换成你确定的做法。

## ⑤ 收录

调 `dict_add`，一次可以提交多条：

```json
{ "terms": [{
  "en": "Edge Auto-scroll", "zh": "边缘自动滚",
  "category": "interaction", "cat1": "列表与滚动", "cat2": "吸附与锁定",
  "keywords": ["edge scroll", "自动滚动", "边缘滚动", "边缘自动滚"],
  "logic": "拖拽时指针进入容器边缘的感应带就持续滚动…",
  "svg": "<svg viewBox=\"0 0 240 120\" …>…</svg>",
  "prompt": "在上文提到的位置实现「边缘自动滚」（Edge Auto-scroll）。【要达到的效果】…"
}]}
```

它会**逐条校验**，不合格的单独退回并说明理由，合格的照常写入 —— 所以一次提交多条时，
要看返回的 `rejected` 数组，别以为 `ok: true` 就是全进去了。

会被拒的：缺 `en` / 缺 `zh` / `logic` 短于 20 字 / `category` 不在三类里 /
`cat1`+`cat2` 不是有效的一对 / 这个 id 已经收录过。

写入 `~/.eas/dict-user.json`，**只在本机，不上传**。辞典面板会当场多出这一条，
让用户 hover 上去看一眼图、点一下试试 chip —— 到这儿才算完。

## 不要做的事

- **不要自动收集。** 用户没开口就不要往辞典里加东西。这条链路 2026-08-31 专门拆掉过：
  它归类只能靠猜、产不出示意图、还在用户没看的时候花钱。
- **不要跳过第 ③ 步。** 「先收进去，图以后再补」= 又造一个空壳。
- **不要一次加一堆。** 用户说「把这几个都收了」时也一条条走完五步；
  批量塞进去的必然是没图没提示词的半成品。
