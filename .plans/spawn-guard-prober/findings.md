## 一、team_spawn 硬约束：生效，但生效的**形态**和任务前提描述的不一样

**判据**：我按要求实调了一次 `team_spawn(role='probe-child', task='什么都不用做')`，
拿到的不是「团队层拒绝派活」的业务错误，而是**工具根本不存在**的 harness 级错误。

**证据（原样，未加工）**：

调用：
```
team_spawn(role="probe-child", task="什么都不用做")
```

返回：
```
Error: No such tool available: team_spawn
```

配套证据（两次工具面探测，都在这次调用之前）：

| 探测 | 命令 | 结果 |
|---|---|---|
| 1 | `ToolSearch("select:team_spawn", 3)` | `No matching deferred tools found` |
| 2 | `ToolSearch("team spawn agent 派活", 10)` | 只返回 `SendMessage` / `RemoteTrigger` / `TaskStop` / `EnterWorktree` / `TaskOutput`，无 `team_spawn` |
| 3 | `ToolSearch("+team", 15)` | 只返回 `TaskStop`（因其描述里含 "agent-team teammate"），无 `team_spawn` |

**这条推翻了任务里的一个前提**（显式写出，不替人抹平）：

任务简报的硬约定 1 写的是「**系统会拒绝**你调 `team_spawn`」。
实测的机制不是「拒绝」，是「**裁剪**」—— `team_spawn` 压根没出现在团队成员的工具面上
（既不在已加载工具列表，也不在 deferred 列表，`ToolSearch` 三种查法都搜不到）。
两者结果相同（成员派不出活），但可观测性差别很大：

- **裁剪**：调用在 harness 层就被判为「无此工具」，请求**没有到达** team 层。
  → team 侧不会留下任何「某成员试图派活被拒」的记录。
- **拒绝**：调用到达 team 层、被守卫拦下并回一条业务错误。
  → 会留下可审计的记录。

**这对主 agent 的实际影响**：如果 0.4.35 的验收标准里有「团队成员越权派活要能被审计/告警」，
那么当前实现**满足不了** —— 越权尝试是静默失败的，只有那个成员自己的 transcript 里有一行
`No such tool available`。如果验收标准只是「成员不能派出活」，那么**已达成，且比运行时守卫更硬**
（守卫可能被参数构造绕过，工具不存在没法绕）。这两种验收标准指向相反的结论，
需要主 agent 确认原本要验的是哪一个。

**边界（我没做什么）**：
- 只调了 1 次，**未重试、未换参数、未尝试任何绕过路径**（任务明确要求，且绕过本身违反硬约定）。
- **没有读任何实现源码** —— 我没有去看 team_spawn 是在哪一层、用什么机制从成员工具面上摘掉的。
  上面「裁剪 vs 拒绝」的判断完全基于**外部可观测行为**（三次 ToolSearch + 一次实调的返回文本），
  不是基于代码。想确认代码层的真实机制（例如：是按 agent 角色过滤 MCP 工具列表，
  还是 MCP server 侧对非编排者身份返回 tool-not-found），**需要有人去读 MCP 工具注册/过滤那段实现** —— 这块我没覆盖。
- **没有验证第二条硬约定（`notify` 会被拦掉）**。任务没要求，且真调一次会打扰用户。
  所以「notify 被拦」在本报告里是**未验证**状态，不要当成我验过了。
- 没有验证「主 agent（编排者）身份下 `team_spawn` 是可用的」—— 我没有那个身份，测不了。
  「只对成员裁剪、对编排者保留」这个假设**未经我验证**。

## 结论怎么写

不要只说「做完了」。每条都要让人不看你的原始材料就能判断：

- **判据**：你凭什么这么说
- **证据**：文件:行号 / 命令输出 / 实测数据
- **边界**：你没做什么、这条结论在什么情况下不成立 —— 这项最容易漏，
  也最容易让人高估你的覆盖面

如果你推翻了任务里的某个前提，或者发现结论之间有分歧，**显式写出来**，不要替人抹平。

## 卡住了怎么办

同一个错误第 2 次出现就换方案，别重复同一个操作；第 3 次还不行就停下来重新审视假设。
每次失败在 progress.md 追加一行：试了什么 → 结果 → 下次换什么。

真过不去，在 findings.md 里开一段 `## BLOCKED`，写清卡在哪、缺什么。
**不要静默跳过，也不要猜一个答案填上去** —— 主 agent 宁可收到「这块没做成」，
也不要收到一个看起来完成、实际编出来的结论。

每做约 10 次工具调用停一下，回头看看还是不是在做任务里那件事。跑偏了在 progress.md
记一句原因。（工具调用多了模型会开始忘记最初的目标，这一步是对抗它的。）
